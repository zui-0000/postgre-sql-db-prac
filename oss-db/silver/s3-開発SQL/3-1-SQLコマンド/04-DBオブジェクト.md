## 学習メモ

### スキーマ（データベースの中の名前空間）

PostgreSQL のオブジェクトは、次の階層で管理される。

```text
データベースクラスタ
└── データベース（postgres、mydb など）   ← 1つの接続は、この1つに繋がる
    └── スキーマ（public、sales など）    ← 1つの接続の中で名前空間を分ける単位
        └── テーブル、ビュー、関数など
```

- **1つの接続は1つのデータベースにしか繋がらない**。別のデータベースのテーブルを SQL で直接参照すると、`ERROR: cross-database references are not implemented` になる（[S2.2](../../s2-運用管理/2-2-標準付属ツール.md) の「\c は接続し直し」を参照）。
- 同じ接続の中で名前空間を分けたいときは、**スキーマ**を使う。
- テーブルは必ずどこかのスキーマに属する。既定のスキーマは **`public`**。

#### 同じ名前のテーブルを、別々のスキーマに作れる

```sql
CREATE SCHEMA sales;
CREATE TABLE sales.orders (id int);
CREATE TABLE public.orders (id int, note text);
```

```text
 Schema |  Name  | Type  |  Owner
--------+--------+-------+----------
 public | orders | table | postgres
 sales  | orders | table | postgres
```

#### スキーマを省略すると、search_path の順に探す

スキーマ名を付けずに `orders` と書くと、設定パラメータ `search_path` に並んだスキーマを先頭から順に探す。既定値は次のとおり。

```text
   search_path
-----------------
 "$user", public
```

`"$user"` は「接続しているユーザーと同じ名前のスキーマ」の意味で、そのスキーマがなければ飛ばされる。そのため既定では `public` が使われる。

実機で確認した結果:

```text
（既定の search_path）
\d orders  →  Table "public.orders"

SET search_path TO sales, public;
\d orders  →  Table "sales.orders"     ← 見つかるテーブルが変わった
```

#### MySQL の「データベース」は PostgreSQL の「スキーマ」に近い

MySQL の公式ドキュメントには「`CREATE SCHEMA` は `CREATE DATABASE` の同義語である」と書かれている。つまり MySQL の「データベース」は、PostgreSQL の「スキーマ」に近い。

| | MySQL | PostgreSQL |
| --- | --- | --- |
| 階層 | サーバー ＞ データベース（＝スキーマ）＞ テーブル | クラスタ ＞ データベース ＞ スキーマ ＞ テーブル |
| 切り替え | `USE`（同じ接続のまま） | `\c`（接続し直す） |
| 別のデータベースのテーブル | `db.table` で参照できる | 参照できない（拡張機能が必要） |
| 1つの接続の中で名前空間を分けるには | データベースを分ける | **スキーマを分ける** |

MySQL で複数のデータベースをまたいで JOIN するような設計は、PostgreSQL では1つのデータベースの中でスキーマを分けるのが自然である。別のデータベースを参照する `postgres_fdw` などの仕組みは、Gold の出題範囲。

`public` スキーマの権限は、PG15 で変わった（[S2.5](../../s2-運用管理/2-5-基本的な運用管理作業.md) の「⚠️ 試験と最新版の違い」を参照）。

### ビュー（テーブルとの違い）

| | テーブル | ビュー |
| --- | --- | --- |
| 中身 | **データそのもの**を持つ | **SELECT 文（問い合わせ）だけ**を持つ。データは持たない |
| ディスク上のファイル | ある | ない |
| `SELECT` したとき | 保存してあるデータを読む | 定義した SELECT 文を、そのたびに実行する |
| 使う側から見ると | どちらも `SELECT ... FROM 名前` で同じように読める | ← |

公式ドキュメント（CREATE VIEW）には「ビューは物理的には実体化されない。ビューを参照するたびに、問い合わせが実行される」とある。

db で確かめた結果:

```sql
CREATE TABLE fruits (name text, price int);
INSERT INTO fruits VALUES ('りんご', 150), ('メロン', 1200);
CREATE VIEW expensive_fruits AS SELECT name, price FROM fruits WHERE price >= 1000;
```

```text
SELECT * FROM expensive_fruits;      → メロン だけ

INSERT INTO fruits VALUES ('マンゴー', 2000);
SELECT * FROM expensive_fruits;      → メロン、マンゴー（テーブルに足した行が、ビューにもすぐ出る）

     relname      | relkind | pg_relation_filepath
------------------+---------+----------------------
 fruits           | r       | base/5/16787          ← r = テーブル。ファイルがある
 expensive_fruits | v       |                       ← v = ビュー。ファイルがない
```

TypeScript で例えると、テーブルは値を保存したプロパティ、ビューは getter にあたる。

```ts
class User {
  firstName = 'Asuka';                                      // テーブル: 値を保存している
  get fullName() { return `${this.firstName} Langley`; }    // ビュー: 読むたびに計算する
}
```

システムカタログにも、テーブルとビューがある。

| 名前 | 種類 | 中身 |
| --- | --- | --- |
| `pg_database`、`pg_authid` | テーブル | データベースやロールの情報を保存している |
| `pg_roles` | ビュー | `pg_authid` を読むが、パスワードの列を `'********'` に置き換えて見せる |
| `pg_settings` | ビュー | 関数 `pg_show_all_settings()` で、メモリ上の設定値を取り出す（[S2.3](../../s2-運用管理/2-3-設定ファイル.md) を参照） |

`pg_roles` のように、**見せたい列だけを、見せたい形で出す**のもビューの使い道である。

#### 更新できるビュー

ビューは「読むだけ」とは限らない。公式ドキュメント（CREATE VIEW）には「単純なビューは自動的に更新可能で、通常のテーブルと同じように INSERT、UPDATE、DELETE、MERGE を使える」とある。ビューへの更新は、元のテーブルに反映される。

```text
CREATE VIEW expensive_fruits AS SELECT name, price FROM fruits WHERE price >= 1000;
UPDATE expensive_fruits SET price = 1500 WHERE name = 'メロン';

SELECT * FROM fruits;
  name  | price
--------+-------
 メロン |  1500      ← 元のテーブルが書き換わった
 りんご |   150
```

「単純なビュー」の条件は公式ドキュメントに列挙されている（`FROM` にテーブルかビューがちょうど1つだけある、`GROUP BY` や集約関数を使っていない、など）。条件を満たさないビューを更新しようとすると、`Views that do not select from a single table or view are not automatically updatable.` のようなエラーになる。そのようなビューでも、`INSTEAD OF` トリガーやルールを作れば更新できるようになる。

`pg_settings` は関数から値を取り出すビューなので自動では更新できないが、ルールで `UPDATE` を `set_config()`（`SET` の関数版）に書き換えているため、`UPDATE` できる（[S2.3](../../s2-運用管理/2-3-設定ファイル.md) の「pg_settings は UPDATE できる（SET と同じ）」を参照）。

結果を保存しておく「マテリアライズドビュー」（`CREATE MATERIALIZED VIEW`）も出題範囲にある。こちらは結果をディスクに保存するので、元のテーブルが変わっても、`REFRESH MATERIALIZED VIEW` するまで結果は変わらない（学習時に確かめる）。

## 確認問題

### 問1（選択）

PostgreSQL のオブジェクトの階層として、正しいものを1つ選べ。

- A. クラスタ ＞ スキーマ ＞ データベース ＞ テーブル
- B. クラスタ ＞ データベース ＞ スキーマ ＞ テーブル
- C. データベース ＞ クラスタ ＞ スキーマ ＞ テーブル
- D. スキーマ ＞ データベース ＞ クラスタ ＞ テーブル

### 問2（全て選択）

スキーマについて、正しいものをすべて選べ。

- A. 1つの接続から、別のデータベースのテーブルを「データベース名.スキーマ名.テーブル名」で参照できる
- B. 異なるスキーマには、同じ名前のテーブルを作れる
- C. スキーマを省略したテーブル名は、`search_path` の順に探される
- D. `search_path` の既定値は `"$user", public` である

### 問3（全て選択）

ビュー（`CREATE VIEW` で作ったもの）について、正しいものをすべて選べ。

- A. ビューはデータを持たず、参照するたびに定義した SELECT 文が実行される
- B. 元のテーブルに行を追加すると、ビューを作り直さなくても、ビューの結果に反映される
- C. ビューは、テーブルと同じく `SELECT ... FROM ビュー名` で読める
- D. `pg_settings` は、PostgreSQL の設定値を保存しているテーブルである

### 問4（選択）

テーブル fruits から作った単純なビュー `CREATE VIEW v AS SELECT name, price FROM fruits WHERE price >= 1000;` に、`UPDATE v SET price = 1500 WHERE name = 'メロン';` を実行した。結果として正しいものを1つ選べ。

- A. ビューは読み取り専用なので、エラーになる
- B. 元のテーブル fruits のメロンの price が 1500 になる
- C. ビューの中だけで 1500 になり、fruits は変わらない
- D. ビューが作り直される

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | B | データベースの中にスキーマがあり、スキーマの中にテーブルがある |
| 2 | B、C、D | 1つの接続は1つのデータベースにしか繋がらないので、A は `cross-database references are not implemented` というエラーになる |
| 3 | A、B、C | `pg_settings` はビューで、関数 `pg_show_all_settings()` でメモリ上の設定値を取り出している |
| 4 | B | 単純なビューは自動的に更新可能で、更新は元のテーブルに反映される。ビュー自体はデータを持たない |
