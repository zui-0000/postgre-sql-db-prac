## 学習メモ

### 識別子（名前）の大文字と小文字

公式ドキュメントでは、次のように定められている。

> キーワードと、引用符で囲まない識別子は、大文字と小文字を区別しない。

```sql
UPDATE MY_TABLE SET A = 5;
uPDaTE my_TabLE SeT a = 5;   -- 上と同じ意味になる
```

キーワードを大文字で書くのは読みやすくするための慣習で、決まりではない。

ただし、**引用符で囲まない識別子は小文字に変換される**。ダブルクォートで囲むと変換されず、大文字と小文字が区別される。

| 書き方 | PostgreSQL での扱い |
| --- | --- |
| `FOO`、`foo`、`"foo"` | **すべて同じ**（`foo`） |
| `"Foo"` | `"FOO"` とも、上の3つとも**別物** |

データベース名で確かめた結果（テーブル名や列名でも規則は同じ）:

```sql
CrEaTe DaTaBaSe MixedCase;     -- 引用符なし → mixedcase になる
CREATE DATABASE "MixedCase";   -- 引用符あり → MixedCase のまま
```

```text
  datname
------------
 MixedCase
 mixedcase     ← 別々のデータベースが2つできた
```

SQL 標準では「引用符で囲まない名前は**大文字**に変換する」と決まっていて、PostgreSQL は標準と逆になっている（公式ドキュメントにも、標準と互換性がないと明記されている）。

実務では、**名前は最初から小文字のスネークケース（`user_accounts` など）にする**のが安全。大文字を含む名前を引用符付きで作ると、そのあとは毎回引用符で囲んで書く必要がある。ORM がテーブル名を `"User"` のように引用符付きで作る場合も、生の SQL を書くときは `"User"` と書かなければならない。

### PRIMARY KEY は採番しない

**`PRIMARY KEY` は制約であって、値を自動で用意する機能はない。** `PRIMARY KEY` の意味は「重複してはいけない（`UNIQUE`）」と「空ではいけない（`NOT NULL`）」の2つだけである。db で確かめた（試したものはすべてロールバックした）。

```text
CREATE TABLE pk_only (id int PRIMARY KEY, name text);
INSERT INTO pk_only (name) VALUES ('aoki');          ← id を指定しない

ERROR:  null value in column "id" of relation "pk_only" violates not-null constraint
DETAIL:  Failing row contains (null, aoki).
```

id を書かないと、番号が自動で入るのではなく NULL になり、`NOT NULL` に違反した。同じ id を2回入れれば、主キーの重複でエラーになる（[S3.3](../3-3-トランザクション.md) の Ping-t の問題は、この勘違いを突いたもの）。

自動で採番したいときは、`PRIMARY KEY` とは別に指定する。

| 書き方 | 自動で採番するか | id を手で指定したとき |
| --- | --- | --- |
| `id int PRIMARY KEY` | しない | そのまま入る |
| `id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY` | する（1, 2, …） | エラーになる（`cannot insert a non-DEFAULT value into column "id"`）。`INSERT ... OVERRIDING SYSTEM VALUE VALUES (...)` と書けば入る |
| `id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | する | 入る。ただし、あとで番号がぶつかることがある |
| `id serial PRIMARY KEY` | する | 入る。ただし、あとで番号がぶつかることがある |

`GENERATED BY DEFAULT AS IDENTITY` と `serial` で、自動で 1 を入れたあと、手で 2 を入れ、また自動に任せると、どちらも `duplicate key value violates unique constraint ... Key (id)=(2) already exists` になった。番号を出す係（シーケンス）は、手で入れた 2 を知らないので、次に 2 を出してしまう。

`serial` の中身は、「`integer` 型の列 ＋ シーケンス ＋ 既定値 `nextval(...)`」である。db で確かめると、`serial` の列の既定値は `nextval('ser_id_seq'::regclass)` になっていて、`ser_id_seq` というシーケンスが作られていた（シーケンスは [04 DBオブジェクト](04-DBオブジェクト.md) で扱う）。

MySQL で言うと、`PRIMARY KEY` と `AUTO_INCREMENT` が別の指定であるのと同じで、`PRIMARY KEY` だけでは採番されない。

## ⚠️ 試験と最新版の違い

- **PG18**: 列の `NOT NULL` 制約が `pg_constraint` に格納されるようになり、制約に名前を付けられるようになった。

## 確認問題

### 問1（全て選択）

PostgreSQL で、同じ識別子として扱われるものをすべて選べ。

- A. `FOO`
- B. `foo`
- C. `"foo"`
- D. `"Foo"`

### 問2（選択）

`CREATE TABLE "UserAccount" (id int);` でテーブルを作成した。このテーブルを参照できる SELECT 文を1つ選べ。

- A. `SELECT * FROM UserAccount;`
- B. `SELECT * FROM useraccount;`
- C. `SELECT * FROM "UserAccount";`
- D. `SELECT * FROM USERACCOUNT;`

### 問3（全て選択）

`CREATE TABLE t (id int PRIMARY KEY, name text);` で作ったテーブルについて、正しいものをすべて選べ。

- A. `INSERT INTO t (name) VALUES ('a');` を実行すると、id に 1 が自動で入る
- B. `INSERT INTO t (name) VALUES ('a');` を実行すると、id が NULL になり、エラーになる
- C. 同じ id の行を2回 `INSERT` すると、エラーになる
- D. 自動で採番したいなら、`id int GENERATED ALWAYS AS IDENTITY PRIMARY KEY` のように指定する

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | A、B、C | 引用符で囲まない名前は小文字に変換されるので、`FOO` も `foo` も `"foo"` と同じ。`"Foo"` は大文字を含むので別物 |
| 2 | C | A、B、D はどれも小文字の `useraccount` として扱われ、そのテーブルは存在しない。実機でも、A と D のどちらのエラーも `relation "useraccount" does not exist` と小文字の名前で表示された。引用符付きで作った名前は、引用符付きで書く必要がある |
| 3 | B、C、D | `PRIMARY KEY` は `UNIQUE` と `NOT NULL` の制約で、採番はしない。自動採番は `GENERATED ... AS IDENTITY` か `serial` で指定する |
