# S3.3 トランザクションの概念

- 重要度: **1** / 50
- 公式の説明: 「トランザクション機能に関する知識を問う」
- 実習環境: db（psql を2つ開いて、同時に実行したときの挙動を確かめる）

## 出題範囲

### 主要な知識範囲

- トランザクションの構文
- トランザクション分離レベル(リードコミッティド、リピータブルリード、シリアライザブル)
- LOCK 文
- 行ロックとテーブルロック
- デッドロック

### 重要な用語、コマンド、パラメータなど

`BEGIN` / `COMMIT` / `ROLLBACK` / `SAVEPOINT` / `SET TRANSACTION` / `LOCK TABLE` / `SELECT FOR UPDATE / SHARE`

## 学習メモ

### トランザクション管理と同時実行制御

| | トランザクション管理 | 同時実行制御 |
| --- | --- | --- |
| 何を管理するか | 1つのまとまり（どこからどこまでが1単位か） | 複数のトランザクションが同時に動いたときの相互作用 |
| 守る ACID の性質 | 原子性（A）と永続性（D） | 独立性（I） |
| 代表的な仕組み | `COMMIT`、`ROLLBACK`、WAL | MVCC、ロック、トランザクション分離レベル |

**PostgreSQL は自動コミットなので、`BEGIN` を書かなくても1つの SQL 文が1つのトランザクションとして実行される。** つまり `BEGIN` を書くかどうかに関係なく、同時実行制御は常に働いている。トランザクションを開始する操作そのものが同時実行を制御しているわけではない。こちらが選べるのは制御の強さで、その手段がトランザクション分離レベルと明示的なロックである。

### トランザクションの構文

| SQL | 意味 | 同じ意味の書き方 |
| --- | --- | --- |
| `BEGIN` | トランザクションを始める | `START TRANSACTION`（SQL 標準） |
| `COMMIT` | 確定する | `END`（PostgreSQL の拡張） |
| `ROLLBACK` | 取り消す | `ABORT`（PostgreSQL の拡張） |
| `SAVEPOINT 名前` | トランザクションの途中に目印を付ける | — |
| `ROLLBACK TO SAVEPOINT 名前` | 目印のところまで取り消す（トランザクションは続く） | — |
| `RELEASE SAVEPOINT 名前` | 目印を消す（それまでの変更は残る） | — |
| `SET TRANSACTION ...` | そのトランザクションの分離レベルなどを決める（最初の SQL より前） | `BEGIN ISOLATION LEVEL ...` |

sandbox の使い捨てのクラスタで確かめた結果を、順に示す。

#### 1. 同じ意味の書き方

`START TRANSACTION` → `INSERT` → `END` では1行が確定し、`BEGIN` → `INSERT` → `ABORT` では取り消された。

トランザクションの終わらせ方は、**「確定する」か「取り消す」かの2択**である。`STOP TRANSACTION` のような「止めるだけ」のコマンドはなく、db で打つと `ERROR:  syntax error at or near "STOP"` になった。終わらせるときは、変更をどうするかを必ず決める必要があるためである。

| 始める | 終わらせる（確定） | 終わらせる（取り消し） |
| --- | --- | --- |
| `BEGIN` | `COMMIT` | `ROLLBACK` |
| `START TRANSACTION` | `END`（PostgreSQL の拡張） | `ABORT`（PostgreSQL の拡張） |

`END` は「終わる」という名前だが、**中身は `COMMIT`（確定）**である。「止める」に近い名前なので、取り消しと勘違いしないようにする。

`TRANSACTION` と `WORK` は、付けても付けなくてもよい。db で次の組み合わせがすべて通った。

```sql
BEGIN TRANSACTION;   COMMIT TRANSACTION;
BEGIN WORK;          COMMIT WORK;
BEGIN;               END TRANSACTION;
BEGIN;               ROLLBACK TRANSACTION;
BEGIN;               ABORT WORK;
```

ただし `START` だけは省略できず、`START TRANSACTION` と書く（`START` だけでは `syntax error at end of input` になった）。

#### 2. エラーが起きると、そのトランザクションは使えなくなる

```text
BEGIN;
INSERT INTO t VALUES (3, 'c');          ← 成功
INSERT INTO t VALUES (1, 'dup');        ← ERROR:  duplicate key value violates unique constraint "t_pkey"
INSERT INTO t VALUES (4, 'd');          ← ERROR:  current transaction is aborted, commands ignored until end of transaction block
COMMIT;                                 ← 表示は ROLLBACK
```

- トランザクションの中でエラーが起きると、**そのあとの SQL はすべて拒否される**（`current transaction is aborted`）。
- この状態で `COMMIT` を実行しても、実際には**ロールバック**される（表示も `ROLLBACK` になった）。エラーの前に成功した id=3 の行も残らなかった。

これは [S2.2](../s2-運用管理/2-2-標準付属ツール.md) の `psql -1` でエラーが起きたときの動きと同じである。

#### 3. SAVEPOINT で途中まで取り消す

```sql
BEGIN;
INSERT INTO t VALUES (10, 'x');
SAVEPOINT sp1;
INSERT INTO t VALUES (11, 'y');
ROLLBACK TO SAVEPOINT sp1;      -- 11 だけ取り消す
INSERT INTO t VALUES (12, 'z');
COMMIT;
```

残ったのは 10 と 12 だった。`ROLLBACK TO SAVEPOINT` は目印より後ろだけを取り消し、トランザクションは続く。

#### 4. SAVEPOINT でエラーから立ち直る

```sql
BEGIN;
INSERT INTO t VALUES (20, 'p');
SAVEPOINT before_risky;
INSERT INTO t VALUES (1, 'dup');          -- ERROR（主キーの重複）
ROLLBACK TO SAVEPOINT before_risky;       -- エラーの前に戻る
INSERT INTO t VALUES (21, 'q');           -- 実行できた
RELEASE SAVEPOINT before_risky;
COMMIT;
```

20 と 21 が残った。エラーが起きても、目印まで戻れば `current transaction is aborted` の状態から抜け出して、続きを実行できる。

TypeScript で例えると、`SAVEPOINT` は `try` の直前の位置、`ROLLBACK TO SAVEPOINT` は `catch` の中で「その位置まで戻る」処理に近い。トランザクション全体を捨てずに、失敗した部分だけやり直せる。

##### 同じ名前の SAVEPOINT は積み重なる

公式ドキュメント（SAVEPOINT）には「SQL 標準では、同じ名前の SAVEPOINT を作ると古いほうは自動で消える。PostgreSQL では古いほうも残るが、ROLLBACK や RELEASE で使われるのは新しいほうだけ。新しいほうを RELEASE すると、古いほうがまた使えるようになる」とある。

JavaScript の配列をスタック（`push` と `pop`）として使うのと同じように考える。

| SQL | 目印の扱い |
| --- | --- |
| `SAVEPOINT sp` | 目印を上に積む（`push`） |
| `RELEASE SAVEPOINT sp` | 一番上の `sp` を取り除く（`pop`）。変更は取り消さない |
| `ROLLBACK TO sp` | 一番上の `sp` の時点まで戻る。目印は残る |

Ping-t で出た問題（db で実行して確かめた）:

```sql
BEGIN;
CREATE TABLE sample(id INTEGER);
INSERT INTO sample VALUES(1);
INSERT INTO sample VALUES(2);
SAVEPOINT sp;
INSERT INTO sample VALUES(3);
SAVEPOINT sp;
INSERT INTO sample VALUES(4);
RELEASE SAVEPOINT sp;
ROLLBACK TO sp;
SELECT * FROM sample;
```

| SQL | テーブルの中身 | 積まれている目印 |
| --- | --- | --- |
| `BEGIN`、`CREATE TABLE` | （空） | なし |
| `INSERT 1`、`INSERT 2` | 1, 2 | なし |
| `SAVEPOINT sp` | 1, 2 | sp①（1, 2 の時点） |
| `INSERT 3` | 1, 2, 3 | sp① |
| `SAVEPOINT sp` | 1, 2, 3 | sp①、sp②（1, 2, 3 の時点） |
| `INSERT 4` | 1, 2, 3, 4 | sp①、sp② |
| `RELEASE SAVEPOINT sp` | 1, 2, 3, 4（取り消さない） | sp①（上の sp② だけ消える） |
| `ROLLBACK TO sp` | **1, 2**（sp① の時点に戻る） | sp① |

答えは **1 と 2**。`RELEASE` で sp② が消えたため、`ROLLBACK TO sp` は下に残っていた sp① まで戻った。

| 違い | 結果 |
| --- | --- |
| この問題（`RELEASE` してから `ROLLBACK TO`） | 1, 2 |
| `RELEASE` しないで `ROLLBACK TO` | 1, 2, 3（一番上の sp② まで戻るので、4 だけが消える） |
| `sp` が2つしかないのに `RELEASE` を3回 | 3回目で `ERROR:  savepoint "sp" does not exist` |

#### 5. 二重の BEGIN と、トランザクションの外の COMMIT

どちらもエラーではなく、**警告（WARNING）** になる。

```text
BEGIN; BEGIN;   → WARNING:  there is already a transaction in progress
COMMIT; COMMIT; → WARNING:  there is no transaction in progress
```

#### 6. DDL もロールバックできる

```sql
BEGIN;
CREATE TABLE ddl_test (id int);
INSERT INTO ddl_test VALUES (1);
DROP TABLE t;
ROLLBACK;
```

ロールバックのあと、`ddl_test` は存在せず、`DROP TABLE` した `t` は元に戻っていた。PostgreSQL では、`CREATE TABLE` や `DROP TABLE` のような DDL もトランザクションの中で取り消せる。MySQL では DDL を実行すると暗黙にコミットされるので、ここは大きく違う。

#### 7. トランザクションの中で実行できないもの

```text
VACUUM t;          → ERROR:  VACUUM cannot run inside a transaction block
CREATE DATABASE x; → ERROR:  CREATE DATABASE cannot run inside a transaction block
```

#### psql の AUTOCOMMIT

PostgreSQL は自動コミットなので、`BEGIN` を書かなければ SQL は1つずつ確定する。psql の変数 `AUTOCOMMIT` を `off` にすると、psql が自動で `BEGIN` を送るようになり、`COMMIT` するまで確定しない。db で `\set AUTOCOMMIT off` にして `INSERT` すると、別のセッションからは行が見えず、`ROLLBACK` で取り消せた。`AUTOCOMMIT` はサーバーの設定ではなく、psql の変数である（[S2.3](../s2-運用管理/2-3-設定ファイル.md) の `SET` と `\set` の違いと同じ）。

### 実機で確かめた同時実行の動き

`accounts(id=1, balance=1000)` を用意し、セッション A が残高を 1000 から 900 に更新して**コミットせずに保持**している間に、セッション B から同じ行を触った。

#### ① B の読み取りは待たされず、更新前の値が見えた

```text
 balance
---------
    1000      ← A の未コミットの変更（900）は見えない
Time: 3.910 ms   ← 待たされていない
```

#### ② B が同じ行を更新しようとすると待たされた

```sql
SET lock_timeout = '1500ms';
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
```

```text
ERROR:  canceling statement due to lock timeout
```

待ち時間の上限を 1.5 秒に設定したので、そこで打ち切られた。上限を設けなければ、A がコミットするまで待ち続ける。A がコミットしたあとの残高は 900 だった。

#### ③ 分離レベルはリードコミッテドだった

`SHOW transaction_isolation` は `read committed` を返した。これは PostgreSQL のデフォルトである。

ここからわかる PostgreSQL の同時実行制御の性質:

> **読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしない。ただし、同じ行への書き込み同士は待たされる。**

前者は MVCC（読み手には変更前のバージョンを見せる）の働き、後者は行ロックの働きである。

再現するときは、次のようにセッション A をバックグラウンドで動かしてから、セッション B を実行する。

```sh
# セッション A: 更新して 4 秒保持する
docker compose exec -T db psql -U postgres -d concur_demo \
  -c "BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 1; SELECT pg_sleep(4); COMMIT;" &

# セッション B: 読み取りと更新を試す
docker compose exec -T db psql -U postgres -d concur_demo \
  -c "SELECT balance FROM accounts WHERE id = 1" \
  -c "SET lock_timeout = '1500ms'" \
  -c "UPDATE accounts SET balance = balance - 500 WHERE id = 1"
```

### トランザクション分離レベル

SQL 標準は4つの分離レベルを定め、それぞれで起きてはいけない現象を決めている。

| 現象 | 内容 |
| --- | --- |
| ダーティリード | コミットされていない、ほかのトランザクションの変更を読んでしまう |
| 反復不能読み取り | 同じ行を読み直すと、ほかのトランザクションがコミットした変更で値が変わっている |
| ファントムリード | 同じ条件で検索し直すと、ほかのトランザクションがコミットした行が増減している |
| 直列化異常 | 複数のトランザクションをコミットした結果が、1つずつ順番に実行したどの順序の結果とも一致しない |

| 分離レベル | ダーティリード | 反復不能読み取り | ファントムリード | 直列化異常 |
| --- | --- | --- | --- | --- |
| リードアンコミッテド | 標準では起きうるが、**PostgreSQL では起きない** | 起きる | 起きる | 起きる |
| リードコミッテド（**PostgreSQL のデフォルト**） | 起きない | 起きる | 起きる | 起きる |
| リピータブルリード | 起きない | 起きない | 標準では起きうるが、**PostgreSQL では起きない** | 起きる |
| シリアライザブル | 起きない | 起きない | 起きない | 起きない |

#### ファジーリードとファントムリードの見分け方

**ファジーリード（fuzzy read）**は、上の表の「反復不能読み取り」の別名である。ファントムリードとの違いは、名前の英語の意味と、原因になる操作で覚える。

| 名前 | 英語の意味 | 起きること | 主な原因 |
| --- | --- | --- | --- |
| ファジーリード | fuzzy ＝ ぼやけた | **同じ行**を読み直すと、**値**が変わっている | ほかのトランザクションの `UPDATE` |
| ファントムリード | phantom ＝ 幽霊 | **同じ条件**で検索し直すと、**行**が増えている（減っている） | ほかのトランザクションの `INSERT` |

- ファジーリードは、知っている行の中身がぼやけて変わる。
- ファントムリードは、さっきまでいなかった行が幽霊のように現れる。
- `DELETE` はどちらも起こしうる（知っている1行が消えればファジーリード寄り、検索結果の件数が減ればファントムリード寄り）が、「**UPDATE → ファジー、INSERT → ファントム**」と覚えれば迷わない。

sandbox で、A が同じ2つの `SELECT` を2回実行し、その間に B が「id=1 の給料を 999 に `UPDATE`」と「営業部の人を1人 `INSERT`」をしてコミットした結果:

| A の分離レベル | id=1 の給料（1回目 → 2回目） | 営業部の人数（1回目 → 2回目） |
| --- | --- | --- |
| `read committed` | 300 → **999**（ファジーリード） | 2 → **3**（ファントムリード） |
| `repeatable read` | 300 → 300 | 2 → 2 |

フロントエンドの一覧画面で例えると、ファジーリードは「一覧にいる山田さんの行を開き直したら、給料が変わっていた」、ファントムリードは「同じ検索条件で一覧を読み込み直したら、知らない人が1行増えていた」にあたる。

| 現象 | 一言で | 防げる分離レベル（PostgreSQL） |
| --- | --- | --- |
| ダーティリード | コミット前の値が見える | すべて（PostgreSQL では起きない） |
| ファジーリード | 値が変わる（ぼやける） | リピータブルリード以上 |
| ファントムリード | 行が増える（幽霊） | リピータブルリード以上（SQL 標準ではシリアライザブルで初めて防げる） |

PostgreSQL に特有の注意点:

- **要求できる分離レベルは4つだが、内部で実装されているのは3つ**。リードアンコミッテドを指定しても、**リードコミッテドとして動く**。MVCC の構造上、こう対応づけるのがもっとも自然なため。
- **リピータブルリードではファントムリードも起きない**。SQL 標準より厳しい保証になっている（標準は「これ以上厳しくてもよい」としている）。
- デフォルトは**リードコミッテド**。上の実験で `SHOW transaction_isolation` が `read committed` を返したのは、このため。

#### default_transaction_isolation で動きを比べる

デフォルトの分離レベルは、設定 `default_transaction_isolation` で決まる（既定値は `read committed`。変え方は [S2.3](../s2-運用管理/2-3-設定ファイル.md) の「default_transaction_isolation」を参照）。

sandbox の使い捨てのクラスタで、セッション A が同じテーブルの行数を2回数え、その間にセッション B が1行を足してコミットした。A の分離レベルは `SET default_transaction_isolation` で変えた。

```text
A: BEGIN; SELECT count(*) FROM t;     ← 1回目
B: INSERT INTO t VALUES (1);           ← 自動コミット
A: SELECT count(*) FROM t; COMMIT;    ← 2回目
```

| A の分離レベル | 1回目 | 2回目 |
| --- | ---: | ---: |
| `read committed`（デフォルト） | 0 | **1**（B のコミットが見えた） |
| `repeatable read` | 0 | **0**（トランザクションの最初の状態のまま） |

- **リードコミッテド**は、SQL を実行するたびに、その時点でコミット済みのデータを見る。そのため、2回目で B の行が見えた（ファントムリード）。
- **リピータブルリード**は、トランザクションの最初の SQL の時点の状態を、トランザクションが終わるまで見続ける。そのため、B の行は見えなかった。PostgreSQL のリピータブルリードではファントムリードが起きない、という上の表の内容と一致する。

Node.js で例えると、リードコミッテドは読むたびに `fetch` し直して最新の値を取り、リピータブルリードは最初に取った値をキャッシュして使い続けるのに近い。

#### 同じ行を同時に更新したとき

sandbox で、セッション A が残高（1000）を読んだあと、セッション B が同じ行から 500 を引いてコミットし、そのあと A が 100 を引いた。

| A の分離レベル | A が読んだ値 | A の `UPDATE` | 最終の残高 |
| --- | ---: | --- | ---: |
| `read committed` | 1000 | 成功 | **400**（B の変更の上に A の変更が重なった） |
| `repeatable read` | 1000 | `ERROR:  could not serialize access due to concurrent update` | **500**（A は取り消された） |

- **リードコミッテド**では、`UPDATE` の時点で最新のコミット済みの行（500）を読み直して更新する。そのため最終は 400 になった。ただし、A が最初に読んだ 1000 は古い値になっている。アプリケーションが「1000 − 100 = 900」と計算して書き込むと、B の変更が消える（更新の消失）。防ぐには、読むときに `SELECT ... FOR UPDATE` で行ロックを取る。
- **リピータブルリード**では、トランザクションの開始後にほかのトランザクションが変更した行を更新しようとすると、エラーになる。アプリケーションは、トランザクションを最初からやり直す必要がある。

#### リードコミッテドのままで守る（在庫の例）

リードコミッテドはダーティリードを防ぐが、それだけでは足りない場面がある。「在庫を読む → 在庫があれば注文を入れて、在庫を減らす」という処理を、在庫1個の商品に対して A と B が同時に実行した（どれもリードコミッテド。sandbox で確認）。

| 書き方 | 結果 |
| --- | --- |
| ① `SELECT stock` で読み、アプリで計算した値を `UPDATE items SET stock = 0` のように書く | **注文が A と B の2件、在庫は 0**。1個しかないのに2個売れた |
| ② 読むときに `SELECT stock ... FOR UPDATE` で行ロックを取る | 注文は A だけ。B は A のコミットを待ってから在庫 0 を読み、注文しなかった |
| ③ `UPDATE items SET stock = stock - 1 WHERE id = 1 AND stock > 0` の1文で減らし、更新できたときだけ注文を入れる | 注文は A だけ |

①では、A も B もコミット済みの正しい値（在庫 1）を読んでいて、ダーティリードは起きていない。それでも、**2人とも「買える」と判断した**ことで、在庫が合わなくなった。

フロントエンド（React）で例えると、①は `setCount(count + 1)`（読んだ時点の古い値から計算して書く）、③は `setCount(c => c + 1)`（今の値をもとに更新させる）にあたる。連続して呼ばれると、①は更新が消える。

リードコミッテドのまま守る方法は、次のとおり。

1. **判断と更新を1つの SQL にまとめる**（③）。最も簡単で、待ちも少ない。
2. **読むときに行ロックを取る**（②）。ほかのトランザクションは待たされる。
3. **分離レベルを上げる**（リピータブルリードかシリアライザブル）。ぶつかるとエラーになるので、アプリケーションにやり直しの処理が必要になる。

> **リードコミッテドで十分なことが多い。ただし、「読んでから書く」処理は、1文の UPDATE か FOR UPDATE で守る。**

#### 表示と注文は別のトランザクション

分離レベルが決めるのは、**1つのトランザクションが続いている間**に、ほかのトランザクションの変更がどう見えるかである。EC サイトの画面の流れでは、表示と注文は別のトランザクションになる。

```text
10:00  商品ページを表示する   ← トランザクション1（在庫を読んで、すぐ終わる）
         （ユーザーが迷う）
10:05  注文ボタンを押す       ← トランザクション2（在庫を減らし、注文を入れる）
```

- トランザクション1の分離レベルを上げても、5分後の注文には関係しない。シリアライザブルにしても、ぶつかりが検出されるのはトランザクション2（注文のとき）である。
- 表示から注文までを1つのトランザクションにすることはできない。ユーザーが考えている間、ロックや接続を持ち続けることになる（それを切るのが [S2.3](../s2-運用管理/2-3-設定ファイル.md) の `idle_in_transaction_session_timeout`）。
- 分離レベルを上げるほど、ぶつかったときに**失敗する**ようになる。アクセスが集中する在庫では、エラーとやり直しが増える。そのため、1文の `UPDATE` や在庫を確保する仕組みで守ることが多い。

表示と注文では、目的も使う道具も違う。

| 場面 | 目的 | 使う道具 |
| --- | --- | --- |
| 表示するとき、カートに入れるとき、購入手続きの画面 | UX（在庫の目安を早めに伝える） | 在庫を確かめる API。読んだ時点の値なので、**少し古い可能性がある**のは前提 |
| カートに入れるとき（在庫を確保する場合） | 購入手続きの間、在庫を押さえておく | 確保用の行を作るなどのアプリケーションの設計。放置されたカートの確保を期限で外す仕組みも必要 |
| 注文するとき | **正しさ**（売りすぎない） | データベース（1文の `UPDATE`、`FOR UPDATE`、分離レベル、`CHECK (stock >= 0)` のような制約） |

途中で在庫を確かめても、注文までの間にほかの人が買う可能性は残る。そのため、**最後の判断は必ず注文のトランザクションで行い**、失敗したら画面で「在庫切れになりました」と伝える。

フロントエンドの入力チェックと同じ考え方である。画面側のバリデーションは UX のため、サーバー側のバリデーションは正しさのためで、画面側でチェックしても、サーバー側のチェックは省けない。React Query のように画面にキャッシュを出す楽観的 UI で、最後の判断をサーバーの mutation に任せるのとも同じである。

#### シリアライザブルが防ぐもの（書き込みスキュー）

2つの口座（どちらも 1000）について、「合計が残っていれば引き出してよい」という処理を、A と B が同時に実行した。

```text
A: BEGIN ISOLATION LEVEL SERIALIZABLE; SELECT sum(balance) FROM acc;   → 2000
B: BEGIN ISOLATION LEVEL SERIALIZABLE; SELECT sum(balance) FROM acc;   → 2000
A: UPDATE acc SET balance = balance - 1500 WHERE id = 1; COMMIT;
B: UPDATE acc SET balance = balance - 1500 WHERE id = 2; COMMIT;
```

B は次のエラーになり、最終は `1=-500, 2=1000` だった。

```text
ERROR:  could not serialize access due to read/write dependencies among transactions
DETAIL:  Reason code: Canceled on identification as a pivot, during write.
HINT:  The transaction might succeed if retried.
```

A と B は別の行を更新しているので、行ロックはぶつからない。リピータブルリード以下なら両方とも成功し、合計は −1000 になってしまう（どちらを先に実行しても起きない結果なので、直列化異常）。シリアライザブルはこれを検出して、片方を失敗させる。HINT のとおり、失敗したトランザクションはやり直せばよい。

### ロックとデッドロック

ロックには、テーブル単位（テーブルロック）と行単位（行ロック）がある。どちらも**トランザクションが終わるまで持ち続け、`COMMIT` か `ROLLBACK` で外れる**。公式ドキュメント（Explicit Locking）には「UNLOCK TABLE というコマンドはない。ロックは必ずトランザクションの終わりに外れる」とある。

明示的に書かなくても、SQL は自動でロックを取る。「実機で確かめた同時実行の動き」で B の `UPDATE` が待たされたのは、`UPDATE` が自動で行ロックを取るためである。

#### テーブルロック（8種類）

公式ドキュメントの説明をまとめたもの（上ほど弱く、下ほど強い）:

| モード | 自動で取る主な SQL | ぶつかる相手 |
| --- | --- | --- |
| `ACCESS SHARE` | `SELECT` | `ACCESS EXCLUSIVE` だけ |
| `ROW SHARE` | `SELECT ... FOR UPDATE` / `FOR SHARE` | `EXCLUSIVE`、`ACCESS EXCLUSIVE` |
| `ROW EXCLUSIVE` | `INSERT`、`UPDATE`、`DELETE` | `SHARE` から下すべて |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM`（FULL なし）、`ANALYZE`、`CREATE INDEX CONCURRENTLY` | 自分自身と、それより下すべて |
| `SHARE` | `CREATE INDEX`（CONCURRENTLY なし） | `ROW EXCLUSIVE`、`SHARE UPDATE EXCLUSIVE`、`SHARE ROW EXCLUSIVE`、`EXCLUSIVE`、`ACCESS EXCLUSIVE`（`SHARE` 同士はぶつからない） |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`、一部の `ALTER TABLE` | `ROW EXCLUSIVE` から下すべて |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` | `ACCESS SHARE` 以外すべて（読むことだけできる） |
| `ACCESS EXCLUSIVE` | `DROP TABLE`、`TRUNCATE`、`VACUUM FULL`、多くの `ALTER TABLE`、モードを省略した `LOCK TABLE` | **すべて**（`SELECT` も待たされる） |

まず両端を覚える。**`SELECT` の `ACCESS SHARE` は、`ACCESS EXCLUSIVE` とだけぶつかる**。**`ACCESS EXCLUSIVE` は、すべてとぶつかる**。そのため、`ALTER TABLE` や `VACUUM FULL` の実行中は、そのテーブルを `SELECT` することもできない。

トランザクションの中で SQL を実行し、`pg_locks` ビューで取ったロックを見た結果:

| SQL | 取ったテーブルロック |
| --- | --- |
| `SELECT * FROM acc` | `AccessShareLock` |
| `SELECT * FROM acc FOR UPDATE` | `RowShareLock` |
| `UPDATE acc SET ...` | `RowExclusiveLock` |
| `CREATE INDEX ON acc (balance)` | `ShareLock` |
| `ALTER TABLE acc ADD COLUMN memo text` | `AccessExclusiveLock` |
| `TRUNCATE acc` | `AccessExclusiveLock`（ほかに `ShareLock` も見えた） |

#### LOCK TABLE

```sql
LOCK [ TABLE ] テーブル名 [ IN ロックモード MODE ] [ NOWAIT ];
```

- **モードを省略すると `ACCESS EXCLUSIVE`**（最も強いモード）になる。実機でも `AccessExclusiveLock` だった。
- **トランザクションの外では使えない**。`ERROR:  LOCK TABLE can only be used in transaction blocks` になった。公式ドキュメントには「トランザクションの外で使っても、その文が終わるとすぐロックが外れて意味がないので、エラーにしている」とある。
- **`NOWAIT`** を付けると、ロックが取れないときに待たずにエラーになる（`ERROR:  could not obtain lock on relation "acc"`）。
- 外すコマンドはない。`COMMIT` か `ROLLBACK` で外れる。

A が `LOCK TABLE` している間に、B が同じテーブルを触った結果:

| A が取ったモード | B の `SELECT` | B の `UPDATE` |
| --- | --- | --- |
| `ACCESS EXCLUSIVE` | 待たされた（`lock timeout`） | 待たされた |
| `SHARE` | すぐ結果が返った | 待たされた |
| `EXCLUSIVE` | すぐ結果が返った | 待たされた |

`SHARE` や `EXCLUSIVE` は「読むのはいいが、変更はさせない」ためのモードである。

#### 行ロック（4種類）

`SELECT ... FOR UPDATE` のように、`SELECT` の最後に付けて取る。

| 行ロック | 使いどころ | ぶつかる相手 |
| --- | --- | --- |
| `FOR KEY SHARE` | 外部キーの参照元の確認など | `FOR UPDATE` だけ |
| `FOR SHARE` | 読んだ行を、ほかの人に変えさせたくない | `FOR NO KEY UPDATE`、`FOR UPDATE` |
| `FOR NO KEY UPDATE` | キー以外の列を更新する（キーを変えない `UPDATE` が自動で取る） | `FOR SHARE`、`FOR NO KEY UPDATE`、`FOR UPDATE` |
| `FOR UPDATE` | これから更新する行を押さえる | すべて |

A が `SELECT id FROM acc WHERE id = 1 FOR UPDATE` で id=1 をロックしている間に、B が触った結果:

| B の操作 | 結果 |
| --- | --- |
| 普通の `SELECT`（id=1） | **すぐ結果が返った**（普通の読み取りは行ロックで待たされない） |
| id=2 を `UPDATE` | 成功（ロックされているのは id=1 だけ） |
| id=1 を `UPDATE` | 待たされた（`lock timeout`） |
| id=1 を `FOR SHARE` | 待たされた |
| id=1 を `FOR UPDATE NOWAIT` | `ERROR:  could not obtain lock on row in relation "acc"` |
| 全行を `FOR UPDATE SKIP LOCKED` | id=2 だけが返った（ロックされている行を飛ばす） |

A が `FOR SHARE` でロックしている場合は、B の `FOR SHARE` は成功し、B の `UPDATE` は待たされた。`FOR SHARE` 同士はぶつからない。

`SKIP LOCKED` は、複数のワーカーが1つのテーブルから仕事を取り出すキューのような使い方に向いている。Node.js で言えば、ジョブキュー（BullMQ など）の「誰かが処理中のジョブは飛ばして、次を取る」動きにあたる。

##### SELECT ... FOR UPDATE は「取得しつつロックする」

`SELECT ... FOR UPDATE` は、行を**取得したうえで、取得した行にロックをかける**。公式ドキュメント（SELECT）には「FOR UPDATE は、SELECT で取り出した行を、更新するときと同じようにロックする」とある。普通の `SELECT` と同じく結果の行が返ってくる。

sandbox で、`sales` に3行（id 1〜3）を入れ、A がコミットせずにいる間に B が触った結果:

| A の SQL | B の操作 | 結果 |
| --- | --- | --- |
| `SELECT * FROM sales FOR UPDATE` | id=1 を `UPDATE` | 待たされた |
| 〃 | id=3 を `UPDATE` | 待たされた（`WHERE` がないので全行がロックされる） |
| 〃 | 新しい行（id=4）を `INSERT` | 成功（ロックされるのは、そのときに取得した行だけ） |
| 〃 | 普通の `SELECT` | 成功（読むだけなら待たされない） |
| `SELECT * FROM sales WHERE id = 1 FOR UPDATE` | id=2 を `UPDATE` | 成功（ロックされるのは id=1 だけ） |
| `SELECT * FROM sales ORDER BY id LIMIT 1 FOR UPDATE` | id=2 を `UPDATE` | 成功（返した1行だけがロックされる） |

`LIMIT` については、公式ドキュメントにも「LIMIT を使うと、必要な行数を返した時点でロックも止まる（ただし OFFSET で飛ばした行はロックされる）」とある。

**`BEGIN` を書かないと意味がない。** 自動コミットのまま `SELECT * FROM sales FOR UPDATE;` を実行すると、その1文が終わった時点でコミットされ、ロックも外れる。実機でも、直後に B が id=1 を `UPDATE` すると、すぐ成功した。行ロックはトランザクションが終わるまで持ち続けるものなので、`BEGIN` → `SELECT ... FOR UPDATE` → 更新 → `COMMIT` の形で使う。

図書館で例えると、普通の `SELECT` は本棚の前での立ち読み、`FOR UPDATE` は読んだうえでカウンターで貸し出し手続きをすることにあたる。借りている間（トランザクションの間）は、ほかの人はその本に書き込めないが、立ち読みはできる。新しく入った本（あとから `INSERT` された行）は、借りたことにならない。

#### デッドロック

**デッドロック**は、2つのトランザクションが互いに相手の持つロックを待って、どちらも進めなくなる状態。**PostgreSQL は自動的に検出し、関係するトランザクションの1つをエラーで中断して解決する**（残りは処理を続けられる）。

sandbox で、A は id=1 → id=2、B は id=2 → id=1 の順に更新した。

```text
A: BEGIN; UPDATE ... WHERE id = 1;
B: BEGIN; UPDATE ... WHERE id = 2;
A: UPDATE ... WHERE id = 2;     ← B を待つ
B: UPDATE ... WHERE id = 1;     ← A を待つ（互いに待ち合う）
```

A が次のエラーで中断され、B は最後まで進んでコミットできた（最終は `1=999, 2=999`。B の2つの更新だけが残った）。

```text
ERROR:  deadlock detected
DETAIL:  Process 3715 waits for ShareLock on transaction 794; blocked by process 3717.
Process 3717 waits for ShareLock on transaction 793; blocked by process 3715.
HINT:  See server log for query details.
```

- ロックを待ち始めてから、`deadlock_timeout`（既定 `1s`）がたつとデッドロックかどうかを調べる。公式ドキュメントには「デッドロックの検査は重いので、ロックを待つたびには行わない」とある。
- 公式ドキュメントでは、「複数のものにロックをかけるときは、すべてのアプリケーションで同じ順番にする」のが最善の防ぎ方とされている。上の例なら、A も B も id の小さい順に更新すれば起きない。
- どちらのトランザクションが中断されるかについて、公式ドキュメントには「予測しにくく、当てにしてはいけない」とある。

##### deadlock_timeout は変えられる

| 項目 | 内容 |
| --- | --- |
| 既定値 | `1s` |
| context | `superuser`（一般のロールが `SET` すると `permission denied to set parameter "deadlock_timeout"`） |
| 変え方 | `postgresql.conf` に書いてリロード、`ALTER SYSTEM`、スーパーユーザーの `SET` |

sandbox で、同じデッドロックを値を変えて起こした結果:

| `deadlock_timeout` | デッドロックが解消されるまで |
| --- | ---: |
| `1s` | 約 1.3 秒 |
| `3s` | 約 3.3 秒 |

`deadlock_timeout` は「ロックを待ち始めてから、デッドロックかどうかを調べ始めるまでの時間」である。デッドロックが起きていれば、この時間のあとに見つかり、片方が中断される。

小さくすれば早く解消するが、それがよいとは限らない。公式ドキュメントには次のようにある。

> デッドロックの検査は比較的重いので、ロックを待つたびには行わない。本番のアプリケーションではデッドロックはめったに起きないと楽観的に考え、しばらく待ってから検査する。値を大きくすると無駄な検査が減るが、本当のデッドロックの報告は遅くなる。既定の 1 秒は、実用上の最小値くらいだろう。負荷の高いサーバーでは大きくしてもよい。理想は、ふつうのトランザクションにかかる時間より長くすること。

ロック待ちのほとんどは、デッドロックではなく、相手が終わるのを待っているだけである。そのたびに重い検査をするのは無駄なので、少し待ってから検査する。

| 値 | よいところ | 困るところ |
| --- | --- | --- |
| 小さくする | デッドロックが早く解消する | ただの待ちでも、重い検査が何度も走る |
| 大きくする | 無駄な検査が減る | デッドロックが起きたとき、長く待たされる |

Node.js で例えると、「応答がないのでタイムアウトにする」までの時間の決め方と同じで、短すぎると、少し遅いだけの正常な処理まで疑ってしまう。

`log_lock_waits` を `on` にすると、`deadlock_timeout` より長くロックを待ったときにログに記録される（[S2.3](../s2-運用管理/2-3-設定ファイル.md) のログの設定）。公式ドキュメントには、ロック待ちの原因を調べるときは `deadlock_timeout` を普段より短くしてもよい、ともある。

##### 実際のプロダクトで起きやすいパターン

デッドロックは、実際のプロダクトでも起きる。設計がよければ「たまに起きる」程度で、頻繁に起きるなら設計を見直すサインである。sandbox で、よくある2つのパターンを再現した。

**パターン1：更新する順番がばらばら**（振り込みの例。A→B の送金と B→A の送金が同時に起きる）

| 書き方 | 結果 |
| --- | --- |
| A→B の送金は「id 1 → 2」、B→A の送金は「id 2 → 1」の順に更新する | `ERROR:  deadlock detected` |
| どちらも、先に `SELECT id FROM acc WHERE id IN (1, 2) ORDER BY id FOR UPDATE` で id の小さい順にロックしてから更新する | エラーなし |

**パターン2：`FOR SHARE` で読んでから、同じ行を `UPDATE`**（2人が同時に同じ行に対して行う）

| 書き方 | 結果 |
| --- | --- |
| `SELECT ... FOR SHARE` で読む → 同じ行を `UPDATE` | `ERROR:  deadlock detected` |
| `SELECT ... FOR UPDATE` で読む → 同じ行を `UPDATE` | エラーなし（2人目は1人目を待つだけ） |

`FOR SHARE` 同士はぶつからないので、2人とも共有ロックを取れてしまう。そのあと2人とも `UPDATE` しようとすると、互いに「相手の共有ロックが外れるのを待つ」状態になる。**あとで更新するつもりなら、最初から `FOR UPDATE` で読む**。

ほかに、`WHERE id IN (...)` でまとめて更新するバッチ処理が同時に走るときや、外部キーでつながった親子のテーブルを同時に更新するときにも起きやすい。

##### 起きても、手作業の後始末は要らない

- PostgreSQL は、`deadlock_timeout`（1秒）ほどでデッドロックを検出し、**片方のトランザクションだけを中断**する。もう片方は最後まで進んでコミットできる。
- 中断されたトランザクションは**すべてロールバックされる**（原子性）。上の振り込みの例でも、中断された側の変更は1つも残らず、「片方の口座からだけ引かれた」ような中途半端な状態にはならなかった（最終は `1=999, 2=999` で、コミットできた側の2つの更新だけが残った）。そのため、データを手で直す必要はない。
- 中断された側のアプリケーションには、エラーコード（SQLSTATE）**`40P01`（deadlock_detected）**が返る。アプリケーションは、このエラーを受け取ったらトランザクションを最初からやり直す。リピータブルリードやシリアライザブルの `could not serialize access` のエラーコード **`40001`（serialization_failure）**も、同じくやり直せば成功する可能性がある種類のエラーである（公式ドキュメントの付録「PostgreSQL Error Codes」）。

```ts
// node-postgres でのやり直しのイメージ
for (let i = 0; i < 3; i++) {
  try {
    await transfer(client, from, to, amount);   // BEGIN 〜 COMMIT
    break;
  } catch (e) {
    if (e.code === '40P01' || e.code === '40001') continue;   // デッドロック、直列化の失敗ならやり直す
    throw e;
  }
}
```

やり直しを組み込んでおけば、利用者から見ると「少し待たされた」だけで済む。本当に困るのは、検出の仕組みがなく、両方が永遠に待ち続けることで、PostgreSQL はそれを自動で防いでいる。

`pg_stat_database` ビューの `deadlocks` 列に、データベースごとのデッドロックの回数がたまる。実験でも、パターン1とパターン2の失敗のたびに 0 → 1 → 2 と増えた。運用では、この回数が急に増えていないかを監視する。

### 試験の観点

- **`BEGIN` と `START TRANSACTION`、`COMMIT` と `END`、`ROLLBACK` と `ABORT` は同じ意味**。`STOP TRANSACTION` はない（終わらせ方は確定か取り消しの2択）。`END` は取り消しではなく確定。`TRANSACTION` と `WORK` は省略できる。
- **トランザクションの中でエラーが起きると、そのあとの SQL は `current transaction is aborted` で拒否され、`COMMIT` してもロールバックされる**。
- **`SAVEPOINT` で目印を付けると、`ROLLBACK TO SAVEPOINT` でそこまでだけ取り消せる**（トランザクションは続く）。エラーのあとでも、目印まで戻れば続きを実行できる。`RELEASE SAVEPOINT` は目印を消すだけで、変更は取り消さない。同じ名前の SAVEPOINT は積み重なり、`RELEASE` も `ROLLBACK TO` も一番上（最も新しい）ものを相手にする。
- **PostgreSQL では DDL（`CREATE TABLE`、`DROP TABLE` など）もロールバックできる**。`VACUUM` と `CREATE DATABASE` はトランザクションの中では実行できない。
- 二重の `BEGIN` や、トランザクションの外の `COMMIT` は、エラーではなく警告（WARNING）。
- **ファジーリード（反復不能読み取り）は、同じ行の値が変わる（主に `UPDATE` が原因）。ファントムリードは、同じ条件の検索結果の行が増減する（主に `INSERT` が原因）**。PostgreSQL では、どちらもリピータブルリード以上で起きない。
- **デフォルトの分離レベルは `read committed`**。`read uncommitted` を指定しても `read committed` として動く。リピータブルリードやシリアライザブルでは、同時の更新がぶつかると `could not serialize access` のエラーになり、やり直しが必要。
- **ロックはトランザクションが終わるまで持ち続け、`COMMIT` か `ROLLBACK` で外れる**。`UNLOCK TABLE` というコマンドはない。
- **`LOCK TABLE` はトランザクションの中でしか使えず、モードを省略すると `ACCESS EXCLUSIVE`**。`NOWAIT` を付けると、待たずにエラーになる。
- `SELECT` は `ACCESS SHARE` を取り、`ACCESS EXCLUSIVE` とだけぶつかる。`ACCESS EXCLUSIVE`（`DROP TABLE`、`TRUNCATE`、`VACUUM FULL`、多くの `ALTER TABLE`）はすべてとぶつかる。
- **`SELECT ... FOR UPDATE` は、行を取得しつつ、取得した行をロックする**。`BEGIN` を書かないと、文が終わった時点でロックが外れる。あとから `INSERT` された行はロックされない。
- **行ロックは `SELECT ... FOR UPDATE` / `FOR SHARE` で取る**。普通の `SELECT` は行ロックで待たされない。`NOWAIT` で待たずにエラー、`SKIP LOCKED` でロック中の行を飛ばす。
- **デッドロックは PostgreSQL が自動で検出し、1つのトランザクションを `deadlock detected` で中断する**。検出までの時間は `deadlock_timeout`（既定 1秒。context は `superuser`）。小さくすると早く解消するが、ロックを待つたびに重い検査が走る。防ぐには、ロックを取る順番をそろえる。中断されたトランザクションはロールバックされるので、データを手で直す必要はない。アプリケーションはエラーコード `40P01` を受け取ったらやり直す。あとで更新する行は `FOR SHARE` ではなく `FOR UPDATE` で読む。

## ⚠️ 試験と最新版の違い

- **PG15**: `MERGE` 文が追加された。公式ドキュメントのロックの説明では、`MERGE` も `UPDATE` などと同じく `ROW EXCLUSIVE` を取る。試験の基準（PG 12〜14）には `MERGE` はない。
- **PG17**: 設定 `transaction_timeout`（トランザクション全体の時間の上限）が追加された（[S2.3](../s2-運用管理/2-3-設定ファイル.md) の ⚠️ を参照）。試験の基準で使えるのは、`statement_timeout` と `idle_in_transaction_session_timeout`。

- B. ファジーリード
- C. ファントムリード
- D. デッドロック

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | A | リピータブルリードは、トランザクションの最初の SQL の時点の状態を見続ける |
| 2 | A、C | B: PostgreSQL の `read uncommitted` は `read committed` と同じように動くので、ダーティリードは起きない。D: `SET TRANSACTION ISOLATION LEVEL must be called before any query` になる |
| 3 | D | エラーのあとは `current transaction is aborted` になり、`COMMIT` してもロールバックされる。エラーの前の 1 も残らない |
| 4 | B | `ROLLBACK TO SAVEPOINT` は目印より後ろ（11）だけを取り消し、トランザクションは続く |
| 5 | A、B、C | PostgreSQL は DDL もロールバックできる。`VACUUM` は `cannot run inside a transaction block` になる |
| 6 | `ACCESS EXCLUSIVE` | 最も強いモードで、`SELECT` ともぶつかる |
| 7 | A、C、D | `UNLOCK TABLE` というコマンドはない。ロックはトランザクションの終わりに外れる |
| 8 | A | 普通の `SELECT` は行ロックで待たされない（MVCC により、コミット済みの値を読む） |
| 9 | B | 検出までの時間は `deadlock_timeout`（既定 1秒）。残りのトランザクションは続けられる |
| 10 | C | リードコミッテドなら A（最新の行の上に重ねて成功）になる |
| 11 | B、C | 普通の SELECT と同じく行が返り、そのうえでロックされる（A は誤り）。ロックされるのは取得した行だけなので、新しい行の `INSERT` はできる（D は誤り） |
| 12 | B、C、D | `STOP TRANSACTION` はない（構文エラー）。`END` と `COMMIT WORK` は確定、`ABORT` は取り消し |
| 13 | A、C、D | 中断されるのは片方だけで、もう片方は最後まで進める（B は誤り） |
| 14 | B | 同じ名前の SAVEPOINT は積み重なり、`ROLLBACK TO` は一番上（2つ目）の `sp` まで戻る。3 だけが消える。`RELEASE SAVEPOINT sp` を先に実行していれば、1つ目まで戻って 1 だけになる |
| 15 | A、B | C: context が `superuser` なので、一般のロールは `permission denied` になる。D: 小さくすると、ロックを待つたびに重い検査が走るので、負荷はむしろ上がりうる |
| 16 | C | 同じ条件の検索で行が増えたので、ファントムリード。同じ行の値が `UPDATE` で変わった場合なら、ファジーリード |
