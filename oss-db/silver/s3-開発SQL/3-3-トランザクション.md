## 学習メモ

### トランザクション管理と同時実行制御

| | トランザクション管理 | 同時実行制御 |
| --- | --- | --- |
| 何を管理するか | 1つのまとまり（どこからどこまでが1単位か） | 複数のトランザクションが同時に動いたときの相互作用 |
| 守る ACID の性質 | 原子性（A）と永続性（D） | 独立性（I） |
| 代表的な仕組み | `COMMIT`、`ROLLBACK`、WAL | MVCC、ロック、トランザクション分離レベル |

**PostgreSQL は自動コミットなので、`BEGIN` を書かなくても1つの SQL 文が1つのトランザクションとして実行される。** つまり `BEGIN` を書くかどうかに関係なく、同時実行制御は常に働いている。トランザクションを開始する操作そのものが同時実行を制御しているわけではない。こちらが選べるのは制御の強さで、その手段がトランザクション分離レベルと明示的なロックである。

### 実機で確かめた同時実行の動き

`accounts(id=1, balance=1000)` を用意し、セッション A が残高を 1000 から 900 に更新して**コミットせずに保持**している間に、セッション B から同じ行を触った。

#### ① B の読み取りは待たされず、更新前の値が見えた

```text
 balance
---------
    1000      ← A の未コミットの変更（900）は見えない
Time: 3.910 ms   ← 待たされていない
```

#### ② B が同じ行を更新しようとすると待たされた

```sql
SET lock_timeout = '1500ms';
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
```

```text
ERROR:  canceling statement due to lock timeout
```

待ち時間の上限を 1.5 秒に設定したので、そこで打ち切られた。上限を設けなければ、A がコミットするまで待ち続ける。A がコミットしたあとの残高は 900 だった。

#### ③ 分離レベルはリードコミッテドだった

`SHOW transaction_isolation` は `read committed` を返した。これは PostgreSQL のデフォルトである。

ここからわかる PostgreSQL の同時実行制御の性質:

> **読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしない。ただし、同じ行への書き込み同士は待たされる。**

前者は MVCC（読み手には変更前のバージョンを見せる）の働き、後者は行ロックの働きである。

### トランザクション分離レベル

SQL 標準は4つの分離レベルを定め、それぞれで起きてはいけない現象を決めている。

| 現象 | 内容 |
| --- | --- |
| ダーティリード | コミットされていない、ほかのトランザクションの変更を読んでしまう |
| 反復不能読み取り | 同じ行を読み直すと、ほかのトランザクションがコミットした変更で値が変わっている |
| ファントムリード | 同じ条件で検索し直すと、ほかのトランザクションがコミットした行が増減している |
| 直列化異常 | 複数のトランザクションをコミットした結果が、1つずつ順番に実行したどの順序の結果とも一致しない |

| 分離レベル | ダーティリード | 反復不能読み取り | ファントムリード | 直列化異常 |
| --- | --- | --- | --- | --- |
| リードアンコミッテド | 標準では起きうるが、**PostgreSQL では起きない** | 起きる | 起きる | 起きる |
| リードコミッテド（**PostgreSQL のデフォルト**） | 起きない | 起きる | 起きる | 起きる |
| リピータブルリード | 起きない | 起きない | 標準では起きうるが、**PostgreSQL では起きない** | 起きる |
| シリアライザブル | 起きない | 起きない | 起きない | 起きない |

PostgreSQL に特有の注意点:

- **要求できる分離レベルは4つだが、内部で実装されているのは3つ**。リードアンコミッテドを指定しても、**リードコミッテドとして動く**。MVCC の構造上、こう対応づけるのがもっとも自然なため。
- **リピータブルリードではファントムリードも起きない**。SQL 標準より厳しい保証になっている（標準は「これ以上厳しくてもよい」としている）。
- デフォルトは**リードコミッテド**。上の実験で `SHOW transaction_isolation` が `read committed` を返したのは、このため。

#### default_transaction_isolation で動きを比べる

デフォルトの分離レベルは、設定 `default_transaction_isolation` で決まる（既定値は `read committed`。変え方は [S2.3](../s2-運用管理/2-3-設定ファイル.md) の「default_transaction_isolation」を参照）。

sandbox の使い捨てのクラスタで、セッション A が同じテーブルの行数を2回数え、その間にセッション B が1行を足してコミットした。A の分離レベルは `SET default_transaction_isolation` で変えた。

```text
A: BEGIN; SELECT count(*) FROM t;     ← 1回目
B: INSERT INTO t VALUES (1);           ← 自動コミット
A: SELECT count(*) FROM t; COMMIT;    ← 2回目
```

| A の分離レベル | 1回目 | 2回目 |
| --- | ---: | ---: |
| `read committed`（デフォルト） | 0 | **1**（B のコミットが見えた） |
| `repeatable read` | 0 | **0**（トランザクションの最初の状態のまま） |

- **リードコミッテド**は、SQL を実行するたびに、その時点でコミット済みのデータを見る。そのため、2回目で B の行が見えた（ファントムリード）。
- **リピータブルリード**は、トランザクションの最初の SQL の時点の状態を、トランザクションが終わるまで見続ける。そのため、B の行は見えなかった。PostgreSQL のリピータブルリードではファントムリードが起きない、という上の表の内容と一致する。

Node.js で例えると、リードコミッテドは読むたびに `fetch` し直して最新の値を取り、リピータブルリードは最初に取った値をキャッシュして使い続けるのに近い。

### ロックとデッドロック

ロックには、テーブル単位のものと行単位のものがある。

- **テーブルレベルのロック**は8種類ある（`ACCESS SHARE`、`ROW SHARE`、`ROW EXCLUSIVE`、`SHARE UPDATE EXCLUSIVE`、`SHARE`、`SHARE ROW EXCLUSIVE`、`EXCLUSIVE`、`ACCESS EXCLUSIVE`）。`LOCK TABLE` で明示的に取得する。`ACCESS EXCLUSIVE` はすべてのモードと衝突し、そのテーブルを独占する。
- **行レベルのロック**は4種類（`FOR UPDATE`、`FOR NO KEY UPDATE`、`FOR SHARE`、`FOR KEY SHARE`）。`SELECT ... FOR UPDATE` のように指定して取得する。
- 上の実験で B の `UPDATE` が待たされたのは、`UPDATE` が自動的に行レベルのロックを取るため。明示的に `LOCK TABLE` や `SELECT ... FOR UPDATE` を書かなくても、ロックは取られている。

**デッドロック**は、2つのトランザクションが互いに相手の持つロックを待って、どちらも進めなくなる状態。**PostgreSQL は自動的に検出し、関係するトランザクションの1つを中断して解決する**（残りは処理を続けられる）。

再現するときは、次のようにセッション A をバックグラウンドで動かしてから、セッション B を実行する。

```sh
# セッション A: 更新して 4 秒保持する
docker compose exec -T db psql -U postgres -d concur_demo \
  -c "BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 1; SELECT pg_sleep(4); COMMIT;" &

# セッション B: 読み取りと更新を試す
docker compose exec -T db psql -U postgres -d concur_demo \
  -c "SELECT balance FROM accounts WHERE id = 1" \
  -c "SET lock_timeout = '1500ms'" \
  -c "UPDATE accounts SET balance = balance - 500 WHERE id = 1"
```

## 確認問題

### 問1（選択）

セッション A が `repeatable read` でトランザクションを始め、テーブル t の行数を数えた（0 行）。そのあと、セッション B が t に1行を追加してコミットした。A が同じトランザクションの中でもう一度行数を数えたときの結果を1つ選べ。

- A. 0 行
- B. 1 行
- C. エラーになる
- D. B のトランザクションが終わるまで待たされる

### 問2（全て選択）

PostgreSQL のトランザクション分離レベルについて、正しいものをすべて選べ。

- A. デフォルトの分離レベルは `read committed` である
- B. `read uncommitted` を指定すると、コミットされていない変更も読める
- C. デフォルトの分離レベルは、設定 `default_transaction_isolation` で変えられる
- D. 分離レベルは、トランザクションの途中（SQL を実行したあと）でも `SET TRANSACTION` で変えられる

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | A | リピータブルリードは、トランザクションの最初の SQL の時点の状態を見続ける |
| 2 | A、C | B: PostgreSQL の `read uncommitted` は `read committed` と同じように動くので、ダーティリードは起きない。D: `SET TRANSACTION ISOLATION LEVEL must be called before any query` になる |
