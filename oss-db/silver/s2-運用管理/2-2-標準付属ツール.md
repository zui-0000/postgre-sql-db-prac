- データベース管理用コマンドの使い方

## 学習メモ

### ツールの全体像

| コマンド | 役割 | SQL でいうと |
| --- | --- | --- |
| `pg_ctl` | サーバーの起動、停止、再起動、リロード、状態確認 | （SQL では操作できない） |
| `createuser` / `dropuser` | ロールの作成と削除 | `CREATE ROLE` / `DROP ROLE` のラッパー |
| `createdb` / `dropdb` | データベースの作成と削除 | `CREATE DATABASE` / `DROP DATABASE` のラッパー |
| `psql` | 対話的に SQL を実行するクライアント | — |
| `pg_config` | インストール情報（バージョン、ディレクトリ）の表示 | — |
| `pg_controldata` | クラスタの制御情報の表示 | — |
| `pg_isready` | サーバーが接続を受け付けているかの確認 | — |
| `pg_resetwal` | WAL を消去して制御情報を初期化する（最後の手段） | — |

`createuser` などは「SQL のラッパー」である点が重要。OS のコマンドプロンプトから実行できるが、内部では普通の SQL が実行されている。

#### pg_ で始まる名前の見分け方

PostgreSQL では、OS のコマンドにも、システムビューにも、関数にも `pg_` が付く。名前だけではどれなのかわからないので、**どこで打つものか**で区別する。

| 種類 | どこで打つか | 例 |
| --- | --- | --- |
| OS のコマンド | シェル（bash など） | `pg_ctl`、`pg_config`、`pg_isready`、`pg_controldata`、`pg_resetwal` |
| システムビュー | psql などから `SELECT ... FROM` で読む | `pg_settings`、`pg_file_settings`、`pg_hba_file_rules`、`pg_stat_activity`、`pg_roles` |
| 関数 | psql などから `SELECT 関数名()` で呼ぶ | `pg_reload_conf()`、`pg_current_logfile()`、`pg_terminate_backend()` |

- `SELECT ... FROM` の後ろに書かれていれば、ビュー。
- 名前のあとに `()` が付いていれば、関数。
- それ以外で、出題範囲の「標準付属ツール」に並んでいれば、OS のコマンド。
- 例外は `pg_config` で、**OS のコマンドとシステムビューの両方がある**（「pg_config」を参照）。

`pg_settings` をシェルで打つと `command not found` になる。S2.3 の「重要な用語」で `pg_ctl reload/restart`（コマンド）と `pg_settings`（ビュー）が並んでいるので、混同しないようにする。

TypeScript で例えると、Prisma の `npx prisma migrate`（CLI）と、コードの中で呼ぶ `prisma.user.findMany()`（API）の違いに近い。どちらも「prisma」だが、打つ場所が違う。

### pg_ctl

サーバーのライフサイクルを扱うコマンド。データディレクトリは `-D` で指定する（`PGDATA` 環境変数でも可）。

`pg_ctl` のすぐあとに書いて「何をするか」を選ぶ単語を、公式ドキュメントでは**モード**と呼ぶ（「start mode launches a new server」など）。問題集などでは**サブコマンド**と呼ぶこともあるが、同じものを指す。`npm install` の `install` や、`git commit` の `commit` と同じ位置づけである。

```sh
pg_ctl  stop  -D /data -m fast
└────┘  └──┘  └──────────────┘
コマンド  モード   オプション
       （何をするか）（どうやるか）
```

| モード（サブコマンド） | 動作 |
| --- | --- |
| `start` | サーバーをバックグラウンドで起動する |
| `stop` | サーバーを停止する |
| `restart` | 停止してから起動する |
| `reload` | 設定ファイルを読み直す（SIGHUP を送る） |
| `status` | 起動しているかを確認する |
| `promote` | スタンバイサーバーを昇格させる |
| `logrotate` | サーバーのログファイルを切り替える（PG12 から。PG11 の公式ドキュメントにはない） |
| `kill` | 指定したプロセスにシグナルを送る（「pg_ctl kill」を参照） |
| `init` / `initdb` | `initdb` を呼び出してクラスタを作る（Ver.3.0 の改定で出題範囲から削除された） |

「モード」という言葉は、`-m` で指定する**停止モード**（`smart`、`fast`、`immediate`）にも使われるので混同しない。`stop` や `reload` は「何をするか」を選ぶモード（サブコマンド）で、停止モードは「`stop` をどうやるか」を選ぶオプションである。

`logrotate` は、sandbox の使い捨てのクラスタ（`logging_collector = on`）で試すと、`server signaled to rotate log file` と表示され、`log/` に新しいログファイルが作られた。

```text
### logrotate の前
postgresql-2026-09-26_080102.log

### logrotate の後
postgresql-2026-09-26_080102.log
postgresql-2026-09-26_080104.log     ← 新しいファイルに切り替わった
```

| オプション | 意味 |
| --- | --- |
| `-D` / `--pgdata` | データディレクトリの場所 |
| `-l` / `--log` | サーバーのログの出力先ファイル |
| `-m` / `--mode` | 停止モード（`smart`、`fast`、`immediate`） |
| `-w` / `--wait` | 完了を待つ（`start`、`stop`、`restart`、`promote` では既定） |
| `-W` / `--no-wait` | 完了を待たない |
| `-t` / `--timeout` | 完了を待つ最大の秒数。既定は **60 秒**（環境変数 `PGCTLTIMEOUT` があればその値）。「-t（待つ時間の上限）」を参照 |

#### -D を省略するとき（PGDATA）

`initdb` と同じく、**`-D` を省略しても、環境変数 `PGDATA` が設定されていれば実行できる**（[S2.1](2-1-インストール方法.md) の「オプションを省略したときの既定値」を参照）。エラーになるのは、`-D` も `PGDATA` もないときだけである。sandbox の使い捨てのクラスタで `reload` を試した結果:

```text
### -D も PGDATA もなし
pg_ctl: no database directory specified and environment variable PGDATA unset
  exit=1

### PGDATA だけ（-D なし）
server signaled
  exit=0

### -D だけ（PGDATA なし）
server signaled
  exit=0
```

エラーメッセージも「データディレクトリが指定されておらず、**しかも** `PGDATA` も設定されていない」という意味になっている。db と sandbox には Docker の公式イメージが `PGDATA=/var/lib/postgresql/18/docker` を設定しているので、`-D` を省略するとそのディレクトリが使われる。

`pg_ctl kill` だけは例外で、データディレクトリではなく PID を指定する（「pg_ctl kill」を参照）。

#### 設定の再読み込みは pg_ctl 以外でもできる

| 方法 | 実行する場所 | 実行できるユーザー |
| --- | --- | --- |
| `pg_ctl reload` | サーバーのマシンのシェル | データディレクトリの所有者（OS のユーザー） |
| `SELECT pg_reload_conf();` | SQL（psql など） | スーパーユーザー（`GRANT` で許可されたロールも可） |
| `pg_ctl kill HUP （postmaster の PID）`、`kill -HUP （postmaster の PID）` | サーバーのマシンのシェル | データディレクトリの所有者（OS のユーザー） |

公式ドキュメントによると、`pg_reload_conf()` は postmaster に SIGHUP を送り、postmaster が子プロセスにも SIGHUP を送る。つまり、中でしていることは `pg_ctl reload` と同じである。実機でも `pg_reload_conf()` は `t` を返し、サーバーのログに `received SIGHUP, reloading configuration files` が出た。スーパーユーザーでないロールが実行すると、`ERROR:  permission denied for function pg_reload_conf` になった。

`pg_reload_conf()` は SQL なので、サーバーのマシンにログインしなくても、ネットワーク越しに接続して実行できる。

#### restart（停止してから起動する）

公式ドキュメントには「`restart` は、実質的に `stop` のあとに `start` を実行する。postgres の起動オプションを変えるときや、再起動しないと変えられない設定を反映するときに使う」とある。停止モードは `stop` と同じく既定が `fast` で、`-m` で変えられる（「停止モード」を参照）。

sandbox の使い捨てのクラスタ（ポート 5499）で試した結果:

```text
$ pg_ctl -D /tmp/rs restart
waiting for server to shut down.... done
server stopped                        ← まず止める
waiting for server to start.... done
server started                        ← それから起動する
```

わかったことが3つある。

- **前回の起動オプションを引き継ぐ。** `pg_ctl -o "-p 5499" start` で起動すると、データディレクトリの `postmaster.opts` にそのときのコマンドが記録された（`/usr/lib/postgresql/18/bin/postgres "-D" "/tmp/rs" "-p" "5499"`）。`restart` で `-o` を付けなくても、再起動後のポートは 5499 のままだった。
- **`-l`（ログの出力先）は引き継がない。** `-l` を付けずに `restart` すると、サーバーのログが端末に出た。ファイルに出したいときは、`restart` にも `-l` を付ける。
- **止まっているときに `restart` しても、起動する。**

```text
pg_ctl: PID file "/tmp/rs/postmaster.pid" does not exist
Is server running?
trying to start server anyway         ← 「とにかく起動を試す」
waiting for server to start.... done
server started
```

`reload` との違い:

| | `pg_ctl reload` | `pg_ctl restart` |
| --- | --- | --- |
| すること | postmaster に SIGHUP を送り、設定ファイルを読み直させる | 止めてから起動する |
| 接続中のセッション | そのまま | **切れる**（既定の `fast` で止めるため） |
| 反映できる設定 | `context` が `sighup` 以下のもの | すべて（`postmaster` のものも） |
| 使う場面 | `pg_hba.conf` の変更、`log_statement` など | `port`、`listen_addresses`、`max_connections`、`logging_collector` など |

どちらも設定を反映するために使えるが、`restart` は接続を切ってしまう。リロードで済む設定なら、`reload` を使う（`context` の見方は [S2.3](2-3-設定ファイル.md) の「設定の反映方法」を参照）。

#### 停止モード

| | smart | fast（**既定**） | immediate |
| --- | --- | --- | --- |
| ひとことで | **行儀よく待つ** | **切断して確実に止める** | **いきなり止める** |
| 新しい接続 | 拒否する | 拒否する | （すぐに止まる） |
| 接続中のセッション | **自分から切断するまで待つ** | 強制的に切断する | ただちに終了させる |
| 実行中のトランザクション | そのまま最後まで実行できる | **ロールバックされる** | 中断される（コミット前の変更は残らない） |
| 正常な停止処理 | する | する | **しない** |
| 次の起動 | 普通に起動する | 普通に起動する | **リカバリ（WAL の再実行）が走る** |
| 送るシグナル | SIGTERM | SIGINT | SIGQUIT |
| 注意 | 接続が残っていると止まらない | 9.5 からこれが既定 | 非常用。コミット済みのデータは WAL から復元される |

- **smart**: 新しい接続を拒否し、**接続中のクライアントがすべて自分から切断するのを待って**から停止する。待つのは「処理の完了」ではなく「クライアントの切断」なので、接続が残っていると止まらない。
- **fast**（既定）: 新しい接続を拒否し、接続中のクライアントを強制的に切断して停止する。実行中のトランザクションはロールバックされる。正常な停止処理を行うので、次の起動は普通に行える。
- **immediate**: 正常な停止処理を行わずに、すべてのプロセスをただちに終了させる。次の起動時にリカバリ（WAL の再実行）が必要になる。

正常に止まるのは smart と fast で、止まり方が違うだけである。immediate だけが、異常終了と同じ扱いになる。

sandbox の使い捨てのクラスタで、3つのモードを比べた結果:

| 確かめたこと | smart | fast | immediate |
| --- | --- | --- | --- |
| サーバーのログ | `received smart shutdown request` | `received fast shutdown request` | `received immediate shutdown request` |
| 停止中に新しく接続すると | `FATAL:  the database system is shutting down` | — | — |
| 接続していたクライアント | 実行中の SQL は最後まで結果が返った | `FATAL:  terminating connection due to administrator command` | — |
| 停止後のクラスタの状態 | `shut down` | `shut down` | `in production` |
| 次に起動したときのログ | 普通に起動 | 普通に起動 | `database system was not properly shut down; automatic recovery in progress` |

`-m` は、頭文字1文字でも指定できる（公式ドキュメント）。`-m` を省略すると `fast` になる。

| 書き方 | 意味 |
| --- | --- |
| `-m smart` / `-m s` | 接続が全部切れるまで待つ |
| `-m fast` / `-m f` | 接続を切って止める（既定） |
| `-m immediate` / `-m i` | すぐに止める（次の起動時にリカバリが必要） |

**既定は 9.4 までは `smart` で、9.5 で `fast` に変わった**。リリースノートには「pg_ctl の既定の停止モードを smart から fast に変更した。既定の動きは、既存のセッションが終わるのを単に待つのではなく、強制的に取り消すことになる」とある。古い記事や本には `smart` と書かれていることがあるが、試験の基準（PG 12〜14）では `fast` が既定。

#### 実機で確認した結果

```text
### 停止中の pg_ctl status
pg_ctl: no server running
  exit=3                       ← 停止中は終了コード 3

### start
waiting for server to start.... done
server started
  exit=0

### 起動中の pg_ctl status
pg_ctl: server is running (PID: 113)
  exit=0

### reload（設定の再読み込み）
server signaled
  exit=0
```

`status` の終了コードは、**サーバーが停止していれば 3**、データディレクトリを特定できなければ 4 になる。シェルスクリプトから状態を判定するときに使える。

`immediate` で停止すると、クラスタの状態が正常終了時の `shut down` ではなく `in production` のまま残る。

```text
### immediate で停止したあとのクラスタ状態
Database cluster state:               in production

### 次の起動でクラッシュリカバリになるか（ログ）
LOG:  checkpoint starting: end-of-recovery immediate wait
LOG:  database system is ready to accept connections
```

次の起動時にリカバリ処理（`end-of-recovery` のチェックポイント）が走っているのが確認できる。

#### pg_ctl stop の仕組み

| 状況 | 結果（sandbox で確認） |
| --- | --- |
| サーバーが動いているとき | `waiting for server to shut down.... done` → `server stopped`（終了コード 0） |
| **動いていないとき** | `pg_ctl: PID file "/var/lib/postgresql/st/postmaster.pid" does not exist` / `Is server running?`（終了コード 1） |
| **root で実行したとき** | `pg_ctl: cannot be run as root`（終了コード 1）。`initdb` と同じ |

`pg_ctl stop` は、**データディレクトリの `postmaster.pid` から親プロセスの PID を読み取り、そのプロセスにシグナル（停止の合図）を送って**停止させる（[S2.1](2-1-インストール方法.md) で見た `postmaster.pid` の1行目が、その PID）。PID ファイルがないと停止する相手がわからないので、エラーになる。

停止モードと、送られるシグナル（公式ドキュメント「Shutting Down the Server」）:

| 停止モード | シグナル | サーバーの動き |
| --- | --- | --- |
| `smart` | SIGTERM | 新しい接続を受け付けず、既存のセッションが作業を終えるのを待ってから停止する |
| `fast`（既定） | SIGINT | 新しい接続を受け付けず、既存のサーバープロセスに SIGTERM を送ってトランザクションを中断させ、すべてのプロセスが終了してから停止する |
| `immediate` | SIGQUIT | すべての子プロセスに SIGQUIT を送る（5秒以内に終わらなければ SIGKILL）。通常の停止処理をしないので、次の起動時にリカバリが必要になる |

公式ドキュメントでは、`pg_ctl` は「これらのシグナルを送るための便利な手段」とされている。また、SIGKILL でサーバーを止めるのは避けるよう注意している（共有メモリなどが解放されず、子プロセスにも合図が伝わらないため）。

`pg_ctl` は、**サーバーと同じマシンで、データディレクトリにアクセスできる OS のユーザー**でしか使えない。ネットワーク越しに接続する psql とは、ここが違う。

練習は sandbox で行う。db で `pg_ctl stop` を実行すると、サーバー（コンテナの PID 1）が止まってコンテナごと停止する（[環境構築](../../../docs/01-環境構築.md)を参照）。データは名前付きボリュームに残るが、`docker compose start db` で起動し直す必要があり、接続中の psql も切断される。

#### -t（待つ時間の上限）

`-t` は、`-w`（完了を待つ）のときに **pg_ctl が待つ最大の秒数**を指定する。公式ドキュメントによると、既定値は環境変数 `PGCTLTIMEOUT` の値で、設定されていなければ **60 秒**。

**時間切れになっても、サーバーを強制的に止めるわけではない。** 公式ドキュメントには「時間内に終わらなければ、pg_ctl は 0 以外の終了コードで終わる。ただし、操作は裏で続いていて、あとで成功するかもしれない」とある。

sandbox の使い捨てのクラスタで、`SELECT pg_sleep(8)` を実行中の接続を残したまま、`smart` モードの停止を `-t 3` で試した結果:

```text
$ pg_ctl stop -m smart -t 3
waiting for server to shut down...... failed
pg_ctl: server does not shut down
HINT: The "-m fast" option immediately disconnects sessions rather than
waiting for session-initiated disconnection.
  exit=1                          ← 約3秒で、pg_ctl だけが待つのをやめた

$ pg_ctl status                   ← 直後
pg_ctl: server is running         ← サーバーはまだ動いている（停止処理は続いている）

$ pg_ctl status                   ← 接続が終わったあと
pg_ctl: no server running         ← 接続が切れてから止まった
```

`-t` は「pg_ctl が待つのをやめる時間」であって、「サーバーを止める期限」ではない。時間切れで `immediate` などに切り替わることもない。HINT のとおり、確実に止めたいなら `-m fast` を使う。

#### pg_ctl kill（プロセスにシグナルを送る）

```sh
pg_ctl kill シグナル名 PID
```

**指定した PID のプロセスに、指定したシグナルを送る**モード。ほかのモードと違って `-D` は使わず、送る相手を PID で直接指定する。公式ドキュメントには「主に、`kill` コマンドが組み込まれていない Microsoft Windows で役に立つ」とある。Linux なら OS の `kill` コマンドで同じことができる（公式ドキュメントの例: ``kill -INT `head -1 /usr/local/pgsql/data/postmaster.pid` ``）。

使えるシグナル名は `pg_ctl --help` で確認できる。

```text
Allowed signal names for kill:
  ABRT HUP INT KILL QUIT TERM USR1 USR2
```

シグナル名は**大文字で、`SIG` を付けずに**書く。sandbox で確かめた結果:

| コマンド | 結果 |
| --- | --- |
| `pg_ctl kill HUP 1172` | 成功（何も表示されず、終了コード 0） |
| `pg_ctl kill hup 1172` | `unrecognized signal name "hup"`（終了コード 1） |
| `pg_ctl kill SIGHUP 1172` | `unrecognized signal name "SIGHUP"`（終了コード 1） |
| `pg_ctl kill HUP 99999` | `could not send signal 1 (PID: 99999): No such process`（終了コード 1） |

Node.js の `process.kill(pid, 'SIGTERM')` と同じ役割だが、Node.js は `SIG` を付けて書く点が違う。

##### 何が起きるかは、送る相手とシグナルで決まる

`pg_ctl kill` 自体は、シグナルを届けるだけである。何が起きるかは、受け取ったプロセスがそのシグナルをどう扱うかで決まる。

| 送る相手 | シグナル | 起きること | 同じことをする方法 |
| --- | --- | --- | --- |
| postmaster（親プロセス） | HUP | 設定ファイルを読み直す | `pg_ctl reload` |
| postmaster | TERM | smart モードで停止する | `pg_ctl stop -m smart` |
| postmaster | INT | fast モードで停止する | `pg_ctl stop -m fast` |
| postmaster | QUIT | immediate モードで停止する | `pg_ctl stop -m immediate` |
| 接続（バックエンドプロセス） | INT | 実行中の SQL を取り消す（接続は残る） | `SELECT pg_cancel_backend(PID);` |
| 接続（バックエンドプロセス） | TERM | その接続だけを切断する | `SELECT pg_terminate_backend(PID);` |

公式ドキュメントにも「`pg_cancel_backend` と `pg_terminate_backend` は、それぞれ SIGINT と SIGTERM をバックエンドプロセスに送る」とある。postmaster に送るシグナルと停止モードの対応は、「pg_ctl stop の仕組み」の表と同じ。

PID の調べ方:

- postmaster の PID は、`postmaster.pid` の1行目か、`pg_ctl status` で確認できる。
- 接続ごとのバックエンドプロセスの PID は、`pg_stat_activity` の `pid` 列で確認できる。

sandbox で、`SELECT pg_sleep(30)` を実行中の接続に送った結果:

```text
### pg_ctl kill INT（バックエンドの PID）
ERROR:  canceling statement due to user request        ← SQL だけが取り消された

### pg_ctl kill TERM（バックエンドの PID）
FATAL:  terminating connection due to administrator command   ← 接続が切られた
pg_ctl: server is running (PID: 1172)                  ← サーバー全体は動いたまま
```

postmaster に送った結果（サーバーのログ）:

```text
### pg_ctl kill HUP（postmaster の PID）
LOG:  received SIGHUP, reloading configuration files

### pg_ctl kill TERM（postmaster の PID）
LOG:  received smart shutdown request
LOG:  database system is shut down
```

同じ TERM でも、**postmaster に送るとサーバー全体が smart モードで止まり、バックエンドプロセスに送るとその接続だけが切れる**。KILL（SIGKILL）でサーバーを止めてはいけない理由は、「pg_ctl stop の仕組み」を参照。

### createuser と createdb

どちらも SQL のラッパーなので、`-e`（`--echo`）を付けると**実際に実行される SQL が表示される**。

```sh
createuser -U postgres -e --createdb appuser
createdb  -U postgres -e -O appuser appdb
dropdb    -U postgres -e appdb
dropuser  -U postgres -e appuser
```

```sql
CREATE ROLE appuser NOSUPERUSER CREATEDB NOCREATEROLE INHERIT LOGIN NOREPLICATION NOBYPASSRLS;
CREATE DATABASE appdb OWNER appuser;
DROP DATABASE appdb;
DROP ROLE appuser;
```

オプションを何も付けない場合の既定値が、この出力からわかる。**スーパーユーザーではない、データベースを作れない、ロールを作れない、ログインできる、権限を継承する**。

| `createuser` のオプション | 意味 |
| --- | --- |
| `-s` / `--superuser` | スーパーユーザーにする |
| `-d` / `--createdb` | データベースを作成できるようにする（既定は `-D`、作成不可） |
| `-r` / `--createrole` | ほかのロールを作成できるようにする（既定は `-R`） |
| `-L` / `--no-login` | ログインできないロールにする（既定は `-l`、ログイン可） |
| `-P` / `--pwprompt` | パスワードの入力を求める |
| `-g` / `--member-of` | 既存のロールのメンバーにする |
| `-e` / `--echo` | 実行する SQL を表示する |

`createuser` を実行できるのは、**スーパーユーザーか `CREATEROLE` 権限を持つユーザー**だけ。

#### 大文字と小文字のオプション

`createuser` のロール属性のオプションは、**小文字が「付ける」、大文字が「付けない」**の対になっている。

```text
createuser -e -s -d -r -l -i caseA
→ CREATE ROLE "caseA" SUPERUSER CREATEDB CREATEROLE INHERIT LOGIN NOREPLICATION NOBYPASSRLS;

createuser -e -S -D -R -L -I caseB
→ CREATE ROLE "caseB" NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOLOGIN NOREPLICATION NOBYPASSRLS;
```

| 小文字（付ける） | 大文字（付けない） |
| --- | --- |
| `-s` / `--superuser` | `-S` / `--no-superuser`（既定） |
| `-d` / `--createdb` | `-D` / `--no-createdb`（既定） |
| `-r` / `--createrole` | `-R` / `--no-createrole`（既定） |
| `-l` / `--login`（既定） | `-L` / `--no-login` |
| `-i` / `--inherit`（既定） | `-I` / `--no-inherit` |

**この対応は `createuser` のロール属性の5組だけ**で、PostgreSQL のコマンド全体の決まりではない。同じ `createuser` でも、`-p`（ポート）と `-P`（新しいロールのパスワードを設定する）、`-v`（有効期限）と `-V`（バージョン）は無関係である。

ほかのコマンドでは、大文字の意味はばらばらである（PG18.6 の `--help` で確認）。

| コマンド | 小文字 | 大文字 | 関係 |
| --- | --- | --- | --- |
| `psql` | `-s` シングルステップ | `-S` シングルライン | 無関係 |
| `psql` | `-l` データベースの一覧 | `-L` ログファイル | 無関係 |
| `createdb` | `-e` 実行する SQL を表示 | `-E` エンコーディング | 無関係 |
| `pg_ctl` | `-w` 待つ（既定） | `-W` **待たない** | 大文字が否定 |
| `psql`、`createuser` など | `-w` パスワードを**尋ねない** | `-W` パスワードを必ず尋ねる | **小文字が否定**（`pg_ctl` と逆） |
| `pg_dump` | `-t` このテーブルだけ | `-T` このテーブルを除く | 大文字が除外 |

##### 間違えやすい -W と -D

`-W` は、コマンドによって意味が逆になる。

| コマンド | `-w` | `-W` |
| --- | --- | --- |
| `pg_ctl` | 完了を待つ（既定） | 完了を待たない |
| `psql`、`createuser`、`createdb`、`dropdb`、`dropuser`、`pg_dump` など | パスワードを尋ねない | パスワードを必ず尋ねる |

**サーバーに接続するコマンドの `-w` と `-W` は、どれもパスワードの指定である**。`pg_ctl` はサーバーに接続しない（`-h` や `-U` もない）ので、パスワードのオプションがなく、`-w` と `-W` は「待つ（wait）」の意味になる。`createuser` の `-W` と `-P` の違いは、「-W と -P の違い」を参照。

`-D` は、3つのコマンドで意味が違う。

| コマンド | `-D` の意味 | 長い形 |
| --- | --- | --- |
| `pg_ctl`、`initdb` | データディレクトリ | `--pgdata` |
| `createdb` | テーブルスペース | `--tablespace` |
| `createuser` | データベースを作れないロールにする | `--no-createdb` |

##### 迷ったら長い形で考える

長い形のオプションでは、否定はどれも `--no-` で始まる（`--no-createdb`、`--no-login`、`--no-wait`、`--no-password`）。npm の CLI でよく見る `--no-color` と同じ書き方である。短い形の大文字で迷ったら、長い形に置き換えて意味を確かめる。

#### 接続に使うロール（-U）

公式ドキュメントでは、`-U` は「接続に使うユーザー名（**作成するユーザー名ではない**）」と説明されている。

```sh
createuser -U postgres alice
#          └─────────┘ └───┘
#          接続に使うロール  作るロール
```

`-U` を省略した場合、接続に使うロールは次の順で決まる。

| 優先順位 | 決まり方 |
| ---: | --- |
| 1 | `-U` で指定したロール |
| 2 | 環境変数 `PGUSER` |
| 3 | 今ログインしている **OS のユーザーと同じ名前のロール** |

「OS のユーザーで実行される」のではなく、「同じ名前のロールで接続しようとする」点に注意する。db コンテナに root で入った状態で確かめた結果:

```text
### -U なし、PGUSER なし
FATAL:  role "root" does not exist        ← OS のユーザー root と同じ名前のロールを探した

### PGUSER=postgres を設定して、-U なし
CREATE ROLE demo_pguser ...               ← PGUSER の postgres で接続できた
```

データベースを省略した場合も同じ考え方で、ロール名と同じ名前のデータベースに接続しようとする。

| 省略したもの | 使われる既定値 |
| --- | --- |
| ロール（`-U`） | `PGUSER`、なければ OS のユーザー名 |
| データベース（`-d`） | `PGDATABASE`、なければロール名 |

sandbox で `psql` とだけ打って接続できたのは、OS のユーザー、ロール、データベースの名前がすべて `postgres` で揃っていたからである。

##### OS のユーザーと違うロールで接続できるか

できるかどうかは、**認証方式（`pg_hba.conf`）で決まる**。sandbox の OS のユーザーは `postgres` のまま、`-U appadmin` と別のロールを指定して試した結果:

| ローカル接続の認証方式 | 結果 |
| --- | --- |
| `peer`（OS のユーザー名とロール名が一致しないと接続させない） | `FATAL:  Peer authentication failed for user "appadmin"` |
| `trust`（パスワードなしで接続させる） | 成功。`CREATE ROLE newrole ...` が実行された |

| 認証方式 | OS のユーザーと違うロールで接続できるか |
| --- | --- |
| `peer` | できない |
| `trust` | できる（パスワードも要らない） |
| `scram-sha-256` など | そのロールのパスワードがわかればできる |

学習環境の db と sandbox は、ローカル接続が `trust` なので、どのロールでも接続できる。パッケージでインストールした Linux の環境では、ローカル接続が `peer` になっていることが多いため、`sudo -u postgres createuser ...` のように OS のユーザーごと切り替えて実行するやり方をよく見かける。認証方式の設定は [S2.3](2-3-設定ファイル.md) で扱う。

##### 接続に使うロールに権限が必要

権限のないロールで `createuser` を実行すると、エラーになる。

```text
DETAIL:  Only roles with the CREATEROLE attribute may create roles.
```

`dropuser` では、PG18 の場合さらに条件がある。

| 操作 | 結果（PG18） |
| --- | --- |
| `CREATEROLE` を持つ `appadmin` が、自分で作った `newrole` を削除 | 成功 |
| `CREATEROLE` を持つ `appadmin` が、postgres が作った `victim` を削除 | `ERROR:  permission denied to drop role` |

```text
DETAIL:  Only roles with the CREATEROLE attribute and the ADMIN option on role "victim" may drop this role.
```

PG16 から、`CREATEROLE` を持っていても、そのロールに対する `ADMIN OPTION` がないと削除できなくなった。自分で作ったロールには自動で `ADMIN OPTION` が付くので、`newrole` は削除できた。試験の基準（PG 12〜14）では、`CREATEROLE` があればスーパーユーザー以外のロールを削除できる（[S2.5](2-5-基本的な運用管理作業.md) の「⚠️ 試験と最新版の違い」を参照）。

##### -W と -P の違い

| オプション | 入力を求めるパスワード |
| --- | --- |
| `-W`（`--password`） | **接続のための**パスワード（`-U` で指定したロールの） |
| `-P`（`--pwprompt`） | **新しく作るロールの**パスワード |

#### 作ったロールと OS のユーザーの関係

**オプションを付けずに作ったロールの属性は、誰が実行しても同じ既定値になる**。実行した OS のユーザーの設定も、接続に使ったロールの属性も引き継がない。

db コンテナに OS の root ユーザーで入り、`createuser -U postgres -e` を実行した結果（作るロールの名前も省略した）:

```text
CREATE ROLE root NOSUPERUSER NOCREATEDB NOCREATEROLE INHERIT LOGIN NOREPLICATION NOBYPASSRLS;

 rolname  | rolsuper | rolcreatedb | rolcreaterole | rolcanlogin | rolinherit
----------+----------+-------------+---------------+-------------+------------
 postgres | t        | t           | t             | t           | t
 root     | f        | f           | f             | t           | t
```

- OS の root は何でもできる管理者だが、作られたロールはスーパーユーザーではない。
- 接続に使った postgres はスーパーユーザーだが、その属性も引き継がれない。

ただし、**作るロールの名前を省略すると、名前は次の順で決まる**（createuser のソースコードと実機で確認）。上の例で root というロールができたのは、3番目のルールによる。

| 優先順位 | 作るロールの名前 |
| ---: | --- |
| 1 | コマンドの最後に書いた名前 |
| 2 | 環境変数 `PGUSER` |
| 3 | 実行した OS のユーザー名 |

`PGUSER=postgres createuser` のように名前を省略すると、postgres を作ろうとして `ERROR:  role "postgres" already exists` になった。

また、`createuser` が作るのは PostgreSQL の中の**ロール**だけで、**OS のユーザーは作らないし、変えもしない**。中でしているのは `CREATE ROLE` の実行だけである。PostgreSQL のロールと OS のユーザーは別物で、OS のユーザー名が関わるのは次の2つに限られる。

- 名前の既定値（接続に使うロール、作るロール、`createdb` で作るデータベース）
- 認証方式が `peer` のときの照合（[S2.3](2-3-設定ファイル.md) の `pg_hba.conf` で扱う）

#### createdb のオプション

| `createdb` のオプション | 意味 |
| --- | --- |
| `-O` / `--owner` | データベースの所有者を指定する |
| `-T` / `--template` | コピー元のテンプレートを指定する（`-T template0` など） |
| `-E` / `--encoding` | エンコーディングを指定する |
| `-l` / `--locale` | ロケールを指定する |
| `-D` / `--tablespace` | 既定のテーブルスペースを指定する |
| `-e` / `--echo` | 実行する SQL を表示する |

**データベース名を省略すると、実行した OS ユーザーと同じ名前のデータベースが作られる。**（公式ドキュメントの説明。ソースコードでは、環境変数 `PGDATABASE`、`PGUSER` が設定されていれば、その順に優先される。）`createdb` の `-D` はテーブルスペースの指定で、`pg_ctl` や `initdb` の `-D`（データディレクトリ）とは意味が違う点に注意する。

#### テンプレートと違うエンコーディングで作る

テンプレート（既定は `template1`）と違うエンコーディングのデータベースを作るには、**`-T template0` と `-E` を指定する**。ただし、エンコーディングはロケールとも合っている必要があるので、環境によってはロケールも一緒に指定する。

`template1` のエンコーディングが `UTF8`、ロケールが `en_US.utf8` の環境で、EUC_JP のデータベースを作ろうとした結果:

| コマンド | 結果 | 原因 |
| --- | --- | --- |
| `createdb -E EUC_JP e1` | ✗ | ロケール（`en_US.utf8`）と合わない |
| `createdb -T template0 -E EUC_JP e2` | ✗ | ロケール（`en_US.utf8`）と合わない |
| `createdb -E EUC_JP -l C e1` | ✗ | テンプレート（`template1`、UTF8）とエンコーディングが違う |
| **`createdb -T template0 -E EUC_JP -l C e3`** | **○** | — |

`template1` からは、エンコーディングを変えられない。

```text
ERROR:  new encoding (EUC_JP) is incompatible with the encoding of the template database (UTF8)
HINT:  Use the same encoding as in the template database, or use template0 as template.
```

公式ドキュメント（CREATE DATABASE）には「エンコーディングとロケールの設定は、テンプレートと一致していなければならない。ただし `template0` をテンプレートにする場合は例外である」とある。理由は「ほかのデータベースには、指定したエンコーディングに合わないデータや、`LC_COLLATE` と `LC_CTYPE` で並び順が変わるインデックスが入っているかもしれない」から。`template1` には誰かがテーブルなどを入れているかもしれず、それを別のエンコーディングのまま丸ごとコピーすると、中身と設定が食い違う。何も手が加わっていない `template0` なら、この心配がない。

また、エンコーディングはロケールと合っている必要がある（[S2.1](2-1-インストール方法.md) の「エンコーディングとロケール」を参照）。

```text
ERROR:  encoding "EUC_JP" does not match locale "en_US.utf8"
DETAIL:  The chosen LC_CTYPE setting requires encoding "UTF8".
```

`en_US.utf8` は UTF8 専用なので、EUC_JP にするならロケールも変える。公式ドキュメントの例も、エンコーディングとロケールを両方指定している。

```sh
createdb -E EUC_KR -T template0 --lc-collate=ko_KR.euckr --lc-ctype=ko_KR.euckr korean
```

成功したときに、`-e` で表示された SQL:

```sql
CREATE DATABASE e3 ENCODING 'EUC_JP' TEMPLATE template0 LOCALE 'C';
```

クライアントとサーバーのエンコーディングが違う場合の自動変換は、[S2.3](2-3-設定ファイル.md) の「クライアントのエンコーディング」で扱う。

#### createdb と CREATE DATABASE は別物

`createdb` は `CREATE DATABASE` を小文字にしたものではない。名前が似ているだけで、実行する場所が違う。

| | `CREATE DATABASE` | `createdb` |
| --- | --- | --- |
| 正体 | **SQL 文** | **OS のコマンド（プログラム）** |
| 実行する場所 | psql などの中 | OS のシェル |
| 大文字と小文字 | 区別しない（`create database` でも動く） | **区別する**（Linux のコマンドなので） |

実機で確認した結果:

```text
psql の中で createdb foo;   → ERROR:  syntax error at or near "createdb"
シェルで createdb           → 成功
シェルで CREATEDB           → bash: CREATEDB: command not found
```

`createdb` は、内部で `CREATE DATABASE` をサーバーに送るラッパーである。SQL のキーワードと識別子の大文字・小文字の扱いは、[S3.1 の 02 テーブルと制約](../s3-開発SQL/3-1-SQLコマンド/02-テーブルと制約.md)で扱う。

ただし、psql のメタコマンド **`\!`** を使うと、psql の中から OS のコマンドを実行できる。

```text
postgres=# \! createdb bangdb        ← OS のコマンドとして実行される
postgres=# SELECT datname FROM pg_database WHERE datname = 'bangdb';
 datname
---------
 bangdb                              ← 作られていた

postgres=# \! whoami
postgres                             ← OS のユーザーとして動いている
```

| 場所 | 打てるもの | データベースを作るには |
| --- | --- | --- |
| シェル（`postgres@...:/$`） | OS のコマンド | `createdb mydb` |
| psql の中（`postgres=#`） | SQL とメタコマンド | `CREATE DATABASE mydb;` |
| psql の中で `\!` を付ける | OS のコマンド | `\! createdb mydb` |

`\!` で実行されるのは、**psql を動かしているマシン**である。サーバーが別のマシンにある場合は、サーバー側ではなく手元のマシンで実行される。

#### データベースを削除するときの制約

データベースに接続しているセッションがあると、そのデータベースは削除できない。

| 状況 | 結果（実機で確認） |
| --- | --- |
| 自分が接続しているデータベースを、自分で削除する | `ERROR:  cannot drop the currently open database` |
| 別のセッションが接続しているデータベースを `dropdb` する | `ERROR:  database "dropcheck" is being accessed by other users`（`DETAIL:  There is 1 other session using the database.`） |
| `DROP DATABASE dropcheck WITH (FORCE);` | 削除できた（接続を切ってから削除する） |
| `dropdb --force forcecheck`（短い形は `-f`） | 削除できた |

削除するときは、自分は別のデータベース（`postgres` など）に接続した状態で実行し、ほかに接続しているセッションがないことを確かめる。どうしても切断して削除したいときは、`WITH (FORCE)` か `--force` を使う（どちらも PG13 で追加された）。

`CREATE DATABASE` でコピー元に接続があると失敗するのと同じで、**データベース全体を扱う操作は、接続中のセッションがあると失敗する**（[S2.1](2-1-インストール方法.md) のテンプレートデータベースを参照）。

##### 削除できるのは、所有者とスーパーユーザーだけ

公式ドキュメント（DROP DATABASE）には「データベースの所有者しか実行できない」とある。スーパーユーザーは権限のチェックをすべて通るので、所有者でなくても削除できる。`dropdb` は `DROP DATABASE` のラッパーなので、同じ決まりに従う。

db で、alice が作ったデータベースを、ほかのロールに削除させた結果:

| 削除しようとしたロール | 結果 |
| --- | --- |
| bob（`CREATEDB` 権限あり、所有者ではない） | ✗ `ERROR:  must be owner of database adb1` |
| alice（所有者） | ○ |
| postgres（スーパーユーザー） | ○ |
| carol（alice のメンバー。`GRANT alice TO carol;`） | ○ |

- **`CREATEDB` 権限があっても、ほかのロールが所有するデータベースは削除できない。** `CREATEDB` は「作る」権限であって、「削除する」権限ではない。
- 公式ドキュメント（Privileges）には「オブジェクトを変更したり削除したりする権利は、所有者であることに付いてくるもので、それ自体を `GRANT` したり `REVOKE` したりはできない。ただし、ほかの権限と同じく、所有者のロールのメンバーには引き継がれる」とある。carol が削除できたのはこのためである。試験では「所有者とスーパーユーザー」と覚えておけば十分である。

`DROP DATABASE ... WITH (FORCE)` で切断できるのも、実行したロールが `pg_terminate_backend` で切断できる接続に限られる。切断できない接続が残ると、削除は失敗する（公式ドキュメント）。

### psql

#### シェルと psql の違い

「postgres」という名前は、いくつもの別のものに使われている。実機で確認すると、次の5つがあった。

| 種類 | 実体 |
| --- | --- |
| サーバーのプログラム | `/usr/lib/postgresql/18/bin/postgres` |
| サーバーのプロセス | db コンテナの PID 1 で動いている `postgres` |
| OS のユーザー | `uid=999(postgres)`。sandbox に `bash` で入ったときのユーザー |
| データベース | `initdb` が作る `postgres` データベース |
| ロール | `initdb` が作るスーパーユーザーの `postgres` |

そのため、コンテナのシェルと psql の両方のプロンプトに「postgres」が出てくるが、意味は違う。

| | コンテナのシェル（bash） | psql の中 |
| --- | --- | --- |
| プロンプト | `postgres@10ddd12c5212:/$` | `postgres=#` |
| この `postgres` は | **OS のユーザー名** | **接続中のデータベース名** |
| 最後の記号 | `$` は一般ユーザー（root なら `#`。db のシェルは `root@...:/#`） | `#` はスーパーユーザー（そうでなければ `>`） |
| 打てるもの | OS のコマンド（`initdb`、`pg_ctl`、`createdb`、`psql`） | SQL とメタコマンド（`SELECT`、`CREATE DATABASE`、`\l`、`\c`） |
| 抜け方 | `exit` | `\q` |

psql のプロンプトは、既定では `'%/%R%x%# '` という設定で作られる（公式ドキュメント。末尾の空白までが設定値）。

| 記号 | 意味 |
| --- | --- |
| `%/` | 接続中のデータベース名 |
| `%R` | 通常は `=`。SQL を打ち終えていない続きの行では `-` |
| `%x` | トランザクションの状態。トランザクション中は `*` |
| `%#` | スーパーユーザーなら `#`、それ以外は `>` |

実機でプロンプトが変わる様子:

```text
postgres=# BEGIN;
postgres=*# SELECT 1           ← トランザクション中なので * が付く
postgres-*# ;                  ← セミコロンがないので、続きの行になった
postgres=*# ROLLBACK;
postgres=# SELECT 2;           ← トランザクションが終わり、* が消えた
```

一般ユーザーのロールで接続すると、最後の記号が `>` になる。

```text
postgres=> SELECT current_user;
```

**プロンプトを見れば、今どのデータベースに、どの権限で、トランザクション中かどうかがわかる。**

```text
Mac のターミナル
   │ docker compose exec sandbox bash
   ▼
コンテナのシェル（bash）          postgres@10ddd12c5212:/$   ← OS のユーザー postgres
   │ psql
   ▼
psql（クライアント）               postgres=#               ← データベース postgres に接続中
   │ SQL を送る
   ▼
postgres（サーバーのプロセス）     ← 裏で動き続けている。直接「入る」ものではない
   │
   ▼
データベース postgres
```

Node.js で例えると、サーバーの `postgres` は `node server.js` で動いている Express のサーバー、psql は `curl` のようなクライアントにあたる。サーバーの中に入るのではなく、クライアントから SQL を送っている。

よくある打ち間違い:

| 打った場所 | 打ったもの | 結果 |
| --- | --- | --- |
| psql の中 | `createdb mydb;` | 構文エラー（OS のコマンドなので） |
| シェル | `SELECT 1;` | `command not found`（SQL なので） |
| db コンテナのシェル（root） | `psql`（`-U` なし） | `FATAL:  role "root" does not exist` |

最後の例は、db コンテナに `docker compose exec db bash` で入ると root になるために起きる。psql はユーザー名を省略すると OS のユーザー名（`root`）で接続しようとするが、そのロールは存在しない。`psql -U postgres` と指定するか、`docker compose exec -u postgres db bash` で postgres ユーザーとして入る。

なお、対話モードで結果が画面に収まらないときは、ページャ（`less`）が開く。`q` で psql に戻る。

##### 自分で試す

```sh
docker compose exec -u postgres db bash   # OS のユーザー postgres で入る → postgres@...:/$
psql                                       # → postgres=#
```

psql の中で、次のように打ってプロンプトの変化を見る。

```sql
BEGIN;          -- → postgres=*#
SELECT 1        -- セミコロンなしで Enter → postgres-*#
;               -- 実行される
ROLLBACK;       -- → postgres=#
\q
```

最後に `exit` でシェルから抜ける。

#### オプション

| オプション | 意味 |
| --- | --- |
| `-c` / `--command` | SQL を1つ実行して終了する |
| `-f` / `--file` | ファイルから SQL を読み込んで実行する |
| `-l` / `--list` | データベースの一覧を表示して終了する |
| `-d`、`-U`、`-h`、`-p` | 接続先のデータベース、ユーザー、ホスト、ポート |
| `-A` / `--no-align` | 桁揃えをしない出力にする |
| `-t` / `--tuples-only` | ヘッダーと行数の表示を省く |
| `-x` / `--expanded` | 縦方向の拡張表示にする |
| `-X` / `--no-psqlrc` | `~/.psqlrc` を読み込まない |
| `-s` / `--single-step` | シングルステップモード。コマンドを送る前に毎回確認を求める |
| `-S` / `--single-line` | シングルラインモード。改行で SQL の終わりとみなす |
| `-1` / `--single-transaction` | `-c` と `-f` で渡したコマンドを、1つのトランザクションにまとめる（「-1（シングルトランザクション）」を参照） |

#### -s（シングルステップ）と -S（シングルライン）

小文字の `-s` と大文字の `-S` は、まったく別の意味を持つ。

| オプション | 公式ドキュメントの説明 |
| --- | --- |
| `-s`（`--single-step`） | シングルステップモードで実行する。**コマンドをサーバーに送る前に毎回ユーザーに確認を求め**、実行を取り消すこともできる。スクリプトのデバッグに使う |
| `-S`（`--single-line`） | シングルラインモードで実行する。**改行が、セミコロンと同じように SQL の終わりとみなされる** |

`-s` で2つの SQL を流し、1つ目は Enter で実行し、2つ目は `x` で取り消した結果:

```text
/**(Single step mode: verify command)******************************************/
SELECT 1 AS first;
/**(press return to proceed or enter x and return to cancel)*******************/
 first
-------
     1                          ← Enter を押したので実行された

/**(Single step mode: verify command)******************************************/
SELECT 2 AS second;
/**(press return to proceed or enter x and return to cancel)*******************/
                                ← x を入力したので実行されなかった
```

`-S` では、セミコロンがなくても改行で実行された。

```text
$ psql -S   （入力: SELECT 10 AS no_semicolon ⏎ SELECT 20 AS also_no_semicolon ⏎）
 no_semicolon
--------------
           10

 also_no_semicolon
-------------------
                20
```

同じ入力を `-S` なしで流すと、2行が1つの SQL としてつながり、構文エラーになった。

```text
ERROR:  syntax error at or near "SELECT"
LINE 2: SELECT 20 AS also_no_semicolon
```

公式ドキュメントは `-S` について、「こだわる人のために用意しているが、使うことを勧めるわけではない。SQL とメタコマンドを1行に混ぜると、実行の順番がわかりにくくなる」と注意している。

同じ `-s` でも、**コマンドが違えば意味が違う**。オプションはコマンド名とセットで覚える。

| コマンド | `-s` の意味 |
| --- | --- |
| `psql -s` | シングルステップ（毎回確認する） |
| `pg_ctl -s` | サイレント（エラー以外のメッセージを出さない） |
| `createuser -s` | スーパーユーザーとして作る |

#### SQL ファイルを実行する

ファイルに書いた SQL を実行する方法は3つある。

| やり方 | どこで打つか |
| --- | --- |
| `psql testdb < sample.sql` | シェル（リダイレクト） |
| `psql testdb -f sample.sql` | シェル（psql のオプション） |
| `\i sample.sql` | psql の中（メタコマンド） |

1つ目の `<` は、psql のオプションではなく**シェルの機能（リダイレクト）**である。シェルがファイルを開き、その中身を psql の標準入力に流し込む。psql から見ると、キーボードから打ったものと同じ扱いになる。

```sh
psql testdb < sample.sql
#    └────┘ └──────────┘
#    接続するデータベース（最初の引数）
#           sample.sql の中身を psql の標準入力に流し込む
```

公式ドキュメントでは、`-f` は「メタコマンドの `\i` とほぼ同じ」であり、「`psql < ファイル名` とは微妙に違う。どちらも期待どおりに動くが、`-f` を使うとエラーメッセージに行番号が付く」と説明されている。

3行目でわざと主キーを重複させたファイルで、3つのやり方を比べた。

```sql
CREATE TABLE fruits (id int PRIMARY KEY, name text);
INSERT INTO fruits VALUES (1, 'りんご');
INSERT INTO fruits VALUES (1, 'みかん');   -- 3行目: 主キーが重複する
INSERT INTO fruits VALUES (2, 'ぶどう');
SELECT * FROM fruits ORDER BY id;
```

```text
### psql testdb < sample.sql
ERROR:  duplicate key value violates unique constraint "fruits_pkey"

### psql testdb -f sample.sql（\i も同じ）
psql:/tmp/sample.sql:3: ERROR:  duplicate key value violates unique constraint "fruits_pkey"
     └──────────────────┘
     ファイル名と行番号がわかる
```

**既定では、エラーが起きても最後まで実行される**。どのやり方でも、3行目のあとの INSERT と SELECT が実行されていた。

```text
 id |  name
----+--------
  1 | りんご
  2 | ぶどう      ← エラーのあとの行も実行されている
```

エラーで止めたいときは、変数 **`ON_ERROR_STOP`** を設定する。

```text
$ psql testdb -v ON_ERROR_STOP=1 -f sample.sql
psql:/tmp/sample.sql:3: ERROR:  duplicate key value violates unique constraint "fruits_pkey"
  exit=3        ← 3行目で止まり、終了コード 3 で終わった
```

psql も、`pg_isready` と同じく終了コードで結果を返す（公式ドキュメント）。

| 終了コード | 意味 |
| ---: | --- |
| 0 | 正常に終了した |
| 1 | psql 自身の致命的なエラー（ファイルが見つからないなど） |
| 2 | 対話モードでないときに、サーバーとの接続が切れた |
| 3 | `ON_ERROR_STOP` を設定していて、スクリプトでエラーが起きた |

#### -1（シングルトランザクション）

`-1`（`--single-transaction`）は、**`-c` や `-f` で渡したコマンドを、まとめて1つのトランザクションにする**オプション。公式ドキュメントによると、psql が最初の `-c` や `-f` の前に `BEGIN` を、最後のあとに `COMMIT` を送る。これで「すべてのコマンドが成功するか、何も反映されないか」のどちらかになる。

`-1` は数字の「いち」である。小文字の `-l`（エル）は「データベースの一覧」なので、見た目で間違えないようにする。

同じトランザクションで実行されたかは、トランザクション ID（`txid_current()`）で確かめられる。

```text
psql -c "SELECT txid_current()" -c "SELECT txid_current()"      → 948 と 949（別々のトランザクション）
psql -1 -c "SELECT txid_current()" -c "SELECT txid_current()"   → 950 と 950（同じトランザクション）
```

途中でエラーが起きたときの違い（`id` が主キーのテーブルに 1、1、2 を `INSERT` し、2つ目が重複でエラーになる）:

| 実行のしかた | 結果 |
| --- | --- |
| `-1` なし | 1つ目と3つ目が入る（2行）。**途中まで反映される** |
| `-1` あり | 0行。**すべて取り消される** |

`-1` ありの場合、エラーのあとのコマンドは `current transaction is aborted, commands ignored until end of transaction block` になり、実行されなかった。TypeScript で例えると、Prisma の `$transaction([...])` で包むのと同じである。

注意点（公式ドキュメントと実機で確認）:

- **トランザクションの中で実行できないコマンドが含まれると、全体が失敗する**。`psql -1 -c "VACUUM t"` は `ERROR:  VACUUM cannot run inside a transaction block` になった。`CREATE DATABASE` も同じ。
- **コマンドの中に `BEGIN`、`COMMIT`、`ROLLBACK` があると、期待どおりに動かない**。
- **対話モードでは使えない**。端末から `psql -1` で起動すると、`psql: error: -1 can only be used in non-interactive mode` になる。パイプで SQL を流し込んだ場合は、`-f -`（標準入力をファイルとして読む）と同じ扱いになるので使える。

psql の「single」が付くオプションは3つある。

| オプション | 名前 | 意味 |
| --- | --- | --- |
| `-s` | single-step | 1文ずつ確認しながら実行する |
| `-S` | single-line | 改行で SQL の終わりとみなす |
| `-1` | single-transaction | すべてを1つのトランザクションにまとめる |

#### メタコマンド

`\` で始まる、psql 自身が解釈するコマンド。SQL ではない。

| メタコマンド | 内容 |
| --- | --- |
| `\l` | データベースの一覧 |
| `\c` / `\connect` | 接続先を切り替える |
| `\d` | テーブル、ビュー、シーケンスの一覧。`\d テーブル名` で列の定義 |
| `\dt` | テーブルの一覧 |
| `\di` / `\dv` / `\dn` / `\df` | インデックス / ビュー / スキーマ / 関数の一覧 |
| `\du` / `\dg` | ロール（ユーザー）の一覧。今はどちらも同じ |
| `\drg` | ロールの所属関係（PG16 で追加） |
| `\x` | 拡張表示の切り替え |
| `\timing` | 実行時間の表示の切り替え |
| `\conninfo` | 現在の接続情報 |
| `\copy` | クライアント側でファイルとやり取りする COPY |
| `\i` | ファイルを読み込んで実行する |
| `\?` | メタコマンドのヘルプ |
| `\h` | SQL の構文のヘルプ（`\h CREATE TABLE` など） |
| `\q` | 終了する |
| `\!` | OS のコマンドを実行する（`\! createdb mydb` など） |

実機での出力例:

```text
=> \du
                             List of roles
 Role name |                         Attributes
-----------+------------------------------------------------------------
 postgres  | Superuser, Create role, Create DB, Replication, Bypass RLS

=> \d demo_tools
             Table "public.demo_tools"
 Column |  Type   | Collation | Nullable | Default
--------+---------+-----------+----------+---------
 id     | integer |           | not null |
 name   | text    |           | not null |
Indexes:
    "demo_tools_pkey" PRIMARY KEY, btree (id)

=> \x on
Expanded display is on.
=> SELECT 1 AS a, 'two' AS b;
-[ RECORD 1 ]
a | 1
b | two

=> \timing on
Timing is on.
=> SELECT count(*) FROM pg_class;
 count
-------
   419
Time: 0.177 ms
```

`\copy` と `COPY` の違いは [S2.4](2-4-バックアップ方法.md) で扱う。`\copy` はクライアント側のファイルを読み書きし、`COPY` はサーバー側のファイルを読み書きする。

#### \du と \dg

名前の由来は違うが、**今の PostgreSQL では同じコマンド**である。公式ドキュメントには、`\du` と `\dg` のどちらの説明にも次のように書かれている。

> データベースのロールを一覧表示する。（「ユーザー」と「グループ」という概念は「ロール」に統合されたため、このコマンドは今では `\dg`（`\du`）と同じである。）

昔の PostgreSQL ではユーザーとグループが別々にあり、`\du` はユーザー（users）、`\dg` はグループ（groups）の一覧だった。ロールに統合されたあとは、どちらもロールの一覧を表示する。

ログインできる `alice` と、ログインできない（グループ代わりの）`staff` を作って比べた結果:

```text
### \du
 Role name |                         Attributes
-----------+------------------------------------------------------------
 alice     |
 postgres  | Superuser, Create role, Create DB, Replication, Bypass RLS
 staff     | Cannot login

### \dg
（まったく同じ出力。diff で比べても差分はなかった）
```

`\du` でもグループ代わりの `staff` が表示され、`\dg` でもユーザー代わりの `alice` が表示される。今の「ユーザー」と「グループ」の違いは、ログインできるかどうか（`LOGIN` 属性）の違いにすぎない（詳しくは [S2.5](2-5-基本的な運用管理作業.md) で扱う）。

| 書き方 | 意味 |
| --- | --- |
| `\du` / `\dg` | ユーザーが作ったロールだけを表示する |
| `\duS` | 組み込みのロール（`pg_` で始まるもの）も表示する |
| `\du+` | ロールのコメントも表示する |
| `\du パターン` | 名前がパターンに合うロールだけを表示する |

ロールの所属関係は、PG16 で追加された `\drg` で表示する。

```text
 Role name | Member of |   Options    | Grantor
-----------+-----------+--------------+----------
 alice     | staff     | INHERIT, SET | postgres
```

試験では、言葉の揺れに惑わされないように次のように答える。

| 問われ方 | 答え |
| --- | --- |
| ユーザーの一覧を表示するメタコマンドは？ | `\du`（名前の由来どおり） |
| グループの一覧を表示するメタコマンドは？ | `\dg` |
| `\du` の説明は？ | 「ユーザーの一覧」「ロールの一覧」どちらでも正しい |
| `\du` と `\dg` の違いは？ | 今は同じ（ロールに統合されたため） |

入力問題で「ユーザーの一覧を表示するメタコマンド」と問われたら、`\dg` でも実際には動くが、出題者が期待しているのは `\du` である。頭文字の `u`（users）と `g`（groups）で覚える。

#### 今のデータベースを確かめる

今どのデータベースに接続しているかは、次の4つの方法で確かめられる。

| 方法 | 種類 | 実機の結果 |
| --- | --- | --- |
| プロンプトを見る | 見るだけ | `postgres=#` の `postgres` の部分 |
| `\conninfo` | メタコマンド | 接続情報の表の `Database` の行 |
| `\echo :DBNAME` | メタコマンド（psql の変数を表示する） | `postgres` |
| `SELECT current_database();` | SQL | `postgres` |

`hoge` データベースを作り、`\c` で切り替えてから `\conninfo` を実行した結果:

```text
postgres=# \c hoge
You are now connected to database "hoge" as user "postgres".
hoge=# \conninfo
           Connection Information
      Parameter       |        Value
----------------------+---------------------
 Database             | hoge                   ← 今のデータベース
 Client User          | postgres               ← 接続しているユーザー
 Socket Directory     | /var/run/postgresql    ← Unix ドメインソケットで接続中
 Server Port          | 5432
 Options              |
 Protocol Version     | 3.0
 Password Used        | false
 GSSAPI Authenticated | false
 Backend PID          | 490731
 SSL Connection       | false
 Superuser            | on
 Hot Standby          | off
```

プロンプトも `postgres=#` から `hoge=#` に変わっている。`\conninfo` は、データベース名だけでなく、誰として、どうやって接続しているかまで一度にわかる。

使い分け:

- psql で手早く確かめるなら、プロンプトか `\conninfo`。
- アプリケーションのコードから確かめるなら、`SELECT current_database();`。SQL なので、psql 以外のクライアントでも使える（MySQL の `SELECT DATABASE();` にあたる）。

#### MySQL との対応

| やりたいこと | MySQL | PostgreSQL（psql） |
| --- | --- | --- |
| データベースの一覧 | `SHOW DATABASES;` | `\l` |
| データベースを切り替える | `USE hoge;` | `\c hoge` |
| テーブルの一覧 | `SHOW TABLES;` | `\dt` |
| テーブルの定義 | `DESCRIBE hoge;` | `\d hoge` |
| 今のデータベース名 | `SELECT DATABASE();` | `SELECT current_database();` |

MySQL の書き方をそのまま打つと、エラーになる。

```text
SHOW DATABASES;  → ERROR:  unrecognized configuration parameter "databases"
USE mydb;        → ERROR:  syntax error at or near "USE"
```

1つ目のエラーは、**PostgreSQL の `SHOW` が設定パラメータを表示するコマンド**だから起きる（`SHOW port` など。[S2.3](2-3-設定ファイル.md) を参照）。`databases` という設定パラメータを探しに行って、見つからなかった。

#### \c は「切り替え」ではなく「接続し直し」

MySQL の `USE` は同じ接続のまま既定のデータベースを切り替えるが、psql の `\c` は**今の接続を閉じて、別のデータベースに新しく接続し直す**。接続ごとにバックエンドプロセスが作られるので、`\c` の前後でプロセス ID が変わる。

```text
### 切り替える前
 current_database | pg_backend_pid
------------------+----------------
 postgres         |         483177

You are now connected to database "mydb" as user "postgres".

### \c mydb で切り替えたあと
 current_database | pg_backend_pid
------------------+----------------
 mydb             |         483178     ← プロセスが変わった
```

PostgreSQL では**1つの接続は1つのデータベースにしか繋がらない**。そのため、別のデータベースのテーブルを SQL で直接参照することもできない。

```text
mydb から postgres のテーブルを参照 → ERROR:  cross-database references are not implemented
```

MySQL の「データベース」は、PostgreSQL の「スキーマ」に近い（詳しくは [S3.1 の 04 DBオブジェクト](../s3-開発SQL/3-1-SQLコマンド/04-DBオブジェクト.md)）。

#### 接続するときにデータベースを選ぶ

psql の外には「データベースを切り替える」という操作はない。**接続するときにデータベースを選ぶ**。

| 書き方 | 接続されたデータベース（実機で確認） |
| --- | --- |
| `psql`（何も指定しない） | `postgres`（ロール名と同じ名前） |
| `psql -d switchdemo` | `switchdemo` |
| `psql switchdemo`（最初の引数で指定） | `switchdemo` |
| `PGDATABASE=switchdemo psql`（環境変数） | `switchdemo` |
| `psql "dbname=switchdemo"`（接続文字列） | `switchdemo` |
| `psql postgresql:///switchdemo?host=/var/run/postgresql`（URI） | `switchdemo` |

公式ドキュメントでは、psql の書式は `psql [option...] [dbname [username]]` で、「`-d` は、最初の引数にデータベース名を書くのと同じ」と説明されている。

##### 省略したときの既定値

接続先を何も指定しないと、次の値が使われる（公式ドキュメント psql）。オプションがなければ環境変数を見て、環境変数もなければ既定値になる。

| 省略したもの | 環境変数 | 既定値 |
| --- | --- | --- |
| `-h`（ホスト） | `PGHOST` | 同じマシンの **Unix ドメインソケット**（Windows では TCP/IP の `localhost`） |
| `-p`（ポート） | `PGPORT` | **5432**（コンパイル時に決まる値。サーバーの既定値と同じなので、普通は指定しなくてよい） |
| `-U`（ユーザー） | `PGUSER` | **OS のユーザー名** |
| `-d`（データベース） | `PGDATABASE` | **ユーザー名と同じ名前** |

サーバー側のポートの既定値も 5432 である（db の `pg_settings` で `boot_val` が `5432`。[S2.3](2-3-設定ファイル.md) の「リモートから接続するために必要な2つの設定」を参照）。Unix ドメインソケットで接続するときもポート番号は使われ、ソケットのファイル名が `.s.PGSQL.5432` になる。

##### 引数の順番（データベース名、ユーザー名）

オプションのあとの**1つ目の引数がデータベース名、2つ目の引数がユーザー名**になる。オプションと引数が混ざって並ぶので、読み間違えやすい。

```text
psql -f test.sql   testdb   postgres
     └─────────┘   └────┘   └──────┘
     オプション     1つ目の引数 2つ目の引数
     （ファイル）   ＝データベース ＝ユーザー名
```

`SELECT current_database(), current_user;` を書いた `test.sql` で確かめた結果:

| コマンド | 接続先 / ユーザー |
| --- | --- |
| `psql -f test.sql testdb postgres` | `testdb` / `postgres` |
| `psql -U postgres testdb < test.sql` | `testdb` / `postgres`（上と同じ結果） |
| `psql -f test.sql testdb alice`（2つ目の引数を変えた） | `testdb` / `alice` |
| `psql -f test.sql postgres testdb`（順番を逆にした） | `FATAL:  role "testdb" does not exist` |

順番を逆にすると、`testdb` をユーザー名として扱い、そのロールを探しに行ってエラーになった。

「testdb の中の postgres ユーザー」と読むのは誤り。ロールはデータベースに属するものではなく、クラスタ全体で共有される（[S2.1](2-1-インストール方法.md) で見たとおり、ロールの一覧 `pg_authid` は `global/` にある）。正しくは「**testdb に、postgres というロールで接続する**」と読む。

迷ったら、`-d` と `-U` に書き直して読む。

| 元の書き方 | オプションで書き直すと |
| --- | --- |
| `psql -f test.sql testdb postgres` | `psql -f test.sql -d testdb -U postgres` |
| `psql -U postgres testdb < test.sql` | `psql -U postgres -d testdb < test.sql` |

どちらも「testdb に postgres で接続して、test.sql を実行する」という同じ意味になる。違いは、ファイルを `-f` で渡すか、シェルのリダイレクト（`<`）で渡すかだけ。

psql の中の `\c` も、公式ドキュメントでは次のように説明されている。

> PostgreSQL サーバーへの新しい接続を確立する。新しい接続に成功すると、前の接続は閉じられる。ただし、接続に失敗した場合（ユーザー名の誤り、アクセスの拒否など）、対話モードなら前の接続が残る。

存在しないデータベースに `\c` して、実際に確かめた結果:

```text
### 対話モード
postgres=# \c nosuchdb
connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  database "nosuchdb" does not exist
Previous connection kept                    ← 前の接続が残った
postgres=# SELECT current_database();
 postgres

### スクリプト（対話モードでない）
\connect: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  database "nosuchdb" does not exist
（次の SELECT は実行されずに終わった）
```

つまり、psql の中でも外でも、やっていることは「新しく接続する」ことだけである。

アプリケーションから使う場合も同じで、接続文字列でデータベースを選ぶ。

```text
postgresql://user:password@localhost:5432/mydb
                                          └──┘
                                          接続するデータベース
```

別のデータベースを使いたいときは、接続先を変えた新しい接続（クライアントや接続プール）を作る。SQL には、MySQL の `USE` にあたる命令がない。

#### 円記号（¥）とバックスラッシュ（\）は別の文字

日本語配列の Mac では、`¥` キーを押すと円記号（`¥`、U+00A5）が入力されることがある。見た目は似ていても、psql のメタコマンドに使うバックスラッシュ（`\`、U+005C）とは**別の文字**である。

```text
¥l  → ERROR:  syntax error at or near "¥l"   ← メタコマンドではなく SQL として解釈された
\l  → データベースの一覧が表示される
```

対処法:

- `Option` + `¥` でバックスラッシュを入力する
- キーボードの入力ソース（日本語）の設定で、「`¥` キーで入力する文字」を「`\`（バックスラッシュ）」に変える。変えたあとは `Option` + `¥` で円記号になる

なお、公式サイトの出題範囲で `\copy` が `¥copy` と書かれているのは、日本語の環境では `\` が `¥` のように表示されることがあるため（[S2.4](2-4-バックアップ方法.md) を参照）。

### pg_config

インストールされた PostgreSQL の情報を表示する。

```sh
pg_config --version --bindir --sharedir
```

```text
PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2)
/usr/lib/postgresql/18/bin
/usr/share/postgresql/18
```

オプションを付けずに実行すると、すべての項目が表示される（db で確認。一部を抜粋）。

```text
BINDIR = /usr/lib/postgresql/18/bin        ← コマンドが置いてある場所
SHAREDIR = /usr/share/postgresql/18
INCLUDEDIR = /usr/include/postgresql       ← C のヘッダファイルの場所
PKGLIBDIR = /usr/lib/postgresql/18/lib     ← 拡張機能などのライブラリの場所
CONFIGURE =  '--build=aarch64-linux-gnu' '--prefix=/usr' ...   ← ビルドしたときのオプション
CC = gcc
VERSION = PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2)
```

バージョンは項目の1つにすぎない。名前の「config」は、ソースからビルドするときの `configure` のことで、実行時の設定のことではない。公式ドキュメントには「PostgreSQL と連携するソフトウェアが、必要なヘッダファイルやライブラリを見つけるために使う」とある。

#### pg_config と pg_settings の違い

| | `pg_config` | `pg_settings` |
| --- | --- | --- |
| 種類 | OS のコマンド | システムビュー |
| 見られるもの | **インストールの情報**（ディレクトリ、ビルドのオプション、バージョン） | **動いているサーバーの設定値**（`work_mem`、`port` など。PG18.6 で 399 個） |
| いつ決まるか | ビルドしたとき。あとから変わらない | 設定ファイルや `SET` で、あとから変えられる |
| サーバーが動いている必要 | ない | ある（接続して見る） |

Node.js で例えると、`pg_settings` はアプリが今読み込んでいる設定、`pg_config` は `node -p process.config`（Node.js 自体をビルドしたときのオプション）に近い。

**`pg_config` という名前のシステムビューもある。** 中身はコマンドの `pg_config` と同じ情報で、SQL で読める（db では 23 行）。公式ドキュメントには「既定では、スーパーユーザーしか読めない」とある。

| 名前 | 種類 | 中身 |
| --- | --- | --- |
| `pg_config` | OS のコマンド | インストールの情報 |
| `pg_config` | システムビュー | 同じ情報を SQL で読む（既定ではスーパーユーザーのみ） |
| `pg_settings` | システムビュー | 実行時の設定値（[S2.3](2-3-設定ファイル.md) を参照） |
| `pg_controldata` | OS のコマンド | データベースクラスタの制御情報（次の節） |

バージョンだけを知りたいときは、次のどれでもよい。

| 方法 | 打つ場所 | 結果（db） |
| --- | --- | --- |
| `pg_config --version` | シェル | `PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2)` |
| `SHOW server_version;` | psql | `18.6 (Debian 18.6-1.pgdg13+2)` |
| `SELECT version();` | psql | `PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2) on aarch64-unknown-linux-gnu, compiled by gcc ...` |

### pg_controldata

クラスタの制御情報（`pg_control` ファイルの内容）を表示する。**サーバーが停止していても実行できる**ので、クラスタの状態を調べるのに使う。

```sh
pg_controldata -D ~/s22
```

```text
pg_control version number:            1800
Catalog version number:               202506291
Database cluster state:               shut down
Data page checksum version:           1
```

`Database cluster state` の主な値:

| 値 | 意味 |
| --- | --- |
| `in production` | 起動中（または異常終了してそのまま残った状態） |
| `shut down` | 正常に停止した |
| `in archive recovery` | リカバリ中 |

### pg_isready

サーバーが接続を受け付けているかを確認する。**終了コードで結果を判断する**ので、監視スクリプトや起動待ちの処理に向いている（[環境構築](../../../docs/01-環境構築.md)の healthcheck でも使っている）。

| 終了コード | 意味 |
| ---: | --- |
| 0 | 接続を正常に受け付けている |
| 1 | 接続を拒否している（起動処理中など） |
| 2 | 応答がなかった |
| 3 | 接続を試みなかった（パラメータが不正など） |

#### 終了コードの見方

終了コードは**画面には表示されない**。表示されるメッセージは人間向けで、終了コードはスクリプトやプログラム向けである。

| 出てくるもの | 誰のためのものか | 見え方 |
| --- | --- | --- |
| メッセージ（`accepting connections` など） | 人間 | 画面に表示される |
| 終了コード（0 / 1 / 2 / 3） | スクリプトやプログラム | 表示されない。**直後に `echo $?`** で確認する |

```text
$ pg_isready
/var/run/postgresql:5432 - accepting connections
$ echo $?
0

$ pg_isready -p 5433
/var/run/postgresql:5433 - no response
$ echo $?
2
```

**`$?` は直前のコマンドの終了コード**なので、間に別のコマンドを挟むと上書きされる。

```text
$ pg_isready -q -p 5433; ls > /dev/null; echo $?
0      ← pg_isready の 2 ではなく、ls の 0
```

#### -q でメッセージを出さない

`-q`（`--quiet`）を付けると、メッセージを出さずに終了コードだけを返す。スクリプトで使うときに便利。

```text
$ pg_isready -q -p 5433           （何も表示されない。終了コードは 2）
$ pg_isready -q -p 5433 && echo "起動している" || echo "起動していない"
起動していない
```

#### healthcheck での使われ方

この学習環境の `compose.yaml` の healthcheck でも `pg_isready` を使っている。

```yaml
healthcheck:
  test: ["CMD", "pg_isready", "-h", "127.0.0.1", "-U", "postgres"]
```

Docker はメッセージではなく、**終了コードが 0 かどうか**で healthy かどうかを判定する。TypeScript の世界でいえば、CI で `npm test` の終了コードが 0 でなければ失敗扱いになるのと同じ仕組み。

`pg_ctl status`（停止中は 3）も同じ考え方で、PostgreSQL のコマンドには、状態を終了コードで返すものが多い。

### pg_resetwal

**WAL を消去して、`pg_control` の制御情報を初期化する**コマンド。ファイルが壊れてサーバーが起動しなくなったときの、**最後の手段**として使う。

公式ドキュメントの警告:

- 「それ以外の用途で使うのは危険であり、細心の注意を払う必要がある」
- 実行後はサーバーを起動できるようになるかもしれないが、**中途半端にコミットされたトランザクションのせいでデータが矛盾している可能性がある**。すぐにダンプを取り、`initdb` でクラスタを作り直して、リストアすること
- ダンプを取る前に、データを変更する操作をしてはいけない

安全のための制約もある。**サーバーが起動しているときは実行できない**。

```text
$ pg_resetwal -D ~/s22
pg_resetwal: error: lock file "postmaster.pid" exists
pg_resetwal: hint: Is a server running?  If not, delete the lock file and try again.
  exit=1
```

- データディレクトリへの読み書きが必要なので、**サーバーをインストールしたユーザー（データディレクトリの所有者）でしか実行できない**。
- `-D` でデータディレクトリを明示的に指定する必要がある。
- `-f` / `--force` は、正常に停止していない場合など、危険な状況でも強行するためのオプション。

#### -n（--dry-run）で事前に確かめる

`-n`（長い形は `--dry-run`）を付けると、**何も変更せずに終了する**。公式ドキュメントでは次のように説明されている。

> `-n` / `--dry-run` を指定すると、`pg_resetwal` は `pg_control` から再構成した値と、変更される予定の値を表示し、何も変更せずに終了する。主にデバッグ用の機能だが、本当に実行する前の確認にも使える。

使い捨てのクラスタで、`-n` の前後と、`-n` なしで実行したあとの制御情報（`pg_controldata`）を比べた結果:

```text
$ pg_resetwal -n -D ~/rw
Current pg_control values:
  ...（今の制御情報が並ぶ）
Values to be changed:
First log segment after reset:        000000010000000000000002    ← 変更される予定の値
```

| | チェックポイントの位置 | REDO の WAL ファイル |
| --- | --- | --- |
| 実行前 | `0/1761588` | `000000010000000000000001` |
| **`-n` を付けて実行したあと** | **`0/1761588`（変わらない）** | **`000000010000000000000001`（変わらない）** |
| `-n` なしで実行したあと（`Write-ahead log reset` と表示された） | `0/2000028` | `000000010000000000000002` |

`-n` で「変更される予定」と表示された値は、実際に実行したあとの値と一致した。本番の前に、何が起きるかを確かめられる。

ただし、**`-n` を付けても、サーバーの起動中は実行できない**。

```text
（サーバーの起動中に pg_resetwal -n を実行）
pg_resetwal: error: lock file "postmaster.pid" exists
```

| オプション | 意味 |
| --- | --- |
| `-n` / `--dry-run` | 表示だけして、何も変更しない |
| `-f` / `--force` | 正常に停止していない場合など、危険な状況でも強行する |
| `-D` / `--pgdata` | データディレクトリ。安全のため、コマンドラインで明示する必要がある |

### 試験の観点

- `createuser` と `createdb` は **SQL のラッパー**。`-e` で実行される SQL が見える。
- `createuser` の既定は「スーパーユーザーではない、データベースを作れない、ロールを作れない、ログインできる」。
- **`pg_ctl` は、`-D` を省略しても、環境変数 `PGDATA` が設定されていれば実行できる**（`initdb` と同じ）。「`-D` でデータディレクトリを指定しないと実行できない」は誤り。エラーになるのは、`-D` も `PGDATA` もないときだけ。
- **設定の再読み込みは、`pg_ctl reload` のほかに、SQL の `SELECT pg_reload_conf();` でもできる**（既定ではスーパーユーザーのみ）。どちらも postmaster に SIGHUP を送る。
- **`pg_config` はインストールの情報（ディレクトリ、ビルドのオプション、バージョン）を表示する OS のコマンド**。実行時の設定値は、システムビューの `pg_settings` で見る。`pg_config` には同じ名前のシステムビューもある（既定ではスーパーユーザーのみ）。
- **`pg_` で始まる名前には、OS のコマンド、システムビュー、関数がある**。`pg_settings` はコマンドではなく、`SELECT ... FROM pg_settings` で読むビュー。
- **`pg_ctl restart` は、停止（既定は `fast`）してから起動する**。接続中のセッションは切れるが、`context` が `postmaster` の設定も反映できる。`reload` は SIGHUP を送るだけで接続は切れないが、反映できるのは `sighup` 以下の設定だけ。止まっているときに `restart` しても起動する。
- **pg_ctl のモード（サブコマンド）は、`start`、`stop`、`restart`、`reload`、`status`、`promote`、`logrotate`、`kill` など**。`-m` で指定する停止モード（`smart`、`fast`、`immediate`）とは別物。
- **`pg_ctl` の `-t` は、完了を待つ最大の秒数で、既定は 60 秒**（環境変数 `PGCTLTIMEOUT` で変えられる）。時間切れになると pg_ctl は 0 以外の終了コードで終わるが、サーバーの停止処理は裏で続く。強制的に止まるわけではない。
- **psql の接続先の既定値は、ホストが Unix ドメインソケット、ポートが 5432、ユーザーが OS のユーザー名、データベースがユーザー名と同じ名前**。環境変数 `PGHOST`、`PGPORT`、`PGUSER`、`PGDATABASE` で変えられる。
- **`pg_ctl stop` の既定の停止モードは `fast`**（9.4 までは `smart` だった）。`smart` はクライアントが自分から切断するまで待つので、接続が残っていると止まらない。`fast` は実行中のトランザクションをロールバックして切断する。`immediate` は正常な停止処理をしないので、次の起動時にリカバリが走る。`-m s`、`-m f`、`-m i` のように頭文字でも指定できる。
- **`pg_ctl status` は、停止中なら終了コード 3**。
- **`pg_isready` の終了コードは 0 / 1 / 2 / 3**。終了コードは画面に表示されないので、直後に `echo $?` で確認する。`-q` でメッセージを出さないようにできる。
- **`pg_resetwal` は最後の手段**。サーバー起動中は実行できず、実行後はダンプとリストアが必要。
- **`pg_resetwal -n`（`--dry-run`）は、変更される予定の値を表示するだけで、何も変更しない**。ただし `-n` を付けても、サーバーの起動中は実行できない。コマンド名は `pg_resetwal`（`reset` と `wal` の間にアンダースコアはない）。
- **`psql -s` はシングルステップ（毎回確認する）、`psql -S` はシングルライン（改行で SQL を終える）**。`-s` の意味はコマンドごとに違い、`pg_ctl -s` はサイレント、`createuser -s` はスーパーユーザー。
- **psql の中では SQL（`CREATE DATABASE`）、シェルでは OS のコマンド（`createdb`）を使う**。psql の中から OS のコマンドを実行するには `\!` を使う。
- **接続中のデータベースは削除できない**。ほかのセッションが接続していても失敗する。`DROP DATABASE ... WITH (FORCE)` や `dropdb --force` を使うと、接続を切って削除できる（PG13 で追加）。
- **今のデータベースは、プロンプト、`\conninfo`、`\echo :DBNAME`、`SELECT current_database();` で確かめられる**。`\conninfo` は現在の接続の情報を表示するメタコマンド。
- **`\du` と `\dg` は同じ**（どちらもロールの一覧）。問題文では「ユーザーの一覧」とも書かれる。ユーザーの一覧を問われたら `\du`、グループの一覧なら `\dg` と答える。試験の基準では、`\du` の「Member of」列で所属先がわかる（PG16 からは `\drg`）。
- **`createuser` の `-U` は接続に使うロール**（作るロールではない）。省略すると `PGUSER`、それもなければ OS のユーザーと同じ名前のロールで接続する。OS のユーザーと違うロールで接続できるかは、認証方式（`peer` か `trust` かなど）で決まる。
- **`-W` は接続のためのパスワード、`-P` は新しく作るロールのパスワード**の入力を求める。
- **`pg_ctl stop` は、データディレクトリの `postmaster.pid` からサーバーの PID を読み取って停止の合図を送る**。サーバーが動いていないと `PID file ... does not exist` というエラーになる。root では実行できない。
- **接続するデータベースは `-d` か最初の引数で指定する**。環境変数 `PGDATABASE`、接続文字列、URI でも指定できる。SQL には、データベースを切り替える命令はない。
- **`\c` は新しく接続し直すメタコマンド**。成功すると前の接続は閉じられ、対話モードで失敗した場合は前の接続が残る。
- **ファイルの SQL は、`psql データベース名 < ファイル名`（シェルのリダイレクト）、`-f`、`\i` で実行できる**。`-f` と `\i` は、エラーメッセージに行番号が付く。
- **既定では、エラーが起きても最後まで実行される**。止めたいときは `ON_ERROR_STOP` を設定する。止まったときの終了コードは 3。
- **psql の書式は `psql [オプション] [データベース名 [ユーザー名]]`**。引数が2つ並んでいたら、1つ目がデータベース名、2つ目がユーザー名。迷ったら `-d` と `-U` に書き直して読む。
- **`psql -1`（`--single-transaction`）は、`-c` と `-f` で渡したコマンドを `BEGIN` と `COMMIT` で包み、1つのトランザクションにする**。途中でエラーが起きると、すべて取り消される。対話モードでは使えない。`-1` は数字の「いち」で、`-l`（データベースの一覧）とは別物。
- **`createuser` のロール属性は、小文字が「付ける」、大文字が「付けない」**（`-s`/`-S`、`-d`/`-D`、`-r`/`-R`、`-l`/`-L`、`-i`/`-I`）。これは `createuser` だけの対応で、ほかのコマンドには当てはまらない。特に **`-W` は、`pg_ctl` では「待たない」、接続するコマンド（`psql` など）では「パスワードを必ず尋ねる」**。**`-D` は、`pg_ctl` と `initdb` ではデータディレクトリ、`createdb` ではテーブルスペース、`createuser` では「データベースを作れない」**。
- **オプションなしの `createuser` で作ったロールは、スーパーユーザーではなく、データベースもロールも作れず、ログインはできる**。実行した OS のユーザーや、接続に使ったロールの属性は引き継がない。`createuser` は OS のユーザーを作らない。
- **データベースを削除できるのは、所有者とスーパーユーザーだけ**（`dropdb` も同じ）。`CREATEDB` 権限を持っていても、ほかのロールが所有するデータベースは削除できない（`must be owner of database`）。
- **`pg_ctl kill シグナル名 PID` は、指定したプロセスにシグナルを送る**。主に Windows のためのモードで、`-D` ではなく PID を指定する。シグナル名は `HUP`、`INT`、`TERM` のように大文字で、`SIG` を付けない。postmaster に HUP を送ると設定の再読み込みになり、バックエンドプロセスに TERM を送ると、その接続だけが切断される。
- **テンプレートと違うエンコーディングのデータベースは、`createdb -T template0 -E エンコーディング` で作る**。`template1` からだとエラーになる。エンコーディングはロケールとも合っている必要があるので、必要ならロケールも指定する。
- Ver.3.0 の改定で `pg_config`、`pg_controldata`、`pg_isready`、`pg_resetwal` が出題範囲に追加された。

## ⚠️ 試験と最新版の違い

- **PG13**: `DROP DATABASE ... WITH (FORCE)` と `dropdb --force`（`-f`）が追加され、接続中のセッションを切断してデータベースを削除できるようになった。試験の基準（PG 12〜14）のうち、PG12 にはこの機能がない。
- **PG15**: psql の `-1`（`--single-transaction`）で途中にエラーが起きたとき、最後に送るコマンドが変わった。PG14 までは常に `ROLLBACK` を送っていたが、PG15 からは `ON_ERROR_STOP` を設定しているときだけ `ROLLBACK` を送り、設定していなければ `COMMIT` を送る（公式のリリースノート）。ただし、エラーで中断されたトランザクションは `COMMIT` しても確定しないので、**すべて取り消されるという結果はどのバージョンでも同じ**（PG18 で `ON_ERROR_STOP` なしで確認し、0行だった）。
- **PG18**: psql の `\conninfo` が表形式になり、表示される情報が増えた（公式のリリースノート）。試験の基準（PG 12〜14）では、表ではなく1行の文章で表示される。表示の形は違っても、「現在の接続の情報を表示するメタコマンド」という役割は同じ。
- **PG16**: ロールの所属関係を詳しく表示する `\drg` が追加され、`\du` と `\dg` の出力から「Member of」列が削除された（公式のリリースノート）。試験の基準（PG 12〜14）では、`\du` の「Member of」列でロールの所属先がわかる。
- **PG16**: `CREATEROLE` を持つロールでも、対象のロールに対する `ADMIN OPTION` がないと削除できなくなった（`dropuser` で確認。自分で作ったロールには自動で付く）。試験の基準（PG 12〜14）では、`CREATEROLE` があればスーパーユーザー以外のロールを削除できる。

- C. `reload` をすると、接続中のセッションは切れる

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | B | 既定は `fast`。クライアントの切断を待たず、実行中のトランザクションはロールバックされる |
| 2 | `pg_isready` | 0 は受付中、1 は拒否、2 は無応答、3 は試行せず |
| 3 | A、B、D、E | 既定ではデータベースを作成できない（`-d` を付けると作成可）ので C が誤り |
| 4 | C | 起動中は `postmaster.pid` があるため実行できない。データディレクトリの所有者が実行する |
| 5 | C | 停止中は 3、データディレクトリを特定できない場合は 4 |
| 6 | D | `\c` は接続先の切り替え。終了は `\q` |
| 7 | B | `createdb` は OS のシェルで実行するコマンドで、SQL ではない。psql の中で SQL として作るなら `CREATE DATABASE mydb;`（小文字の `create database mydb;` でも動く） |
| 8 | A | `-n` を付けても、サーバーの起動中は `postmaster.pid` があるので拒否される（C は誤り）。D は `-f`（`--force`）の説明 |
| 9 | `-n` | 長い形は `--dry-run`。危険な状況でも強行する `-f` と区別する |
| 10 | B | A は `-S`（大文字、シングルライン）の説明。C は `pg_ctl -s`、D は `createuser -s` と混同させる選択肢 |
| 11 | D | 大文字の `-S` はシングルラインモード（改行で SQL を終える）。シングルステップは小文字の `-s` |
| 12 | B | 終了コードは画面には表示されない。`$?` は直前のコマンドの終了コードなので、すぐに確認する |
| 13 | `-q` | 長い形は `--quiet`。スクリプトや healthcheck では、メッセージではなく終了コードで判定する |
| 14 | B | `ERROR: cannot drop the currently open database` になる。別のデータベースに接続してから実行する |
| 15 | `\!` | `\! createdb mydb` のように使う。実行されるのは psql を動かしているマシン |
| 16 | A、B、C | D は MySQL の書き方。PostgreSQL の `SHOW` は設定パラメータを表示するコマンドなので、`unrecognized configuration parameter "databases"` というエラーになる |
| 17 | `current_database` | `SELECT current_database();` のように使う。MySQL の `DATABASE()` にあたる |
| 18 | B | ユーザーとグループはロールに統合されたので、今はどちらも同じ。ログインできないロールも `\du` に表示される |
| 19 | `\du` | `\dg` でも同じ結果になるが、「ユーザーの一覧」なら名前の由来どおり `\du` と答える |
| 20 | B | `-U` は接続に使うロール。作るロールの名前は最後の引数に書く |
| 21 | B | `-W` は接続のためのパスワード、`-p` はポート番号、`-w` はパスワードの入力を求めない |
| 22 | A、B、D | `pg_ctl` は `initdb` と同じく、root では実行できない（`pg_ctl: cannot be run as root`） |
| 23 | A、B、C | D は MySQL の書き方。PostgreSQL の SQL には `USE` がないので、構文エラーになる |
| 24 | A | 対話モードでは前の接続が残る。スクリプトを実行している（対話モードでない）場合は、前の接続が閉じられてエラーになる |
| 25 | A | `<` はシェルのリダイレクト。B は `>`（出力のリダイレクト）と混同させる選択肢 |
| 26 | `ON_ERROR_STOP` | `psql -v ON_ERROR_STOP=1 -f sample.sql` のように指定する。既定ではエラーが起きても最後まで実行される |
| 27 | D | 0 は正常終了、1 は psql 自身の致命的なエラー、2 は対話モードでないときの接続の切断 |
| 28 | A | 1つ目の引数がデータベース名、2つ目の引数がユーザー名。ロールはデータベースに属さないので、C の「testdb の中の postgres ユーザー」は誤り |
| 29 | B | 引数の順番で意味が決まる。実機では、testdb というロールがないので `FATAL: role "testdb" does not exist` になった |
| 30 | A | B は `fast`、C は `immediate` の説明。既定は 9.5 から `fast`（9.4 までは `smart`） |
| 31 | A、B、D | `smart` で停止中は、新しい接続は `the database system is shutting down` というエラーで拒否される |
| 32 | `template0` | `template1` からは、エンコーディングもロケールも変えられない |
| 33 | B | `encoding "EUC_JP" does not match locale "en_US.utf8"` になる。`-l C` などでロケールも合わせる必要がある |
| 34 | `pg_ctl kill HUP 1172` | `pg_ctl reload` と同じ効果になる |
| 35 | B、D | A: `-D` は使わず、PID を直接指定する。C: `SIG` は付けない（`SIGTERM` と書くと `unrecognized signal name` になる） |
| 36 | A、B | 削除できるのは所有者とスーパーユーザーだけ。`CREATEDB` は作る権限で、C は `must be owner of database appdb` で失敗する |
| 37 | B | `-S`、`-D`、`-R`、`-L` はそれぞれ `--no-superuser`、`--no-createdb`、`--no-createrole`、`--no-login`。`createuser` の `-D` はデータディレクトリではない |
| 38 | A、B | C: `createuser -W` は接続に使うパスワードを尋ねるオプションで、新しいロールのパスワードは `-P`。D: 「待たない」のは `pg_ctl` だけ |
| 39 | `-1` | 長い形は `--single-transaction`。数字の「いち」で、`-l`（エル）ではない |
| 40 | A、C | B: 対話モードでは `-1 can only be used in non-interactive mode` になる。D: それは `-l`（エル） |
| 41 | B、D | オプションなしなら `NOSUPERUSER NOCREATEDB NOCREATEROLE INHERIT LOGIN`。接続に使ったロールの属性は引き継がない（A）。`createuser` は PostgreSQL のロールを作るだけで、OS のユーザーは作らない（C） |
| 42 | B、C、D | `-D` がなくても `PGDATA` があれば実行できるので、A は誤り。C と D も、postmaster に SIGHUP を送る点で `pg_ctl reload` と同じ |
| 43 | A、C、D | `-t` は pg_ctl が待つのをやめる時間で、停止モードは切り替わらない（B は誤り）。既定は 60 秒（`PGCTLTIMEOUT` がなければ） |
| 44 | 5432 | ユーザーは alice（OS のユーザー名）、データベースも alice（ユーザー名と同じ）、ホストは Unix ドメインソケットになる |
| 45 | A、B、D | `fast` は `-m` で指定する停止モードで、`pg_ctl stop -m fast` のように使う。モード（サブコマンド）ではない |
| 46 | A、B、D | 実行時の設定値は `pg_config` ではなく、システムビューの `pg_settings` で見る |
| 47 | A、C | `pg_settings` はシステムビュー（`SELECT ... FROM pg_settings`）、`pg_reload_conf()` は SQL の関数 |
| 48 | A、B、D | `reload` は SIGHUP を送って設定ファイルを読み直させるだけで、接続は切れない（C は誤り）。`listen_addresses` は `context` が `postmaster` |
