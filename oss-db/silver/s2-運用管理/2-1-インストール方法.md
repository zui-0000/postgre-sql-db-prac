## 学習メモ

### データベースクラスタとは

公式ドキュメントの定義は次のとおり。

> データベースクラスタとは、1つの稼働中のデータベースサーバーインスタンスによって管理される、データベースの集まりである。

ファイルシステムから見ると、**データが格納される1つのディレクトリ**であり、これを**データディレクトリ**（データ領域）と呼ぶ。

- **`PGDATA`** は、そのデータディレクトリの場所を指す環境変数。`initdb -D` で指定する場所と同じものを指す。
- サーバー（`postgres`）も同じ `PGDATA` を見てデータディレクトリを見つける。そのため `-D` を毎回書く代わりに `PGDATA` を設定しておく使い方ができる。
- 「1つのサーバー = 1つのクラスタ = 1つのディレクトリ」であり、その中に複数のデータベースが入る。同じマシンで複数のクラスタを動かすなら、ディレクトリもポートも分ける（[S2.3](2-3-設定ファイル.md) の「待ち受けるポートは1つだけ」を参照）。

#### 論理的な見方と物理的な見方

2つの定義がどう対応しているかは、実機で確かめられる。

```sql
SELECT oid, datname FROM pg_database ORDER BY oid;
```

```text
 oid |  datname
-----+-----------
   1 | template1
   4 | template0
   5 | postgres
```

```sh
ls $PGDATA/base
```

```text
1
4
5
```

データベースの OID と、`base/` の下のディレクトリ名が一致している。**データベース1つが、`base/` の下のサブディレクトリ1つに対応する**。

```text
データベースクラスタ ＝ データディレクトリ（/var/lib/postgresql/18/docker）
├── base/
│   ├── 1/   ← template1
│   ├── 4/   ← template0
│   └── 5/   ← postgres
├── global/  ← クラスタ全体で共有するもの
├── pg_wal/
└── ...
```

ただしクラスタは「データベースの集まり」だけではない。どのデータベースにも属さず、**クラスタ全体で共有されるもの**もある。テーブルの実体ファイルの場所を調べると分かる。

```sql
SELECT relname, pg_relation_filepath(oid) AS filepath, relisshared
FROM pg_class
WHERE relname IN ('pg_database', 'pg_authid', 'pg_class')
ORDER BY relname;
```

```text
   relname   |  filepath   | relisshared
-------------+-------------+-------------
 pg_authid   | global/1260 | t      ← ロールの一覧
 pg_class    | base/5/1259 | f      ← テーブルの一覧（データベースごと）
 pg_database | global/1262 | t      ← データベースの一覧
```

- `pg_database`（データベースの一覧）と `pg_authid`（ロールの一覧）は `global/` にあり、`relisshared` が `t` になっている。
- `pg_class`（テーブルの一覧）は `base/5/`、つまり postgres データベースの中にある。

つまり、**ロールはデータベースごとではなく、クラスタ全体で共有される**。1回 `CREATE ROLE` すれば、同じクラスタのどのデータベースにも同じロールで接続できる。一方、テーブルはデータベースごとに別々である。

#### 「1つのディレクトリ」の例外

| 例外 | 内容 |
| --- | --- |
| テーブルスペース | テーブルを別の場所に置ける。データディレクトリの `pg_tblspc/` には、その場所へのシンボリックリンクが入る |
| `initdb -X`（`--waldir`） | WAL だけを別のディレクトリに置ける |

それでも、入口が1つのデータディレクトリであることは変わらない。

#### 「クラスタ」という言葉の注意

「クラスタ」は、複数のサーバーを束ねた構成（Kubernetes のクラスタなど）を指すことが多い。しかし **PostgreSQL のデータベースクラスタは、1台のサーバーの中の話**である。公式の用語集にも「クラスタという言葉は、インスタンスの意味で使われることもある」と書かれている。

### initdb を実行する

データディレクトリは、使う前に `initdb` で初期化する必要がある。

```sh
docker compose exec sandbox bash
initdb -D ~/s21 -E UTF8 --locale=C
```

#### initdb がやること、やらないこと

`initdb` がやるのは**データベースクラスタの初期化**で、PostgreSQL が動くための土台を作ることである。

| やること | やらないこと |
| --- | --- |
| データディレクトリを作る | サーバーを起動する（`pg_ctl start` で行う） |
| システムカタログ（PostgreSQL 自身が使う管理用のテーブル）を作る | アプリケーション用のロールやデータベースを作る（起動後に `CREATE ROLE`、`CREATE DATABASE` で行う） |
| 設定ファイル（`postgresql.conf`、`pg_hba.conf` など）を作る | |
| `postgres`、`template1`、`template0` の3つのデータベースを作る | |

```text
インストール
   ↓
initdb            ← クラスタ（土台）を作る
   ↓
pg_ctl start      ← サーバーを起動する
   ↓
CREATE ROLE / CREATE DATABASE   ← アプリケーション用のロールとデータベースを作る
   ↓
アプリケーションが接続する
```

`git init` に近い。リポジトリの器と初期構造（`.git`）は作ってくれるが、中身のコミットは自分で積んでいく。

Docker の公式イメージでは、初回起動時にエントリポイントが `initdb` を自動で実行する（[環境構築](../../../docs/01-環境構築.md)を参照）。そのため Docker で PostgreSQL を使っていると、`initdb` を自分で実行する機会がない。

#### root では実行できない

```text
initdb: error: cannot be run as root
initdb: hint: Please log in (using, e.g., "su") as the (unprivileged) user that will own the server process.
```

サーバープロセスを所有するユーザーで実行する必要がある。**サーバーは root では動かせないので、`initdb` も root では実行できない**（実行しようとすると拒否される）。

#### 既存のディレクトリには実行できない

すでにファイルがあるディレクトリを指定すると、上書きを防ぐために拒否される（終了コードは 1）。

```text
initdb: error: directory "/var/lib/postgresql/s21" exists but is not empty
initdb: hint: If you want to create a new database system, either remove or empty the directory ...
```

#### 認証方式の警告

オプションを付けずに実行すると、ローカル接続が `trust` 認証（パスワードなしで接続できる）になり、警告が出る。

```text
initdb: warning: enabling "trust" authentication for local connections
initdb: hint: You can change this by editing pg_hba.conf or using the option -A, or --auth-local and --auth-host, the next time you run initdb.
```

#### 主なオプション

| オプション | 意味 |
| --- | --- |
| `-D` / `--pgdata` | データディレクトリの場所。**`initdb` に必須の情報**だが、`PGDATA` 環境変数で代用できる |
| `-E` / `--encoding` | テンプレートデータベースの文字エンコーディング。以降に作るデータベースの既定値にもなる |
| `--locale` | クラスタの既定のロケール。指定しないと `initdb` を実行した環境から引き継ぐ |
| `--lc-collate`、`--lc-ctype`、`--lc-messages` など | ロケールをカテゴリ単位で指定する |
| `-U` / `--username` | 作成するスーパーユーザーの名前。既定は `initdb` を実行した OS ユーザー名 |
| `-W` / `--pwprompt` | スーパーユーザーのパスワードを対話的に入力する |
| `-A` / `--auth` | `pg_hba.conf` に書かれる既定の認証方式（`host` と `local` の両方） |
| `--auth-host` / `--auth-local` | TCP/IP 接続用（`host`）、Unix ドメインソケット用（`local`）に分けて認証方式を指定する |
| `-k` / `--data-checksums` | データページのチェックサムを有効にする |
| `--no-data-checksums` | チェックサムを無効にする（PG18 で追加） |
| `-X` / `--waldir` | WAL（先行書き込みログ）を別のディレクトリに置く |

#### オプションを省略したときの既定値

オプションを省略すると、多くの設定は**実行環境（環境変数や OS のユーザー）から**決まる。ただし、`initdb` がシステムで試して選ぶものや、環境に関係なく固定で決まるものもある。

| 決まり方 | 項目 | sandbox で決まった値 |
| --- | --- | --- |
| **実行環境から** | ロケール（環境変数 `LC_ALL`、`LC_*`、`LANG` の順に見る。どれもなければ `C`） | `en_US.utf8`（`LANG` から） |
| | エンコーディング（ロケールから決まる） | `UTF8` |
| | 全文検索の既定の設定（ロケールから決まる） | `english` |
| | タイムゾーン（OS の設定。環境変数 `TZ` があればそれ） | `Etc/UTC` |
| | スーパーユーザーの名前（`initdb` を実行した OS ユーザー） | `postgres` |
| | データディレクトリ（環境変数 `PGDATA`） | `/var/lib/postgresql/18/docker` |
| **システムで試して選ぶ** | `max_connections`、`shared_buffers`、動的共有メモリの方式 | `100`、`128MB`、`posix` |
| **環境に関係なく固定** | 認証方式 | `trust`（警告が出る） |
| | データチェックサム | 有効（PG18 の既定） |
| | WAL の置き場所 | データディレクトリの中の `pg_wal/` |

オプションなしで実行したときの出力（抜粋）:

```text
The files belonging to this database system will be owned by user "postgres".
The database cluster will be initialized with locale "en_US.utf8".
The default database encoding has accordingly been set to "UTF8".
The default text search configuration will be set to "english".

selecting dynamic shared memory implementation ... posix
selecting default "max_connections" ... 100
selecting default "shared_buffers" ... 128MB
selecting default time zone ... Etc/UTC
```

選ばれた値は、生成された `postgresql.conf` に書き込まれる。

```text
max_connections = 100
shared_buffers = 128MB
dynamic_shared_memory_type = posix
log_timezone = 'Etc/UTC'
datestyle = 'iso, mdy'
timezone = 'Etc/UTC'
lc_messages = 'en_US.utf8'
lc_monetary = 'en_US.utf8'
lc_numeric = 'en_US.utf8'
lc_time = 'en_US.utf8'
default_text_search_config = 'pg_catalog.english'
```

環境変数を変えて実行すると、結果も変わる。

```text
$ LANG=C TZ=Asia/Tokyo initdb -D ~/v2
The database cluster will be initialized with locale "C".
The default database encoding has accordingly been set to "SQL_ASCII".   ← 注意
...
timezone = 'Asia/Tokyo'
```

`-D` も `PGDATA` もない場合は、データディレクトリが決まらないのでエラーになる。

```text
initdb: error: no data directory specified
initdb: hint: You must identify the directory where the data for this database system will reside.  Do this with either the invocation option -D or the environment variable PGDATA.
```

sandbox では Docker の公式イメージが `PGDATA=/var/lib/postgresql/18/docker` を設定しているので、`-D` を省略するとそこにクラスタが作られる。

#### C ロケールでは -E を忘れない

上の結果のとおり、**`C` ロケールで `-E` を省略すると、エンコーディングが `SQL_ASCII` になる**。`SQL_ASCII` は格納するデータのエンコーディングを検証しないので、日本語のような非 ASCII の文字を扱うなら使うべきではない（公式ドキュメント）。`C` ロケールを使うときは、エンコーディングを明示する。

```sh
initdb -D ~/mycluster --no-locale -E UTF8   # --no-locale は --locale=C と同じ意味
```

### エンコーディングとロケール

「日本語を使えるか」という話には、2つの別々の設定が関係する。

| | エンコーディング | ロケール |
| --- | --- | --- |
| 決めること | 文字をどうバイト列にするか | 並び順、文字の分類（大文字・小文字など）、メッセージの言語、数値や日付の書式 |
| 日本語との関係 | **日本語を保存できるかどうかはこちら** | 日本語の保存には関係ない |
| 指定方法 | `initdb -E`、`CREATE DATABASE ... ENCODING` | `initdb --locale`、`CREATE DATABASE ... LOCALE` |

エンコーディングが `UTF8` なら、ロケールが `en_US.utf8` のままでも日本語は問題なく保存できる。

#### ロケールのカテゴリ

| カテゴリ | 意味 | 変更 |
| --- | --- | --- |
| `LC_COLLATE` | 文字列の並び順 | **データベースの作成時に固定** |
| `LC_CTYPE` | 文字の分類（何が文字か、大文字は何か） | **データベースの作成時に固定** |
| `LC_MESSAGES` | メッセージの言語 | 設定ファイルで変更できる |
| `LC_MONETARY` | 通貨の書式 | 設定ファイルで変更できる |
| `LC_NUMERIC` | 数値の書式 | 設定ファイルで変更できる |
| `LC_TIME` | 日付と時刻の書式 | 設定ファイルで変更できる |

`LC_COLLATE` と `LC_CTYPE` が固定されるのは、インデックスの並び順に影響するため。あとから変えると、テキスト列のインデックスが壊れてしまう。

#### 日本語のロケールにできるか

| 方法 | この環境で使えるか |
| --- | --- |
| OS の `ja_JP.UTF-8` | **×** コンテナの OS に入っていない（`locale -a` の結果は `C`、`C.utf8`、`en_US.utf8`、`POSIX` だけ）。使うにはイメージを拡張する必要がある |
| ICU の `ja-JP` | **○** OS のロケールがなくても使える（`ja-x-icu`、`ja-JP-x-icu` が用意されている） |

ICU の日本語ロケールで、データベースを作れた。

```sql
CREATE DATABASE ja_db TEMPLATE template0 LOCALE_PROVIDER icu ICU_LOCALE 'ja-JP' LOCALE 'C';
```

```text
 Name  | Encoding | Locale Provider | Collate | Ctype | Locale
-------+----------+-----------------+---------+-------+--------
 ja_db | UTF8     | icu             | C       | C     | ja-JP
```

エラーメッセージの日本語の翻訳ファイル（`postgres-18.mo`）はイメージに入っているが、メッセージの言語は `lc_messages` で決まり、そこには OS のロケールが必要なので、このイメージのままでは日本語にできない。

#### ロケールを変えたデータベースは template0 から作る

`template1` から、ロケールを変えたデータベースを作ろうとするとエラーになる。

```text
CREATE DATABASE c_db TEMPLATE template1 LOCALE 'C';
ERROR:  new collation (C) is incompatible with the collation of the template database (en_US.utf8)
HINT:  Use the same collation as in the template database, or use template0 as template.
```

`TEMPLATE template0` を指定すれば作れる。エンコーディングを変える場合も同じ。

#### 並び順の違い

```text
C           | A B a b あ か ア カ 亜
en_US.utf8  | a A b B あ ア か カ 亜
ja-x-icu    | a A b B あ ア か カ 亜
```

`C` ロケールは文字コードの順になる。この例では、`en_US.utf8` と ICU の日本語は同じ並び順だった。「日本語のロケールにしないと日本語が正しく並ばない」わけではない。

#### C ロケール以外の注意点

公式ドキュメントには次のように書かれている。

> C や POSIX 以外のロケールを使う欠点は、性能への影響である。文字の処理が遅くなり、`LIKE` で通常のインデックスが使えなくなる。そのため、ロケールは本当に必要な場合にだけ使うこと。

同じテーブルとインデックスで `LIKE 'abc%'` を実行した結果:

```text
--- en_US.utf8 のデータベース
 Bitmap Heap Scan on t
   Filter: (x ~~ 'abc%'::text)            ← インデックスで範囲を絞れていない

--- C ロケールのデータベース
 Index Only Scan using t_x_idx on t
   Index Cond: ((x >= 'abc'::text) AND (x < 'abd'::text))   ← 範囲検索になっている
```

#### 日本語に使えるエンコーディング

| エンコーディング | サーバー側で使えるか |
| --- | --- |
| `UTF8` | ○ |
| `EUC_JP` | ○ |
| `EUC_JIS_2004` | ○ |
| `SJIS` | **×**（クライアント側でだけ使える） |
| `SQL_ASCII` | 使えるが、非 ASCII の文字を扱うなら使うべきではない |

エンコーディングは、ロケール（`LC_CTYPE` と `LC_COLLATE`）と互換性がなければならない。`C` と `POSIX` はどのエンコーディングとも組み合わせられるが、それ以外の libc のロケールは、対応する1つのエンコーディングでしか正しく動かない。

#### 「日本語を扱うならロケールを無効にする」は本当か

日本語を扱う場合は、ロケールを無効にする（`C` ロケール、`--no-locale`）のが推奨されることが多い。ただし、理由は日本語に限った話ではない。根拠は次の3つ。

| 根拠 | 内容 |
| --- | --- |
| 公式ドキュメント | `C` や `POSIX` 以外のロケールは性能に影響し、`LIKE` で通常のインデックスが使えなくなる。ロケールは本当に必要な場合にだけ使う |
| 日本のコミュニティの解説（Let's POSTGRES、2009年） | 日本語のロケールを使うと、文字列の比較やソートに時間がかかる。`LIKE` の前方一致検索でインデックスが使われない。OS が違うと結果が変わるかもしれない |
| 環境に依存しない | `C` ロケールは文字コードの値で並べるので、OS が変わっても結果が変わらない。`LC_COLLATE` と `LC_CTYPE` はあとから変えられないので、最初に決めておく必要がある |

ただし、絶対のルールではない。Let's POSTGRES の記事も、ロケールの利点（辞書順に並べられる、文字の種類を正しく判別できる）を挙げたうえで、「万能なロケールはない。用途に合わせて選ぶ」と結論づけている。**性能と環境への依存を避けたい場合の定番の選択**と理解しておく。

**「ロケールを無効にする」と「エンコーディングを無効にする」は別の話である。** 日本語を保存できるかどうかは、エンコーディングで決まる。

| 書き方 | 結果（sandbox で確認。`LANG=en_US.utf8` の環境） |
| --- | --- |
| `initdb --no-locale` | ロケールは `C`、エンコーディングは **`SQL_ASCII`**（日本語を扱うには不向き） |
| `initdb --no-locale -E UTF8` | ロケールは `C`、エンコーディングは **`UTF8`** |

`--no-locale` を付けると、環境変数 `LANG` が `en_US.utf8` のままでも、エンコーディングは `C` ロケールに合わせて `SQL_ASCII` になった。ロケールを無効にするときは、必ず `-E UTF8` と一緒に指定する。

試験では、次のように判断する。

| 選択肢の例 | 正誤 |
| --- | --- |
| 日本語を扱う場合、ロケールは使わない（`--no-locale`）ことが推奨される | ○ |
| ロケールを使うと、`LIKE` の前方一致検索でインデックスが使えなくなる | ○ |
| ロケールを無効にすると、日本語のデータを保存できなくなる | ×（保存できるかはエンコーディングで決まる） |

#### どうするのがよいか

| 場面 | おすすめ |
| --- | --- |
| この学習環境 | 変えなくてよい。日本語は保存でき、試験の学習にも影響しない |
| 実務でよく採られる構成 | `C` ロケール（`--no-locale`）と `UTF8`。辞書順に並べたい列やクエリだけ `COLLATE "ja-x-icu"` を指定する |

### データディレクトリの中身

`initdb` の直後の PGDATA 直下は次のようになっていた（実機で確認）。

```text
base                 pg_multixact    pg_subtrans           postgresql.auto.conf
global               pg_notify       pg_tblspc             postgresql.conf
pg_commit_ts         pg_replslot     pg_twophase
pg_dynshmem          pg_serial       PG_VERSION
pg_hba.conf          pg_snapshots    pg_wal
pg_ident.conf        pg_stat         pg_xact
pg_logical           pg_stat_tmp
```

役割ごとに分けると次のとおり。

#### データの本体

| 名前 | 内容 |
| --- | --- |
| `base/` | **データベースごとのサブディレクトリ**。ディレクトリ名はデータベースの OID |
| `global/` | **クラスタ全体で共有するテーブル**（`pg_database`、`pg_authid` など） |
| `pg_tblspc/` | テーブルスペースへのシンボリックリンク |

#### WAL とトランザクションの状態

| 名前 | 内容 |
| --- | --- |
| `pg_wal/` | **WAL ファイル**。1ファイルは 16MB |
| `pg_xact/` | **トランザクションのコミット状態** |
| `pg_subtrans/` | サブトランザクションの状態 |
| `pg_multixact/` | 複数のトランザクションが共有する行ロックの状態 |
| `pg_commit_ts/` | トランザクションのコミット時刻 |
| `pg_twophase/` | プリペアドトランザクションの状態 |
| `pg_serial/` | コミット済みのシリアライザブルトランザクションの情報 |

`pg_wal/` の中身は次のようになっていた（db コンテナで確認）。

```text
16M 000000010000000000000002
16M 000000010000000000000003
4.0K archive_status
4.0K summaries
```

#### レプリケーション、統計、その他

| 名前 | 内容 |
| --- | --- |
| `pg_replslot/` | レプリケーションスロットのデータ |
| `pg_logical/` | ロジカルデコーディングの状態 |
| `pg_stat/`、`pg_stat_tmp/` | 統計情報のファイル（永続的なものと一時的なもの） |
| `pg_notify/` | LISTEN / NOTIFY の状態 |
| `pg_snapshots/` | エクスポートされたスナップショット |
| `pg_dynshmem/` | 動的共有メモリで使うファイル |

#### 設定ファイルなど

| 名前 | 内容 |
| --- | --- |
| `postgresql.conf` | メインの設定ファイル |
| `postgresql.auto.conf` | `ALTER SYSTEM` で変更した設定が書かれる。手で編集しない |
| `pg_hba.conf` | クライアント認証の設定 |
| `pg_ident.conf` | OS のユーザー名とデータベースのユーザー名の対応づけ |
| `PG_VERSION` | メジャーバージョン番号（中身は `18`） |

#### 起動すると作られるもの

| 名前 | 作られるタイミング | 停止すると |
| --- | --- | --- |
| `postmaster.pid` | 起動中 | **消える** |
| `postmaster.opts` | 起動時（前回の起動オプションを記録する） | 残る |
| `log/`、`current_logfiles` | **`logging_collector = on` で起動したときだけ** | 残る |

`postmaster.pid` の中身は次のとおり。[S2.2](2-2-標準付属ツール.md) で `pg_resetwal` がサーバーの起動中に拒否されたのは、このファイルがあったため。

```text
1                              ← 親プロセスの PID
/var/lib/postgresql/18/docker  ← データディレクトリ
1789435909                     ← 起動時刻
5432                           ← ポート
/var/run/postgresql            ← Unix ドメインソケットのディレクトリ
*                              ← listen_addresses
  2511659         5            ← 共有メモリの ID
ready                          ← 状態
```

#### log/ ディレクトリ

`log/` は、いつもあるわけではない。

- `logging_collector` の既定は **`off`**。このとき `log/` は作られず、ログは標準エラー出力に出る。学習環境の db もこの状態なので、ログは `docker compose logs db` で見る。
- `logging_collector = on` で起動すると、`log/` と `current_logfiles` が作られた（sandbox で確認）。

```text
$ cat current_logfiles
stderr log/postgresql-2026-09-25_225034.log
```

- `log_directory` の既定は `log`（データディレクトリからの相対パス）、`log_filename` の既定は `postgresql-%Y-%m-%d_%H%M%S.log`。

#### PostgreSQL 10 で名前が変わったもの

古い教材やブログには旧名が出てくる。試験の基準（12〜14）では新しい名前を使う。

| 旧名（9.6 まで） | 新名（10 から） |
| --- | --- |
| `pg_xlog/` | **`pg_wal/`** |
| `pg_clog/` | **`pg_xact/`** |
| `pg_log/`（`log_directory` の既定値） | **`log/`** |
| `pg_resetxlog` | **`pg_resetwal`** |
| `pg_switch_xlog()` | `pg_switch_wal()` |
| `initdb --xlogdir` | `initdb --waldir` |

名前を変えた理由は、公式のリリースノートによると「ただのログファイルだと勘違いして、WAL やトランザクションの状態のファイルを手で削除し、データを失うユーザーがいた」ため。**`pg_wal/` と `pg_xact/` は削除してよいログではない**。

`PG_VERSION` の中身と、クラスタの情報は次のように確認できる。

```sh
cat ~/s21/PG_VERSION          # 18
pg_controldata ~/s21
```

```text
pg_control version number:            1800
Catalog version number:               202506291
Database cluster state:               shut down
Data page checksum version:           1
```

`Data page checksum version` が `1` ならチェックサムが有効、`0` なら無効。`--no-data-checksums` を付けて作ったクラスタでは `0` になった。

### データはまずメモリと WAL に書かれる

データはファイルとして保存されるが、**PostgreSQL の本体はファイルではなく、ファイルを管理するサーバープログラム**である。サーバーが動いている間は、ファイルだけを見ても最新のデータがあるとは限らない。

テーブルに1行を INSERT してコミットし、その文字列がどのファイルにあるかを探した結果:

```text
### テーブルの実体ファイル: base/5/16608
block_size: 8192 バイト
ファイルサイズ: 8192 バイト

### INSERT をコミットした直後
  テーブルのファイルに文字列があるか: 0     ← ない
  WAL（pg_wal）に文字列があるか:     1     ← WAL にはある

### CHECKPOINT のあと
  テーブルのファイルに文字列があるか: 1     ← ここで初めて書かれた
```

コミットした直後のデータは、次の状態にある。

1. 共有メモリ（`shared_buffers`）の上で変更されている
2. WAL には、ディスクへ確実に書かれている
3. テーブルのファイルへの書き出しは後回しで、チェックポイントのときなどにまとめて書かれる

コミットのたびにテーブルのファイルを書き換えると遅いので、コミット時は WAL だけを確実にディスクへ書く。クラッシュしても WAL から復元できる（[S2.2](2-2-標準付属ツール.md) で `immediate` 停止のあとにリカバリが走ったのは、この仕組みによる）。メモリ上の変更をファイルに書き出すのは、`checkpointer` プロセスの役目である。

```text
psql（クライアント）
   │ SQL
   ▼
postgres（サーバープログラム）＝ PostgreSQL の本体
   ・共有メモリでデータを管理する
   ・WAL を書く、トランザクションと同時実行を制御する
   ・権限を確認する、SQL を解析して実行する
   │ 読み書き
   ▼
OS のファイルシステム（データディレクトリ）＝ データの置き場所
   ▼
ディスク
```

Git で例えると、Git の中身は `.git` ディレクトリのファイルだが、Git をファイルシステムとは呼ばない。`.git` の中を手でいじれば壊れるし、正しく扱えるのは `git` コマンドだけである。PostgreSQL も同じで、**データディレクトリのファイルを直接編集してはいけない**。ファイルの中身もテキストではなく、8KB 単位のページ形式のバイナリになっている。

この性質は、[S2.4](2-4-バックアップ方法.md) のバックアップにつながる。サーバーが動いている間はファイルが最新とは限らないので、**データディレクトリをそのままコピーする「ファイルシステムレベルのバックアップ」は、サーバーを止めてから取る**。起動したまま取りたいときは `pg_basebackup` などを使う。

### テンプレートデータベース

`initdb` は3つのデータベースを作る。

| データベース | 役割 |
| --- | --- |
| `postgres` | 既定のデータベース。ユーティリティ、ユーザー、サードパーティのアプリケーションが接続先として使う。中身は `template1` のコピーで、削除して作り直すこともできる |
| `template1` | `CREATE DATABASE` が**既定でコピーする**テンプレート。ここにオブジェクトを追加しておくと、以降に作るデータベースすべてに引き継がれる |
| `template0` | 初期状態のまま保たれるテンプレート。**変更してはいけない** |

実機で確認した結果:

```text
   Name    |  Owner   | Encoding | Locale Provider | Collate | Ctype
-----------+----------+----------+-----------------+---------+-------
 postgres  | postgres | UTF8     | libc            | C       | C
 template0 | postgres | UTF8     | libc            | C       | C
 template1 | postgres | UTF8     | libc            | C       | C
```

```sql
SELECT datname, datistemplate, datallowconn FROM pg_database ORDER BY datname;
```

```text
postgres |f|t
template0|t|f      ← テンプレートだが、接続できない
template1|t|t
```

| 列 | 意味 |
| --- | --- |
| `datistemplate` | テンプレートとして使えるか。`true` なら `CREATEDB` 権限を持つユーザーがコピーできる |
| `datallowconn` | 新しい接続を許可するか。**`template0` は `false`** なので、そもそも接続して変更できない |

`template0` を使う場面は次の2つ。

- **`pg_dump` で取得したダンプを復元するとき。** `template1` に後から追加されたオブジェクトと衝突させないため。
- **エンコーディングやロケールを変えたデータベースを作るとき。** `template1` は既存の設定を引き継ぐしかないが、`template0` からなら新しい設定を指定できる。

```sql
CREATE DATABASE dbname TEMPLATE template0;
```

```sh
createdb -T template0 dbname
```

#### 初期状態の template0 と template1 は同じ内容か

**中身は同じで、属性が違う**。公式ドキュメントには「`template0` は `template1` の初期状態と同じデータ（PostgreSQL が定義済みの標準オブジェクトだけ）を持つ」と書かれている。

まっさらなクラスタで、`template0` と `template1` からそれぞれデータベースを作り、システムカタログを比べた。`template0` には接続できないので、コピーしてできたデータベース同士を比べている。

```text
          | テーブル等 | 関数 | 型  | スキーマ | pg_class のハッシュ              | pg_proc のハッシュ
from_t0   | 415       | 3413 | 621 | 4       | abfe53bc29f0667cc4186e55868e51ea | 41b4c78ddab092634e50def5206d411a
from_t1   | 415       | 3413 | 621 | 4       | abfe53bc29f0667cc4186e55868e51ea | 41b4c78ddab092634e50def5206d411a
```

件数だけでなく、カタログの中身から計算したハッシュ値まで一致した。比較に使った SQL は次のとおり（それぞれのデータベースで実行した）。

```sql
SELECT (SELECT count(*) FROM pg_class)     AS classes,
       (SELECT count(*) FROM pg_proc)      AS functions,
       (SELECT count(*) FROM pg_type)      AS types,
       (SELECT count(*) FROM pg_namespace) AS schemas,
       (SELECT md5(string_agg(oid::text || ':' || relname::text || ':' || relkind::text, ',' ORDER BY oid))
          FROM pg_class) AS class_hash,
       (SELECT md5(string_agg(oid::text || ':' || proname::text, ',' ORDER BY oid))
          FROM pg_proc) AS proc_hash;
```

- `relkind` は `"char"` という特殊な型なので、`::text` で文字列に変換しないと `||` で連結できない。
- `pg_dump --schema-only` の結果を比べる方法は、この確認には使えない。`pg_dump` はユーザーが作ったオブジェクトしか書き出さないので、どちらも空の結果になるだけである。

一方で、データベースとしての属性は違う。

```text
 oid |  datname  | datistemplate | datallowconn |               datacl
-----+-----------+---------------+--------------+-------------------------------------
   1 | template1 | t             | t            | {=c/postgres,postgres=CTc/postgres}
   4 | template0 | t             | f            | {=c/postgres,postgres=CTc/postgres}
```

| | `template1` | `template0` |
| --- | --- | --- |
| 中身（オブジェクト） | 同じ | 同じ |
| テンプレートとして使えるか（`datistemplate`） | ○ | ○ |
| **接続できるか（`datallowconn`）** | **○** | **×** |
| 変更してよいか | ○ | × |

試験では、次のように判断する。

| 選択肢の例 | 正誤 |
| --- | --- |
| 初期状態の `template0` と `template1` は同じ内容である | ○ |
| 初期状態の `template0` と `template1` は同じ内容で、どちらにも接続できる | ×（`template0` には接続できない） |
| `template1` を変更したあとも、`template0` と同じ内容である | ×（`template0` は初期状態のまま） |

**「初期状態では」という条件がポイント**である。`template1` は誰かが手を加えるかもしれないが、`template0` はずっと初期状態のまま保たれる。だからこそ、まっさらなデータベースを作りたいときに `template0` を使う。

#### 3つのデータベースの扱い

「触ってはいけない」のは `template0` だけである。

| データベース | 触ってよいか | 実機で確認した結果 |
| --- | --- | --- |
| `template0` | **×** 変更してはいけない。そもそも接続できない | `FATAL: database "template0" is not currently accepting connections` |
| `template1` | **○** ただし、入れたものは以降に作るすべてのデータベースにコピーされる | `template1` に作ったテーブルが、あとで作ったデータベースにもあった |
| `postgres` | **○** 管理作業の接続先として使う | `CREATE TABLE` できた |

- **`template1`**: 公式ドキュメントにも「`template0` は変更してはいけないが、`template1` にはオブジェクトを追加できる。追加したものは、以降に作るデータベースにコピーされる」とある。全データベースで使う拡張機能を入れておく、といった使い方ができる。ただし、**コピーされるのはデータベースを作成したときだけ**なので、あとから追加しても既存のデータベースには反映されない。
- **`postgres`**: 公式ドキュメントでは「`template1` のコピーにすぎず、必要なら削除して作り直してもよい」とされている。技術的には何でも置けるが、アプリケーションのデータはアプリケーション用のデータベースに分けて置くのが一般的。
- **`template0`**: 誰も手を加えていない初期状態を保証するためにある。`template1` は誰かが変更しているかもしれないため。

#### template1 以外からも作れる

`TEMPLATE` を省略すると `template1` が使われるが、これは**既定値であって必須ではない**。公式ドキュメントでは、`TEMPLATE` を「新しいデータベースの作成元となるテンプレートの名前。`DEFAULT` を指定すると既定のテンプレート（`template1`）を使う」と説明している。

| 書き方 | 結果（実機で確認） |
| --- | --- |
| 省略（または `TEMPLATE DEFAULT`） | `template1` からコピーされる |
| `TEMPLATE template0` | 作れる。`template1` は使わない |
| `TEMPLATE src`（普通のデータベース） | 作れる。`src` のテーブルとデータまでコピーされる |

```sql
CREATE DATABASE cp TEMPLATE src;
```

```text
（cp に接続して seed テーブルを SELECT）
 src のデータ     ← src に入れたデータがそのままある
```

ただし、次の3つの制約がある。

##### 制約1: コピー元にほかの接続があってはいけない

```text
ERROR:  source database "src" is being accessed by other users
DETAIL:  There is 1 other session using the database.
```

接続が切れたあとで同じコマンドを実行すると、成功した。公式ドキュメントにも「コピー中は、ほかのセッションがテンプレートのデータベースに接続していてはならない。開始時にほかの接続があれば `CREATE DATABASE` は失敗する」とある。

##### 制約2: テンプレートとして登録されていないデータベースは、スーパーユーザーか所有者しかコピーできない

```text
CREATEDB 権限だけのロールで src をコピー
ERROR:  permission denied to copy database "src"

ALTER DATABASE src IS_TEMPLATE true; のあとなら
CREATE DATABASE                          ← 同じロールでコピーできた
```

公式ドキュメントでは、`IS_TEMPLATE` が `true` なら `CREATEDB` 権限を持つ任意のユーザーがコピーでき、`false`（既定）ならスーパーユーザーか所有者だけがコピーできる、とされている。`IS_TEMPLATE` の値は `pg_database` の `datistemplate` 列に入る。

##### 制約3: テンプレートとして登録したデータベースは、そのままでは削除できない

```text
ERROR:  cannot drop a template database
```

`ALTER DATABASE ... IS_TEMPLATE false` に戻してから削除する。

なお公式ドキュメントには、普通のデータベースをテンプレートに指定できる機能は「汎用の『データベースのコピー』機能として意図されたものではない」とも書かれている。

使い分けは次のとおり。

| 場面 | テンプレート |
| --- | --- |
| 普段 | 省略して `template1` でよい。手を加えていなければ、中身は `template0` と同じ |
| エンコーディングやロケールを変えたいとき | `template0`（`template1` だとエラーになる） |
| `pg_dump` のダンプを復元するとき | `template0`（`template1` に追加されたものと衝突させないため） |

#### 「デフォルトのデータベース」の3つの意味

「デフォルト」という言葉は、何の既定値かによって答えが変わる。

| 何の既定値か | 既定値 |
| --- | --- |
| 公式ドキュメントでの位置づけ | `postgres`。ユーザーやツールが使うための既定のデータベース |
| **接続先のデータベースを省略したとき** | **ユーザー名と同じ名前のデータベース**（`postgres` とは限らない） |
| `CREATE DATABASE` のコピー元 | `template1` |

接続の既定値は、libpq（PostgreSQL のクライアントが使う接続ライブラリ）の公式ドキュメントで次のように定められている。

- `dbname`（接続先のデータベース名）の既定値は、**ユーザー名と同じ**
- `user`（ユーザー名）の既定値は、アプリケーションを実行している **OS のユーザー名と同じ**

実機で確認した結果:

```text
$ psql -U appuser                   ← 接続先を省略
FATAL:  database "appuser" does not exist
```

`postgres` ロールで接続先を省略したときに postgres データベースに繋がるのは、**ユーザー名とデータベース名がたまたま同じ `postgres` だから**である。`createdb` でデータベース名を省略したときに OS のユーザー名と同じ名前になるのも、同じ考え方。

#### postgres という名前は2種類ある

| 種類 | 名前 | 由来 |
| --- | --- | --- |
| データベース | `postgres` | `initdb` が必ずこの名前で作る |
| ロール | `postgres` | `initdb` を実行した OS ユーザーの名前（`-U` で変えられる）。Docker の公式イメージでは `POSTGRES_USER`（既定値は `postgres`） |

`initdb` が作った3つのデータベースの所有者は、どれもこのロールである。

```text
  datname  |  owner
-----------+----------
 template1 | postgres
 template0 | postgres
 postgres  | postgres
```

#### アプリケーション用のデータベースは別に作る

`postgres`、`template1`、`template0` は改名せずに残し、**アプリケーション用のロールとデータベースを別に作る**のが一般的な運用である。

```sh
createuser appuser              # アプリケーション用のロール
createdb -O appuser myapp       # そのロールを所有者にして、データベースを作る
psql -U appuser -d myapp -c "SELECT current_database(), current_user"
```

```text
 current_database | current_user
------------------+--------------
 myapp            | appuser
```

データベースの改名自体は `ALTER DATABASE ... RENAME TO` でできる。ただし、**接続中のデータベースは改名できない**ので、別のデータベースに接続してから実行する。

```text
postgres に接続して postgres を改名 → ERROR:  current database cannot be renamed
postgres に接続して myapp を改名    → ALTER DATABASE（成功）
```

Docker の公式イメージの `POSTGRES_DB` 環境変数は、この「`initdb` のあとにアプリケーション用のデータベースを作る」作業を自動化したもの。エントリポイントは、同じ名前のデータベースがなければ次の SQL を実行する。

```sql
CREATE DATABASE :"db" ;
```

`POSTGRES_DB` の既定値は `POSTGRES_USER` と同じ名前で、`postgres` なら既に存在するので何も作らない。この学習環境の `compose.yaml` では指定していないので、データベースは3つだけになっている。

### 自分で試す（sandbox）

sandbox でクラスタを作ってから、アプリケーション用のデータベースを作るまでを一通り試す手順。最後に後片付けをすれば、何度でもやり直せる。

```sh
docker compose exec sandbox bash   # sandbox に入る（postgres ユーザーになる）
```

#### 手順1: クラスタを作る

```sh
initdb -D ~/mycluster
```

出力の中に次の行がある。

```text
The files belonging to this database system will be owned by user "postgres".
Data page checksums are enabled.
initdb: warning: enabling "trust" authentication for local connections
Success. You can now start the database server using:
```

#### 手順2: 中身を見る

```sh
ls ~/mycluster               # base、global、pg_wal などがある
ls ~/mycluster/base          # 1、4、5（template1、template0、postgres の OID）
cat ~/mycluster/PG_VERSION   # 18
```

#### 手順3: まだ起動していないことを確かめる

```sh
pg_ctl -D ~/mycluster status   # pg_ctl: no server running
echo $?                        # 3
ls ~/mycluster | grep postmaster   # 何も出ない（postmaster.pid はまだない）
```

#### 手順4: 起動する

```sh
pg_ctl -D ~/mycluster -l ~/mycluster.log start
ls ~/mycluster | grep postmaster   # postmaster.opts と postmaster.pid ができている
```

#### 手順5: 3つのデータベースを見る

```sh
psql -l
psql -d template0 -c "SELECT 1"   # FATAL: database "template0" is not currently accepting connections
psql -c "SELECT current_user, current_database()"   # postgres と postgres
```

接続先を省略すると、ユーザー名（`postgres`）と同じ名前のデータベースに接続される。

#### 手順6: アプリケーション用のロールとデータベースを作る

```sh
createuser appuser
psql -U appuser -c "SELECT 1"     # FATAL: database "appuser" does not exist
createdb -O appuser myapp
psql -U appuser -d myapp -c "SELECT current_database(), current_user"   # myapp と appuser
```

#### 手順7: template1 に入れたものがコピーされるのを見る

```sh
psql -d template1 -c "CREATE TABLE common_master (code text PRIMARY KEY, label text)"
createdb db2
psql -d db2 -c "\dt"          # common_master がある
psql -c "SELECT oid, datname FROM pg_database ORDER BY oid"
ls ~/mycluster/base           # 新しいデータベースの OID のディレクトリが増えている
```

確認した結果（新しいデータベースの OID の値は、環境によって変わる）:

```text
  oid  |  datname
-------+-----------
     1 | template1
     4 | template0
     5 | postgres
 16385 | myapp
 16394 | db2
```

確かめたら、`template1` を元に戻す。

```sh
psql -d template1 -c "DROP TABLE common_master"
```

#### 手順8: 停止と後片付け

```sh
pg_ctl -D ~/mycluster stop
ls ~/mycluster | grep postmaster   # postmaster.pid は消え、postmaster.opts だけが残る
rm -rf ~/mycluster ~/mycluster.log
exit
```

sandbox ごとまっさらに戻したいときは、ホスト側で `docker compose rm -sfv sandbox && docker compose up -d sandbox` を実行する。

### 試験の観点

- **`initdb` は root では実行できない。** サーバープロセスを所有するユーザーで実行する。
- **`PGDATA` と `-D` は同じ場所を指す。** サーバーも同じ変数を見る。
- **`CREATE DATABASE` が既定でコピーするのは `template1`。**
- **`template0` は変更してはいけない。** `datallowconn = false` で接続もできない。
- Ver.3.0 の改定で、出題範囲から `pg_ctl initdb` が削除された（`initdb` コマンドを直接使う）。
- **`base/` はデータベースごと、`global/` はクラスタ全体で共有するもの**。ロールはクラスタ全体で共有される。
- **`pg_wal/` は WAL、`pg_xact/` はコミット状態**。どちらも削除してはいけない。9.6 までは `pg_xlog/`、`pg_clog/` という名前だった。
- **`postmaster.pid` は起動中だけ存在する**。
- **`log/` は `logging_collector = on` のときだけ作られる**。
- **コミット時にディスクへ確実に書かれるのは WAL**。テーブルのファイルへの書き出しは、チェックポイントなどで後から行われる。
- **`initdb` はクラスタを初期化するだけ**。サーバーの起動も、アプリケーション用のデータベースの作成もしない。
- **変更してはいけないのは `template0` だけ**（接続もできない）。`template1` に追加したものは、以降に作るデータベースにコピーされる。
- **接続先のデータベースを省略すると、ユーザー名と同じ名前のデータベースに接続しようとする**。
- **接続中のデータベースは改名できない**。
- **オプションを省略すると、ロケールは環境変数から、エンコーディングはロケールから、スーパーユーザーの名前は OS のユーザーから決まる**。認証方式は環境に関係なく `trust`。
- **`C` ロケールで `-E` を省略すると `SQL_ASCII` になる**。日本語を扱うなら `-E UTF8` を明示する。
- **データディレクトリは `-D`（`--pgdata`）か環境変数 `PGDATA` で指定する**。`PGDATA` を設定していなくても、`-D` か `--pgdata` でディレクトリを指定すれば `initdb` は実行できる。どちらもなければエラーになる。
- **`LC_COLLATE` と `LC_CTYPE` はデータベースの作成時に固定され、あとから変えられない**。ロケールやエンコーディングを変えたデータベースは `template0` から作る。
- **日本語に使えるサーバーのエンコーディングは `UTF8`、`EUC_JP`、`EUC_JIS_2004`**。`SJIS` はサーバー側では使えない。
- **初期状態の `template0` と `template1` は同じ内容**。ただし `template0` には接続できない（`datallowconn = false`）。
- **`TEMPLATE` を省略すると `template1` が使われる**。ただし `TEMPLATE` を指定すれば、`template0` やほかのデータベースからも作れる。
- **コピー元に接続中のセッションがあると、`CREATE DATABASE` は失敗する**。
- **`IS_TEMPLATE`（`datistemplate`）が `true` なら、`CREATEDB` 権限を持つユーザーならコピーできる**。`false` ならスーパーユーザーか所有者だけ。
- **日本語を扱う場合、ロケールは使わない（`--no-locale`）ことが推奨されることが多い**。理由は性能、`LIKE` の前方一致でのインデックス、環境への依存。ロケールを無効にしても日本語は保存できるが、`-E UTF8` を必ず一緒に指定する。

## ⚠️ 試験と最新版の違い

- **PG18**: `initdb` がデフォルトでデータチェックサムを有効にするようになった。無効にするには `--no-data-checksums` を付ける。試験の基準（12〜14）ではデフォルトは無効で、有効にするには `-k`（`--data-checksums`）を付ける。
  - 実機（PG18）で確認すると、既定で `Data page checksum version: 1`、`--no-data-checksums` を付けると `0` だった。
  - PG14 のドキュメントは `-k` を「指定した場合（If set）」と説明するだけで、既定で有効とは書いていない。
- **ドキュメントの記述の違い**: PG18 のドキュメントは `initdb` が `postgres`、`template1`、`template0` の3つを作ると明記している。PG14 のドキュメントの同じ箇所では `postgres` と `template1` しか触れていない（`template0` は別の節で説明されている）。実際にはどちらのバージョンでも3つ作られる。

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | B | サーバーは root で動かせないので `initdb` も root では実行できない。既存の非空ディレクトリを指定すると、上書きせずエラーになる |
| 2 | `PGDATA` | `-D` と同じ場所を指す。サーバーも同じ変数を見る |
| 3 | C | 既定のテンプレートは `template1` |
| 4 | A、B、C | `template0` は `initdb` が作る。D が誤り |
| 5 | B | `base` はデータベースごとの実データ、`global` はクラスタ全体で共有するテーブル |
| 6 | D | `-X`（`--waldir`）は WAL を別のディレクトリに置くオプション。チェックサムは `-k`（`--data-checksums`） |
| 7 | B | `pg_wal/` は WAL であり、削除するとデータを失う。この誤解を防ぐために、PostgreSQL 10 で `pg_xlog/` から改名された |
| 8 | `postmaster.pid` | 停止すると消える。`pg_resetwal` はこのファイルがあると実行を拒否する |
| 9 | A、B、D | C は誤り。`pg_wal/` はサーバーのログではなく WAL（先行書き込みログ）の置き場所 |
| 10 | C | 接続先のデータベース名の既定値はユーザー名と同じ。`postgres` ロールで省略すると postgres データベースに繋がるのは、名前が同じだから |
| 11 | A、C、D | `initdb` はサーバーを起動しない。起動は `pg_ctl start` で行う |
| 12 | A | `CREATE DATABASE` は既定で `template1` をコピーする。コピーは作成時だけなので、既存のデータベースには反映されない |
| 13 | A、B、D | 認証方式は環境に関係なく `trust` になる（警告が出る） |
| 14 | C | `C` ロケールで `-E` を省略すると `SQL_ASCII` になる。日本語を扱うなら `-E UTF8` を明示する |
| 15 | C | `SJIS` はクライアント側でだけ使えるエンコーディング |
| 16 | A | 中身は同じだが、`template0` は `datallowconn = false` なので接続できない。`template1` を変更しても `template0` は初期状態のまま |
| 17 | A、C、D | `TEMPLATE` を指定すれば、`template0` やほかのデータベースからも作れる。B が誤り |
| 18 | A、C、D | 日本語を保存できるかはエンコーディングで決まるので、B が誤り。ロケールを無効にするときは `-E UTF8` を一緒に指定する |
