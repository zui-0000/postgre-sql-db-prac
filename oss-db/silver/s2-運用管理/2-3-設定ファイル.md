## 学習メモ

### 暗号化とハッシュ

PostgreSQL 本体には、データベース全体を自動的に暗号化する機能（透過的データ暗号化、TDE）はない。公式ドキュメントが挙げている選択肢は次のとおり。

| 暗号化する対象 | 手段 | 担当 |
| --- | --- | --- |
| パスワードの保存 | ハッシュ化して保存する（`password_encryption`） | PostgreSQL（標準） |
| 特定の列の値 | `pgcrypto` 拡張 | PostgreSQL（拡張を追加する） |
| データファイル全体 | ファイルシステムやブロックレベルの暗号化（dm-crypt + LUKS など） | **OS**。PostgreSQL の機能ではない |
| 通信（クエリと結果） | SSL 接続、GSSAPI | PostgreSQL の設定 |
| データそのもの | クライアント側で暗号化してから送る | アプリケーション |

#### 暗号化とハッシュは別物

| | 暗号化 | ハッシュ |
| --- | --- | --- |
| 元に戻せるか | 戻せる（鍵があれば） | 戻せない |
| 用途 | 保存したデータを、あとで読みたいとき | パスワードの照合のように、一致だけ確かめたいとき |
| PostgreSQL での例 | `pgp_sym_encrypt`（pgcrypto） | `crypt`（pgcrypto）、ユーザーのパスワードの保存 |

**ユーザーのパスワードは、暗号化ではなくハッシュとして保存される。** 設定名は `password_encryption` だが、公式ドキュメントにも「パスワードはハッシュとして保存されるので、管理者でも実際のパスワードはわからない」と書かれている。名前に引っ張られないよう注意する。

実機で確認した結果:

```sh
docker compose exec db psql -U postgres \
  -c "SELECT rolname, left(rolpassword, 14) FROM pg_authid WHERE rolname = 'postgres'" \
  -c "SHOW password_encryption" -c "SHOW ssl"
```

```text
 rolname  |      left
----------+----------------
 postgres | SCRAM-SHA-256$

 password_encryption
---------------------
 scram-sha-256

 ssl
-----
 off
```

ハッシュはソルト（毎回変わるランダムな値）と組み合わせて計算されるので、同じパスワードでも結果は毎回変わる。照合するときは、保存済みのハッシュをソルトとして渡し、計算し直した結果と比べる。

#### 列単位の暗号化（pgcrypto）

`pgcrypto` は同梱されているが、使うには拡張を追加する必要がある。

```sql
CREATE EXTENSION pgcrypto;
INSERT INTO secrets VALUES (1, pgp_sym_encrypt('4111-1111-1111-1111', 'my-key'));
SELECT pgp_sym_decrypt(card_number, 'my-key') FROM secrets;   -- 元の値に戻る
SELECT pgp_sym_decrypt(card_number, 'wrong-key') FROM secrets; -- ERROR: Wrong key or corrupt data
```

保存されている値は、次のようなバイト列になる。

```text
 id |                   stored
----+---------------------------------------------
  1 | c30d04070302e6618324aad57cf266d244018a0a...
```

公式ドキュメントの注意点:

- `pgcrypto` の関数は**サーバーの中で動く**ため、復号した値と鍵が一時的にサーバー上に存在する。
- クライアントとサーバーの間は平文が流れるので、ローカル接続か SSL 接続を使う。
- サーバーの管理者を信用できない場合は、クライアント側で暗号化するしかない。

つまり「暗号化したから安全」ではなく、**誰から守りたいのか**によって選ぶ手段が変わる。

#### 試験の観点

- Silver の出題範囲に `pgcrypto` は入っていない。押さえるのは `password_encryption` と SSL の設定。
- パスワードは SCRAM-SHA-256 でハッシュ化して保存される（PG14 からのデフォルト。PG12 と PG13 は md5）。
- ディスクの暗号化は OS の仕事で、PostgreSQL の機能ではない。

### 接続方式とプロセス構成

#### 2つの接続方式

PostgreSQL はクライアント/サーバー型で、接続方式は2つある。

| 方式 | 使える範囲 | 指定の仕方 |
| --- | --- | --- |
| Unix ドメインソケット | 同じマシンの中だけ | `psql -h /var/run/postgresql`（ホストを省略した場合もこれ） |
| TCP/IP | ネットワーク越しでも可能 | `psql -h 127.0.0.1`、`psql -h 192.168.1.10` |

どちらで接続しているかは `inet_client_addr()` でわかる。Unix ドメインソケットなら NULL、TCP/IP なら接続元のアドレスが入る（`pg_stat_activity` の `client_addr` 列も同じ）。

```text
=== Unix ドメインソケットで接続した場合 ===
 client_addr | server_addr
-------------+-------------
             |

=== TCP/IP（127.0.0.1）で接続した場合 ===
 client_addr | server_addr | client_port
-------------+-------------+-------------
 127.0.0.1   | 127.0.0.1   |       35084
```

#### リモートから接続するために必要な2つの設定

TCP/IP で接続**できる**ことと、**デフォルトで開いている**ことは別である。リモートからの接続には2つの関門がある。

| 関門 | 役割 | 設定ファイル |
| --- | --- | --- |
| `listen_addresses` | どのアドレスで待ち受けるか。PostgreSQL のデフォルトは `localhost`（同じマシンからのみ） | `postgresql.conf` |
| `pg_hba.conf` の行 | 誰の接続を、どの認証方式で通すか | `pg_hba.conf` |

学習環境で確認した値:

```text
 listen_addresses |  port  | unix_socket_directories
------------------+--------+--------------------------
 *                |  5432  | /var/run/postgresql
```

`*` は「すべてのアドレスで待ち受ける」という意味で、これは Docker の公式イメージが設定したもの。PostgreSQL を素でインストールした場合のデフォルトは `localhost`。**ポートのデフォルトは 5432**。

#### 待ち受けるポートは1つだけ

PostgreSQL が TCP で待ち受けるポートは、`port` に指定した**1つだけ**である。複数のポートで待ち受ける仕組みはない。学習環境で確認した結果は次のとおり。

```text
=== IPv4 ===
  0.0.0.0:5432        ← PostgreSQL
  127.0.0.11:35593    ← Docker が用意した DNS。PostgreSQL ではない
=== IPv6 ===
  ポート 5432          ← 同じ PostgreSQL（IPv6 でも同じポート番号）
```

5433 番に接続しようとすると `Connection refused` になる。

ただし「入り口」という観点では、次の点に注意する。

| 注意点 | 内容 |
| --- | --- |
| Unix ドメインソケットは別の入り口 | TCP を使わない。`listen_addresses = ''` にして TCP を閉じても、同じマシンからソケット経由では接続できる（Docker 公式イメージが初期化中に立てる一時サーバーがこの設定） |
| `listen_addresses` はアドレスを決めるだけ | `*` でも `localhost` でも、ポートは1つ。IPv4 と IPv6 の両方で同じ 5432 を使う |
| 外から見える入り口は別物 | Docker のポート公開（ホストの 15432 からコンテナの 5432 へ）や、pgbouncer のような接続プーラーを挟むと、クライアントが接続するポートはサーバー自身のポートと異なる |
| 複数のクラスタは別ポート | 同じマシンで PostgreSQL のクラスタを複数動かすときは、5432、5433 のように分ける。ポートはクラスタごとに1つ |

レプリケーションの接続も同じポートを使う。専用のポートはない。

#### Node.js との対応

TCP/IP は「ネットワークで通信するための決まりごと」で、IP アドレスがどの機器かを、ポート番号がその機器の中のどのプログラムかを決める。Node.js で Web サーバーを立てるときの設定と、そのまま対応づけられる。

| Node.js | PostgreSQL |
| --- | --- |
| `app.listen(3000)` | `port = 5432` |
| `app.listen(3000, '127.0.0.1')`（自分からのみ） | `listen_addresses = 'localhost'` |
| `app.listen(3000, '0.0.0.0')`（どこからでも） | `listen_addresses = '*'` |
| `fetch('http://localhost:3000')` | `psql -h 127.0.0.1 -p 5432` |

`fetch` が TCP 接続の上に HTTP を載せているのと同じで、PostgreSQL は TCP 接続の上に独自のプロトコルを載せて SQL と結果をやり取りする。SSL 接続は、その TCP の上に TLS を重ねたもの（HTTP と HTTPS の関係と同じ）。

なお、Unix ドメインソケットの実体はファイルである。

```text
srwxrwxrwx 1 postgres postgres 0 Sep 25 06:08 .s.PGSQL.5432
^
└─ 先頭の s が「ソケット」の印
```

#### プロセス構成

PostgreSQL は**マルチプロセス**構成で、接続ごとに専用のプロセス（backend）が作られる。スレッドではない。

```text
    PID    PPID COMMAND
      1       0 postgres                              ← 親プロセス
     71       1 postgres: checkpointer
     72       1 postgres: background writer
     74       1 postgres: walwriter
     75       1 postgres: autovacuum launcher
     76       1 postgres: logical replication launcher
```

プロセスの種類は `pg_stat_activity` の `backend_type` 列でも確認できる。クライアントからの接続は `client backend` として現れる。

プロセスとスレッドの違いは次のとおり。

| | プロセス | スレッド |
| --- | --- | --- |
| 実行単位 | OS から見た独立したプログラムの単位 | プロセスの中にある実行の流れ |
| メモリ | それぞれが自分専用のメモリ空間を持つ | 同じプロセス内のメモリを共有する |
| 作るコスト | 重い | 軽い |
| 1つが壊れたとき | ほかのプロセスに直接は波及しない | 同じプロセス内のすべてのスレッドが道連れになりうる |
| データのやり取り | 共有メモリやソケットなどの仕組みが必要 | 変数をそのまま共有できる（代わりに排他制御が必要） |

接続を2本増やして確認したところ、接続ごとにプロセスが作られ、どれも親プロセス（PID 1）の子になっていた。

```text
  pid   |  backend_type  | state
--------+----------------+--------
 400359 | client backend | active
 400360 | client backend | active
 400367 | client backend | active   ← 確認に使った psql

    PID    PPID COMMAND
 400359       1 postgres: postgres postgres [local] SELECT
 400360       1 postgres: postgres postgres [local] SELECT
```

ただし完全に分離しているわけではない。`shared_buffers` が指す**共有メモリ**は全プロセスで共有され、あるプロセスが読み込んだページを別のプロセスも利用できる。

```text
 shared_buffers | max_connections
----------------+-----------------
 128MB          |             100
```

プロセス方式の利点は、1つの接続で異常が起きてもほかに波及しにくいこと。代償は接続を作るコストが高く、接続数が増えるとメモリも消費すること。そのため `max_connections` をむやみに増やさず、pgbouncer のような接続プーラーを前に置くのが定石になる。

Node.js と比べると、`cluster` でワーカープロセスを fork するのが PostgreSQL のバックエンドプロセスに近い。`worker_threads` のようなスレッド方式は採用していない。大きな違いは、Node.js が1プロセスで多数の接続を捌くのに対して、**PostgreSQL は1接続に1プロセス**である点。アプリケーション側で接続をプールする意味はここにある。

なお `max_connections` と `shared_buffers` は、どちらも `context` が `postmaster` なので変更には再起動が必要（「設定の反映方法」を参照）。

### 設定の反映方法（リロードと再起動）

設定を変えたあと、リロードで足りるのか、サーバーの再起動が必要なのかは、`pg_settings` ビューの `context` 列でわかる。

| context | 反映方法 | 学習環境での例 |
| --- | --- | --- |
| `postmaster` | サーバーの**再起動**が必要 | `port`、`listen_addresses`、`max_connections`、`shared_buffers`、`unix_socket_directories` |
| `sighup` | **リロード**で反映される（`pg_ctl reload`） | `ssl` |
| `superuser` | 実行中のセッションで `SET` できる（スーパーユーザーのみ） | `log_min_duration_statement` |
| `user` | 実行中のセッションで `SET` できる | `work_mem`、`password_encryption` |

`context` は全部で7種類ある（`internal`、`postmaster`、`sighup`、`superuser-backend`、`backend`、`superuser`、`user`）。

リロード（設定ファイルの再読み込み）は、`pg_ctl reload` のほかに、SQL の **`SELECT pg_reload_conf();`** でもできる（既定ではスーパーユーザーのみ）。どちらも postmaster に SIGHUP を送る点は同じで、`pg_reload_conf()` はネットワーク越しに接続した psql からでも実行できる。詳しくは [S2.2](2-2-標準付属ツール.md) の「設定の再読み込みは pg_ctl 以外でもできる」を参照。

```sh
docker compose exec db psql -U postgres \
  -c "SELECT name, setting, context FROM pg_settings WHERE name = 'port'"
```

```text
 name | setting |  context
------+---------+------------
 port | 5432    | postmaster
```

つまり、**`port` や `listen_addresses` の変更はリロードでは反映されず、再起動が必要**である。接続の入り口に関する設定は、どれも `postmaster` になっている。

### クライアントのエンコーディング（client_encoding）

`client_encoding` は、出題範囲の「クライアント接続デフォルト」に含まれる設定で、**クライアントが送受信する文字のエンコーディング**を表す。サーバーのエンコーディング（データベースのエンコーディング）と違う場合は、**サーバーが自動で変換する**。

| 設定 | 意味 | context |
| --- | --- | --- |
| `server_encoding` | データベースのエンコーディング。作成時に決まり、変更できない | `internal` |
| `client_encoding` | クライアントのエンコーディング。既定値はデータベースのエンコーディング | `user` |

`context` が `user` なので、接続ごとに `SET` で変えられる（「設定の反映方法」を参照）。

#### 自動変換を確かめる

EUC_JP のデータベースを作り（作り方は [S2.2](2-2-標準付属ツール.md) の「テンプレートと違うエンコーディングで作る」を参照）、UTF8 のクライアントから「りんご」を入れた。

```text
   s    | euc_jp | utf8
--------+--------+------
 りんご |      6 |    9
```

データベースの中では EUC_JP の6バイト（1文字2バイト）で保存されている。UTF8 に直すと9バイト（1文字3バイト）になる。クライアントは UTF8 で送り、サーバーが EUC_JP に変換して保存した。取り出すときも、サーバーが UTF8 に変換して返す。

#### psql の client_encoding は、接続のしかたで変わる

公式ドキュメント（psql）には「標準入力と標準出力がどちらも端末なら、psql は `client_encoding` を `auto` にし、ロケールの設定（Unix では環境変数 `LC_CTYPE`）から適切なエンコーディングを判定する」とある。

| 接続のしかた | client_encoding | 理由 |
| --- | --- | --- |
| 端末から対話的に接続 | `UTF8` | ロケール（`en_US.utf8`）から判定される |
| パイプやスクリプトから接続 | `EUC_JP` | 判定されないので、既定値（データベースのエンコーディング）になる |

そのため、スクリプトから UTF8 の文字を送ると、サーバーは EUC_JP として読もうとしてエラーになる。

```text
ERROR:  invalid byte sequence for encoding "EUC_JP": 0xe3 0x82
```

`0xe3 0x82` は「り」の UTF8 の先頭2バイトで、EUC_JP としては正しくない並びである。

#### client_encoding の指定方法

| 方法 | 例 | 範囲 |
| --- | --- | --- |
| 環境変数 | `PGCLIENTENCODING=UTF8 psql ...` | その接続 |
| SQL | `SET client_encoding TO 'UTF8';` | そのセッション |
| psql のメタコマンド | `\encoding UTF8` | そのセッション |
| `postgresql.conf` | `client_encoding = 'UTF8'` | サーバー全体の既定値 |

確認は `SHOW client_encoding;` か、引数なしの `\encoding` で行う。

TypeScript で例えると、Node.js の `Buffer.from('りんご', 'utf8')` は9バイトになる。どのエンコーディングでバイト列にするかを、クライアントとサーバーの間で取り決めるのが `client_encoding` である。

#### 試験の観点（client_encoding）

- **`client_encoding` とデータベースのエンコーディングが違うと、サーバーが自動で変換する**。
- `client_encoding` は `SET` や環境変数 `PGCLIENTENCODING` で変えられる。データベースのエンコーディング（`server_encoding`）は作成後に変えられない。

## ⚠️ 試験と最新版の違い

- **PG14（試験の基準の範囲内）**: `password_encryption` のデフォルトが `md5` から `scram-sha-256` に変わった。12/13 と 14 では答えが違う。
- **PG16**: `pg_hba.conf` で、データベース名やユーザー名に正規表現を書けるようになった。別のファイルを読み込む（include）こともできる。どちらも試験の基準にはない書き方。
- **PG17**: `db_user_namespace`（データベースごとのユーザーを模擬する設定）が削除された。
- **PG18**: MD5 パスワード認証が非推奨になった。MD5 形式のパスワードを設定すると警告が出る（`md5_password_warnings` で止められる）。
- **PG18**: 非同期 I/O（AIO）の仕組みが追加され、`io worker` というプロセスが動くようになった。学習環境では `io_method = worker`、`io_workers = 3` で、3つの `io worker` プロセスが起動していた。`pg_aios` というビューも新設された。試験の基準（PG 12〜14）にはこのプロセスは存在しないので、プロセスの種類を問われたときは答えに含めない。

## 確認問題

### 問1（全て選択）

EUC_JP のデータベースに、UTF8 のクライアントから接続する。正しいものをすべて選べ。

- A. `client_encoding` を `UTF8` にすれば、サーバーが UTF8 と EUC_JP の間を自動で変換する
- B. `SET client_encoding TO 'UTF8';` で、そのセッションの `client_encoding` を変えられる
- C. 環境変数 `PGCLIENTENCODING` で、`client_encoding` を指定できる
- D. `SET server_encoding TO 'UTF8';` で、データベースのエンコーディングを UTF8 に変えられる

### 問2（入力）

psql で、現在の `client_encoding` を表示する SQL を答えよ。

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | A、B、C | データベースのエンコーディングは作成時に決まり、あとから変えられない。D は `parameter "server_encoding" cannot be changed` というエラーになる（`context` が `internal`） |
| 2 | `SHOW client_encoding;` | psql のメタコマンドなら、引数なしの `\encoding` でも表示できる |
