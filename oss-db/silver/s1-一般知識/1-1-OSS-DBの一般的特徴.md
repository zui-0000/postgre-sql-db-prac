## 学習メモ

### PostgreSQL とは

- **オブジェクトリレーショナルデータベース管理システム（ORDBMS）**。カリフォルニア大学バークレー校で開発された POSTGRES 4.2 がもとになっている。
- SQL を使い、さらに独自に拡張している。
- 開発しているのは **PostgreSQL Global Development Group** というコミュニティ。特定の企業が所有しているソフトウェアではない。

### 成り立ち

| 年 | 出来事 |
| --- | --- |
| 1986 | カリフォルニア大学バークレー校で、Michael Stonebraker 教授のもと POSTGRES プロジェクトが始まる |
| 1989 | POSTGRES Version 1 をリリース |
| 1994 | バークレーでの最後のリリース POSTGRES 4.2。同じ年に Andrew Yu と Jolly Chen が SQL のインタプリタを追加し、Postgres95 として公開する（問い合わせ言語を PostQUEL から SQL に置き換えた） |
| 1996 | 名前を **PostgreSQL** に変更。バージョン番号はバークレー時代の続きで **6.0** から始まる |
| 2001 | ACID に準拠する |

名前を変えたのは、「Postgres95」という名前をずっと使い続けるのは難しかったため。PostgreSQL という名前には、元の POSTGRES と、SQL に対応した後のバージョンとのつながりが表れている。

### 主な機能

公式ドキュメントでは、次の機能を持つと説明されている。

- 複雑な問い合わせ
- 外部キー
- トリガー
- 更新可能なビュー
- トランザクションの整合性
- 多版型同時実行制御（MVCC）

**拡張性が高い**のも大きな特徴で、ユーザーが次のものを追加できる。

- データ型
- 関数
- 演算子
- 集約関数
- インデックスの種類（インデックスメソッド）
- 手続き言語

公式サイトの About ページでは、機能を次のように分類している。

| 分類 | 主な機能 |
| --- | --- |
| データ型 | 整数、数値、文字列、真偽値、日付と時刻、配列、範囲型、UUID、JSON/JSONB、XML、幾何データ型、複合型、ユーザー定義型 |
| データの整合性 | UNIQUE、NOT NULL、主キー、外部キー、排他制約、明示的なロック、アドバイザリロック |
| 同時実行と性能 | インデックス（B-tree、GiST、SP-GiST、GIN、BRIN など）、クエリの最適化、MVCC、並列処理、テーブルのパーティショニング、JIT コンパイル |
| 信頼性と障害からの復旧 | WAL（先行書き込みログ）、レプリケーション（非同期、同期、論理）、PITR（ポイントインタイムリカバリ） |
| セキュリティ | 認証（SCRAM-SHA-256、LDAP、証明書など）、アクセス制御、列単位と行単位のセキュリティ |
| 拡張性 | ストアド関数とストアドプロシージャ、複数の手続き言語、外部データラッパー（FDW）、拡張機能 |
| 国際化と全文検索 | 多言語の文字セット、ICU の照合順序、全文検索 |

TypeScript で例えると、拡張機能は npm のパッケージに近い。`CREATE EXTENSION` を実行すると、本体を作り直さずに機能を追加できる。

### ライセンス

#### PostgreSQL License

PostgreSQL は **PostgreSQL License** で配布されている。BSD や MIT に似た、制限のゆるいライセンス。

- 目的を問わず、**無料で**、書面の契約なしに、使用・複製・改変・配布できる。
- 条件は、すべての複製に**著作権表示とライセンス文を含める**ことだけ。
- **無保証**。問題が起きても、著作権者は責任を負わない。
- 個人・商用・学術のどの目的でも使える。
- 改変したソフトウェアを配布するときに、ソースコードを公開する義務はない（後述のコピーレフトではない）。
- PostgreSQL Global Development Group は、ライセンスを変更する予定はないと明言している。

#### オープンソースの定義

「オープンソース」の条件は、**Open Source Initiative（OSI）** が「オープンソースの定義（OSD）」として定めている。

| 番号 | 条件 | 内容 |
| ---: | --- | --- |
| 1 | 自由な再配布 | 誰でもソフトウェアを販売したり、無料で配ったりできる |
| 2 | ソースコード | ソースコードを含み、ソースコードでも配布できる |
| 3 | 派生物 | 改変や派生物を認め、同じ条件で配布できる |
| 4 | 作者のソースコードの完全性 | 派生物に、元とは違う名前やバージョン番号を付けるよう求めてよい |
| 5 | 個人やグループの差別の禁止 | 特定の人やグループを差別しない |
| 6 | 利用分野の差別の禁止 | 特定の分野（たとえば商用）での利用を制限しない |
| 7 | ライセンスの分配 | 再配布を受けた人にも、追加の契約なしに同じ権利が及ぶ |
| 8 | 特定製品に限定しない | 特定のディストリビューションの一部であることを条件にしない |
| 9 | ほかのソフトウェアを制限しない | 一緒に配布されるほかのソフトウェアに制限をかけない |
| 10 | 技術的に中立 | 特定の技術やインターフェースを前提にしない |

#### 寛容型ライセンスとコピーレフト

オープンソースのライセンスは、改変したものを配布するときの条件で大きく2つに分かれる。

| 種類 | 代表的なライセンス | 改変して配布するとき | DB の例 |
| --- | --- | --- | --- |
| 寛容型（permissive） | BSD、MIT、PostgreSQL License | 同じ自由を引き継がなくてよい。ソースコードを公開しなくてもよい | PostgreSQL |
| コピーレフト | GPL | 派生物にも同じ自由を引き継ぐ必要がある | MySQL |

- **コピーレフト**とは、著作物に一定の自由を与える代わりに、派生物にも同じ権利を残すよう求める仕組み。代表は GNU General Public License（GPL）。
- **MySQL** は GPLv2 と商用ライセンスの**デュアルライセンス**。自社のソフトウェアと組み合わせて配布し、そのソースコードを GPLv2 で公開したくない場合は、Oracle と商用ライセンスの契約を結ぶ。

TypeScript で例えると、MIT ライセンスの npm パッケージを使ったアプリは、ソースコードを公開しなくても配布できる。PostgreSQL License はこれと同じ感覚で使える。

### コミュニティ

#### 開発体制

PostgreSQL は、世界中の開発者が参加する **PostgreSQL Global Development Group** というコミュニティで開発されている。企業が開発者を雇って作っているのではなく、インターネットを通じて開発者が集まっている。

| 役割 | 内容 |
| --- | --- |
| コアチーム | 長年活動している7人のメンバー。新しいメンバーは、今のコアチームが任命する。リリースの調整、非公開の連絡の窓口、方針の発表、コミット権限などの管理、合意できないときの判断などを担う |
| コミッター | リポジトリにコミットする権限を持つ開発者。パッチをレビューして取り込む |
| コントリビューター | パッチの作成、レビュー、テスト、ドキュメントなどで貢献する人 |

#### メーリングリスト

| メーリングリスト | 用途 |
| --- | --- |
| pgsql-hackers | 開発に関する議論 |
| pgsql-general | ユーザーの一般的な質問 |
| pgsql-sql | SQL に関する質問 |
| pgsql-bugs | バグの報告 |
| pgsql-docs | ドキュメントに関する指摘 |

購読していない人の投稿は、管理者の確認を経るので届くのが遅れる。

#### CommitFest

**CommitFest** は、コミッターとコントリビューターがパッチのレビューやテストに集中して、取り込みを進める期間。

- パッチは CommitFest のアプリケーションに登録する。
- 1回のリリースサイクルで、通常5回（7月、9月、11月、1月、3月）開かれる。
- **誰でも参加できる**。パッチを提出する、レビューを担当する、といった形で関われる。

#### 日本のコミュニティ

**特定非営利活動法人 日本PostgreSQLユーザ会（JPUG）** が、日本での情報交換を進めている。

- PostgreSQL のマニュアルの日本語訳を提供している
- 毎年カンファレンス（PostgreSQL Conference Japan）を開いている
- メーリングリストや Slack で技術的な相談ができる
- 北海道、東北、新潟、関西などに支部がある

### メジャーバージョンとマイナーバージョン

#### 番号の付け方

PostgreSQL 10 から、番号の付け方が変わった。

| | メジャーバージョン | マイナーバージョン | 例 |
| --- | --- | --- | --- |
| 10 以降 | **1つ目**の数字 | **2つ目**の数字 | 18.6 → メジャー 18、マイナー 6 |
| 9.6 以前 | **1つ目と2つ目**の数字 | **3つ目**の数字 | 9.6.24 → メジャー 9.6、マイナー 24 |

#### メジャーリリースとマイナーリリースの違い

| | メジャーリリース | マイナーリリース |
| --- | --- | --- |
| 中身 | 新しい機能を含む、大きな変更 | よく起きるバグの修正、セキュリティの修正、データ破損の修正だけ。**新機能は入らない** |
| データディレクトリの互換性 | ない | ある |
| アップグレードの方法 | ダンプしてリストアする、または `pg_upgrade` を使う | サーバーを止めて、バイナリを入れ替えて、再起動するだけ |

TypeScript で使う npm の semver と比べると、PostgreSQL のマイナーバージョン（18.6 の「6」）は semver の**パッチ**に近い。semver のマイナーと違って、新機能は入らない。

#### アップグレードするときにサーバーを止める必要があるか

サーバーを1台だけで動かしている場合、メジャーでもマイナーでも**一度はサーバーを止める必要がある**。サーバーは起動したときに読み込んだバイナリで動き続けるので、新しいバイナリを使うには起動し直すしかないため。TypeScript で例えると、Node のアプリのコードを差し替えても、プロセスを再起動するまでは古いコードのまま動き続けるのと同じ。

ただし、止まっている時間は方法によって大きく違う。

| 種類 | 方法 | サーバーの停止 | 止まっている時間 |
| --- | --- | --- | --- |
| マイナー | バイナリを入れ替える | サーバーを止めてからバイナリを入れ替え、再起動する | 再起動にかかる時間だけ。データディレクトリはそのまま使える |
| メジャー | `pg_dumpall` でダンプしてリストアする | ダンプを取るあいだ旧サーバーは起動しているが、更新は止めておく。そのあと旧サーバーを止めて、新しいクラスタにリストアする | 長い。データが多いほど長くなる |
| メジャー | `pg_upgrade` | 新旧どちらのサーバーも止めた状態で実行する | `--link` モードなら数分 |
| メジャー | ロジカルレプリケーション | 新しいバージョンのサーバーを別に立てて同期させ、切り替えてから旧サーバーを止める | 切り替えにかかる数秒だけ |

- ロジカルレプリケーションを使えば、サービス全体が止まるのは数秒で済む。TypeScript の世界でいうブルーグリーンデプロイと同じ考え方。ただし、旧サーバーのプロセスを止めることに変わりはない。
- 試験では「マイナーは停止 → バイナリの入れ替え → 起動だけ。メジャーはダンプとリストアか `pg_upgrade` が必要」を押さえておく。`pg_upgrade` やロジカルレプリケーションによるアップグレードは、Silver の出題範囲の用語には入っていない。

#### 実機で確認する

```sh
docker compose exec db postgres --version
docker compose exec db psql -U postgres -c "SELECT version()" -c "SHOW server_version_num"
```

```text
postgres (PostgreSQL) 18.6 (Debian 18.6-1.pgdg13+2)
PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2) on aarch64-unknown-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit
180006
```

`server_version_num` は、バージョンを比較しやすい数値にしたもの。18.6 は「18 × 10000 + 6」で `180006` になる。

### リリースサイクルとサポートポリシー

- **メジャーリリース**: 約1年に1回。最近は毎年9〜10月ごろに出ている。
- **マイナーリリース**: 少なくとも3か月に1回。サポート中のすべてのメジャーバージョンに、同時に出る。緊急のセキュリティ修正などで、予定外のリリースが出ることもある。
- **サポート期間**: メジャーバージョンごとに、**初回リリースから5年間**。期間が終わると最後のマイナーバージョンを出して、サポートを終了（EOL）する。

2026年9月時点のサポート状況:

| バージョン | 最新のマイナー | 初回リリース | サポート終了 |
| --- | --- | --- | --- |
| 18 | 18.6 | 2025-09-25 | 2030-11-14 |
| 17 | 17.11 | 2024-09-26 | 2029-11-08 |
| 16 | 16.15 | 2023-09-14 | 2028-11-09 |
| 15 | 15.19 | 2022-10-13 | 2027-11-11 |
| 14 | 14.24 | 2021-09-30 | 2026-11-12 |
| 13 | 13.23 | 2020-09-24 | 2025-11-13（終了済み） |
| 12 | 12.22 | 2019-10-03 | 2024-11-21（終了済み） |

### バグ報告

| 報告の種類 | 報告先 |
| --- | --- |
| 通常のバグ | Web の[バグ報告フォーム](https://www.postgresql.org/account/submitbug/)、または `pgsql-bugs@lists.postgresql.org` |
| セキュリティの問題 | **`security@postgresql.org`**（公開のメーリングリストには送らない） |
| ドキュメントの問題 | `pgsql-docs@lists.postgresql.org` |

アドレスの見分け方: メーリングリストは `pgsql-〇〇@lists.postgresql.org` の形で、`lists.` が付く。セキュリティの窓口は `security@postgresql.org` で、`lists.` が付かない。公開のメーリングリストではないため。

報告する前に、TODO リストや FAQ を見て、すでに知られている問題でないかを確認する。

報告に含める情報:

- 再現手順（`CREATE TABLE` や `INSERT` も含めて、それだけで再現できるもの）
- 実際の出力（エラーメッセージは省略せずに全部。psql なら `\set VERBOSITY verbose` で詳しく出せる）
- 期待していた出力
- 起動オプションや、デフォルトから変えた設定
- PostgreSQL のバージョン（`SELECT version();` の結果）
- OS やハードウェアなどの環境

やってはいけないこと:

- pgsql-general、pgsql-sql（ユーザーの質問用）や pgsql-hackers（開発の議論用）にバグ報告を送る
- 「動かない」「落ちた」とだけ書く。何が起きたのかを具体的に書く
- 原因を推測して書く

## ⚠️ 試験と最新版の違い

- **サポート中のバージョンが違う。** 出題範囲が作られた2023年2月の時点では、サポート中のバージョンは 11〜15 だった。2026年9月の時点では 14〜18 で、14 も2026年11月12日にサポートが終わる。「サポート中のバージョン」を問う問題では、いつの時点の話なのかに注意する。
- **公式サイトの機能一覧には、試験の基準より新しい機能も載っている。** たとえば About ページの認証方式には OAuth 2.0（PG18 で追加）が含まれる。試験では PG 12〜14 の機能を前提に答える。

### 解答

| 問 | 答え | 解説 |
| --- | --- | --- |
| 1 | B | PostgreSQL License は寛容型のライセンス。ソースコードを公開する義務はなく、契約も要らない。ただし著作権表示とライセンス文は含める必要がある |
| 2 | B、D、E | マイナーリリースに新機能は入らない。データディレクトリの互換性があるので、ダンプとリストアも要らない |
| 3 | B | 9.6 以前は、1つ目と2つ目の数字がメジャーバージョン |
| 4 | 5 | 初回リリースから5年間 |
| 5 | C | セキュリティの問題は、修正が出る前に公開されて悪用されないよう、非公開で報告する。A と B は公開のメーリングリスト、D のバグ報告フォームは通常のバグ用 |
| 6 | A、C、E | pgsql-hackers は開発の議論用。報告は具体的に書き、原因の推測はしない |
| 7 | B | A、D は誤り。C も誤りで、最初の問い合わせ言語は PostQUEL。Postgres95 で SQL に置き換えた |
| 8 | B | コアチームは今のメンバーが任命する。パッチは誰でも提出でき、CommitFest にも誰でも参加できる |
