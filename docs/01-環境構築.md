# 01 環境構築

OSS-DB Silver の学習に使う PostgreSQL の環境を、Docker Compose で用意する。

## 構成

| サービス | 役割 | PostgreSQL サーバー | 主に使う章 |
| --- | --- | --- | --- |
| db | 普段使うサーバー | コンテナの起動と同時に自動で起動する | S2.3、S2.5、S3（SQL、権限、VACUUM、`pg_dump`） |
| sandbox | 運用管理を自分の手で練習する環境 | 起動しない。`initdb` と `pg_ctl` を自分で実行する | S2.1、S2.2、S2.4（`initdb`、`pg_ctl`、PITR） |

動作を確認したバージョン（2026-09-15）:

| ソフトウェア | バージョン |
| --- | --- |
| Docker Desktop | 4.91.0 |
| Docker Engine | 29.8.0 |
| Docker Compose | v5.5.1 |
| PostgreSQL（イメージ） | `postgres:18.6`（18.6-1.pgdg13+2） |

コマンドは `docker compose`（スペース区切り）で書く。ハイフン付きの `docker-compose` は Compose v1 の頃の書き方で、この環境には入っていない。

## セットアップ

```sh
docker compose up -d --wait
docker compose ps
```

- `up` で **db と sandbox の両方**が起動する。
- `--wait` を付けると、db の healthcheck が通るまで待ってからコマンドが終わる。

ホストの 5432 番ポートがほかで使われているときは、リポジトリの直下に `.env` を作ってポートを変える（`.env` は git の管理外）。

```sh
echo "POSTGRES_PORT=15432" > .env
```

## db の使い方

### psql で接続する

```sh
docker compose exec db psql -U postgres
```

コンテナの中から Unix ソケットで接続するので、パスワードは聞かれない（理由は「認証の設定」を参照）。

ホストの GUI ツールなどから接続するときは、次の値を使う。ホストには psql を入れていないので、コマンドで操作するときはコンテナの中の psql を使う。

| 項目 | 値 |
| --- | --- |
| ホスト | `127.0.0.1` |
| ポート | `5432`（`.env` の `POSTGRES_PORT` で変えた場合はその値） |
| ユーザー | `postgres` |
| パスワード | `postgres` |

### 止める・再開する

```sh
docker compose stop db    # 止める（データは残る）
docker compose start db   # 再開する
```

`docker compose stop` は、PostgreSQL に SIGINT を送る（イメージの `STOPSIGNAL SIGINT`）。SIGINT は **fast シャットダウン**にあたり、ログには `received fast shutdown request` と出る。

| シグナル | 停止モード |
| --- | --- |
| SIGTERM | smart |
| SIGINT | fast |
| SIGQUIT | immediate |

### データを消して最初からやり直す

```sh
docker compose rm -sf db
docker volume rm postgre-sql-db-prac_db-data
docker compose up -d --wait db
```

### パスワードについて

パスワードは `compose.yaml` に `postgres` と直接書いている。ローカルの学習専用で、次の2つの条件がそろっているため。

- ポートを `127.0.0.1` にだけ公開していて、ほかの端末からは接続できない
- 練習用のデータしか入れない

`127.0.0.1:` を外して、すべてのネットワークに公開する場合は、固定のパスワードを使わない。

**`POSTGRES_PASSWORD` を変えても、作成済みのクラスタのパスワードは変わらない。** エントリポイントがこの値を使うのは、データディレクトリが空のとき（最初の `initdb`）だけだからだ。パスワードを変えたいときは、上の手順でボリュームを作り直すか、`ALTER ROLE postgres PASSWORD '新しいパスワード';` を実行する。

## sandbox の使い方

### 入る

```sh
docker compose exec sandbox bash
```

`postgres` ユーザーとして入る（`compose.yaml` の `user: postgres`）。ホームディレクトリは `/var/lib/postgresql`。

### クラスタを作って、起動・停止する

```sh
initdb -D ~/data                         # データベースクラスタを作る
pg_ctl -D ~/data -l ~/server.log start   # 起動する（ログは ~/server.log に出る）
pg_ctl -D ~/data status                  # 状態を確認する
psql                                     # 接続する
pg_ctl -D ~/data -m fast stop            # 停止する（-m で smart / fast / immediate を選ぶ）
```

- `-D` を省略すると、環境変数 `PGDATA`（イメージでは `/var/lib/postgresql/18/docker`）が使われる。
- **サーバーを止めても、コンテナは止まらない。** コンテナの PID 1 が postgres ではないため（「db と sandbox を分けた理由」を参照）。
- fast シャットダウンのログに `checkpoint starting: shutdown immediate` と出る。この `immediate` は「チェックポイントを待たずに全速で実行する」という意味で、停止モードの immediate とは別物。

### まっさらに戻す

```sh
docker compose rm -sfv sandbox
docker compose up -d sandbox
```

`-v` を付けると、sandbox に付いている匿名ボリュームも一緒に消える（「PG18 のイメージの変更」を参照）。db のデータには影響しない。

### 注意: サーバーを止めてからコンテナを止める

sandbox のサーバーを起動したまま `docker compose stop sandbox` や `down` を実行すると、PostgreSQL は正常に終了できない。コンテナの PID 1 が終わると、コンテナ内の残りのプロセスは強制終了されるため。次に起動したときはクラッシュリカバリになる。先に `pg_ctl stop` を実行する。

## db と sandbox を分けた理由

公式イメージのエントリポイント（`docker-entrypoint.sh`）は、コンテナの起動時に次の処理をする。

1. CMD が `postgres` のときだけ、2 以降を実行する
2. データディレクトリが空なら `initdb` を実行する
3. サーバーを一時的に起動して（Unix ソケットだけで待ち受ける）、初期化用の SQL を流してから停止する
4. `exec postgres` で、postgres をコンテナの PID 1 にする

Docker では PID 1 が終了するとコンテナも終了する。そのため db で `pg_ctl stop` を実行すると、コンテナごと止まる。`initdb` も自動で実行されてしまう。これでは S2.1（`initdb`）、S2.2 と S2.5（`pg_ctl`）、S2.4（PITR のリストア）を練習できない。

そこで sandbox では、CMD を `sleep infinity` に上書きして 1 の条件から外している。PostgreSQL のコマンドだけが入った Linux 環境になり、試験が前提にしている「サーバーに PostgreSQL をインストールした直後」の状態に近くなる。

```text
【db】コンテナ = PostgreSQL サーバー
└─ PID 1: postgres        ← pg_ctl stop するとコンテナごと終了する
    ├─ checkpointer
    └─ ...

【sandbox】コンテナ = PostgreSQL が入っているだけの Linux 環境
└─ PID 1: docker-init（tini）
    └─ sleep infinity     ← 待機しているだけ
    └─ postgres           ← pg_ctl start で起動する。止めてもコンテナは残る
```

TypeScript で例えると、db は `CMD ["node", "server.js"]` のコンテナ、sandbox は開発用コンテナに入って自分で `npm run dev` を起動したり止めたりする使い方にあたる。

## compose.yaml の設定と理由

| 設定 | 理由 |
| --- | --- |
| `image: postgres:18.6` | バージョンを固定する。`latest` にすると、いつの間にか 19 に上がる（package.json で `^` を使わず、lockfile で固定するのと同じ） |
| `POSTGRES_PASSWORD: postgres` | ローカルの学習専用なので、固定値を直接書く（「パスワードについて」を参照） |
| `127.0.0.1:${POSTGRES_PORT:-5432}:5432` | ホストの 127.0.0.1 だけで待ち受けて、同じネットワークのほかの端末から接続させない。ポートは `.env` の `POSTGRES_PORT` で変えられる（`.env` がなければ 5432） |
| `db-data:/var/lib/postgresql` | 名前付きボリュームにして、コンテナを作り直してもデータが残るようにする |
| healthcheck の `pg_isready -h 127.0.0.1` | 初期化が終わる前に healthy にならないようにする（下の「healthcheck を TCP で確認する理由」を参照） |
| `command: ["sleep", "infinity"]` | エントリポイントによる `initdb` とサーバーの自動起動を止める |
| `init: true` | PID 1 を tini にする。`pg_ctl` で起動したサーバーは、起動したシェルが終わると PID 1 の子プロセスになる。`sleep` は子プロセスの後始末（終了したプロセスの回収）をしないので、tini にやらせる |
| `user: postgres` | `docker compose exec` で postgres ユーザーとして入る。PostgreSQL のサーバーと `initdb` は root では実行できない |

### healthcheck を TCP で確認する理由

エントリポイントの手順 3 の一時サーバーは、`listen_addresses=''` で起動し、Unix ソケットだけで待ち受ける。`pg_isready` はオプションを付けないと Unix ソケットで確認するので、一時サーバーに応答されて、初期化の途中で healthy になってしまう。

`-h 127.0.0.1` を付けて TCP で確認すると、手順 4 のサーバー（`listen_addresses='*'`）が起動してから healthy になる。

## PG18 のイメージの変更

PostgreSQL 18 のイメージから、データの置き場所が変わった。

| 項目 | 17 まで | 18 から |
| --- | --- | --- |
| `PGDATA` | `/var/lib/postgresql/data` | `/var/lib/postgresql/18/docker` |
| `VOLUME` | `/var/lib/postgresql/data` | `/var/lib/postgresql` |

- 古い記事のとおりに `/var/lib/postgresql/data` にマウントすると、エントリポイントが検出してエラーで止まる。
- sandbox にはボリュームを指定していないが、イメージの `VOLUME /var/lib/postgresql` によって**匿名ボリューム**が自動で付く。`docker compose rm` で消すときに `-v` が必要なのはこのため。

## 認証の設定（pg_hba.conf）

db の `pg_hba.conf` の有効な行は次のとおり。上の6行は `initdb` が作るデフォルトで、最後の1行はエントリポイントが追加する（値は `password_encryption` の設定から取る）。

```text
local   all             all                                     trust
host    all             all             127.0.0.1/32            trust
host    all             all             ::1/128                 trust
local   replication     all                                     trust
host    replication     all             127.0.0.1/32            trust
host    replication     all             ::1/128                 trust
host all all all scram-sha-256
```

`pg_hba.conf` は**上から順に見て、最初に一致した行**が使われる。そのため、接続元によって認証が変わる。

| 接続元 | 一致する行 | パスワード |
| --- | --- | --- |
| コンテナの中から Unix ソケット（`docker compose exec db psql`） | `local all all trust` | 不要 |
| コンテナの中から `127.0.0.1` | `host all all 127.0.0.1/32 trust` | 不要 |
| 別のコンテナから（compose ネットワーク経由） | `host all all all scram-sha-256` | 必要 |
| ホストの公開ポート経由 | `host all all all scram-sha-256` | 必要 |

公開ポート経由の接続は、PostgreSQL からは Docker ネットワークのゲートウェイ（確認したときは `172.23.0.1`）からの接続に見える。`127.0.0.1` からの接続には見えないので、パスワードが必要になる。

`pg_hba.conf` の書き方は [S2.3 設定ファイル](../oss-db/silver/s2-運用管理/2-3-設定ファイル.md) で詳しく学ぶ。

## よく使うコマンド

| やりたいこと | コマンド |
| --- | --- |
| 全部起動する | `docker compose up -d --wait` |
| 状態を見る | `docker compose ps` |
| db に psql で入る | `docker compose exec db psql -U postgres` |
| sandbox に入る | `docker compose exec sandbox bash` |
| db のログを見る | `docker compose logs -f db` |
| 全部止める（データは残る） | `docker compose stop` |
| sandbox をまっさらに戻す | `docker compose rm -sfv sandbox && docker compose up -d sandbox` |
